# ⚠️ Ловушки, до первой команды

**1. Риг сейчас на ЖИВОЙ ПОЧТЕ, не на фикстуре.** Это меняет всё: 113+ настоящих точек вместо
трёх, разреженный листинг, реальные задержки. Вернуть на фикстуру — `WOODEV_TEST_PICKUP_LIVE_POCHTA`
в `false` в гитигнореном `.wp-env.override.json` + `npx wp-env start`.

**2. Риг отдаёт РАБОЧЕЕ ДЕРЕВО.** Чекаут другой ветки мгновенно откатывает правки первой. Прежде
чем просить кого-то посмотреть — назови ветку И константы. Готча
`rig-serves-the-working-tree-branch-switch-reverts-fixes`.

```bash
git branch --show-current
MSYS_NO_PATHCONV=1 npx wp-env run cli wp config list --fields=name,value | grep WOODEV_TEST
```

**3. `MSYS_NO_PATHCONV=1` обязателен** для любого `wp-env run` с путём внутри контейнера — иначе
MSYS подменит `/var/www/html/...` на `C:/Program Files/Git/...`. Готча
`wpenv-windows-gitbash-path-mangling`.

**4. Локальный jest считает воркдеревья субагентов.** Достоверный итог только так:

```bash
npm run test:js -- --roots "<rootDir>/tests/js"
```

**5. Никогда `npx jest`** — теряет jsdom, печатает фантомные падения.

**6. В бриф исполнителю — ВЕСЬ набор проверок**, перечислением: PHP → `composer test:unit` +
`composer phpcs` + `composer phpstan`; JS → `npm run test:js -- --roots …`. s57 забыла
`test:unit`, и исчерпывающий i18n-тест упал в CI.

**7. Codex на этой машине НЕ ЧИТАЕТ ФАЙЛЫ.** Диффы — только инлайном в промпте. Рабочий приём:
записать дифф в скретчпад, дать субагенту прочитать и вложить текстом.

**8. Многострочный `wp eval` и heredoc через `wp-env run` съедаются кавычками.** Рабочий приём:
писать PHP в файл, класть в контейнер через `wp eval "file_put_contents(...base64_decode(...))"`,
запускать `wp eval-file`. Bash-heredoc с апострофом внутри тоже ломается — писать скрипт файлом.

**В контейнере рига лежит ВРЕМЕННЫЙ mu-плагин** `wp-content/mu-plugins/woodev-null-trace.php` —
трассировщик для #230. Удалить, когда карточка закроется.

# Очередь

## 1. #234 — точки не накапливаются. **Нужно решение оператора по объёму**

Симптом: в кадре 10 точек, зум +1 → видно 5, зум −1 обратно → по-прежнему 5. Покупатель помнит
предыдущий кадр и не понимает, куда делись точки.

**Механика Почты уже разобрана в бандле** (`plugins-reference/pochta-widget/main.a7d147fb….js`):

```js
p(function(t){ return e.has(t.id) ? null : (e.add(t.id), { type:"Feature", id:t.id, … }) })
h && (n = { prevTopRightPoint: h[0], prevBottomLeftPoint: h[1] });
```

`e` — `Set` уже виденных id: на карте ОБЪЕДИНЕНИЕ показанного за сессию. `prev*Point` со второго
запроса — подсказка серверу отдать дельту, и тогда накопление на клиенте обязательно.

**Почему не сделал сам:** у нас `setPoints()` — полная перерисовка по прямому решению спеки, и это
записано в докблоке. Накопление меняет семантику ФРЕЙМВОРКА, а не фикстуры. Открытые вопросы:
когда сбрасывать накопленное (смена фильтра типов, поиск по адресу, `refresh()`), и что делать с
сайдбаром — он показывает «видимые в кадре», и это как раз правильно, то есть карта и список
намеренно разойдутся.

# Что стоило ошибок в s58

**Поле, одинаковое во всех записях, не может быть вердиктом.** `cashPayment` был замаплен на
`accepts_cod` по формулировке моей же карточки #226. Замер: `false` у всех 12 точек обоих типов.
Покупателю выехало инверсией. **Проверяй РАЗБРОС поля по живым записям, прежде чем вешать на него
решение** — имя поля это заявка, а не доказательство.

**Настоящее правило часто уже написано в продакшн-плагине оператора.** COD-правило годами лежало
в `plugins-reference/woodev-russian-post/includes/classes/checkout.php`. Заглядывать туда ДО того,
как выводить логику из API.

**Окаменелый докблок — второй раз за три сессии — пометил дыру в проводке.** «Переключение табов
проходит через `cardOpened`» было неправдой. Когда докблок уверенно описывает механизм, проверь,
что он есть.

**Тесты контрола проверяют контрол, а не его оповещение.** Все тесты табов проверяли DOM; ни один
не проверял, что кто-то снаружи узнал о смене точки.

**У кэша спрашивай, что ограничивает пространство КЛЮЧЕЙ, а не время жизни записи.** Кэш по bbox
неограничен по построению; укорачивание TTL лечило не то.

**Две по отдельности верные правки могут сложиться в дефект.** #232 — это Part 1 и Part 3 из #228,
каждая обоснованная, вместе дающие мигающую карточку.
