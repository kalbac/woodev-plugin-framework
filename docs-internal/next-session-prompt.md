# ⚠️ Что важно знать про то, что s81 нашла

Две находки — не про #362 как таковой, а про то, как вообще устроен чекаут WooCommerce. Обе стоили
дефекта в уже «отгруженной» фиче, обе теперь готчи. Если будешь трогать поля чекаута — прочти их до
кода, а не после:

1. `js-hidden-checkout-field-is-still-required-server-side` — **WooCommerce валидирует НАЛИЧИЕ, а не
   видимость.** Скрытая строка всё равно постит пустой инпут, и заказ падает с ошибкой про поле,
   которого покупатель не видит. Клиентское правило WC (`.validate-required:visible`) скрытую строку
   пропускает, серверное — нет; блокирует именно сервер. Правило: **что браузер прячет — то сервер
   обязан перестать требовать, в том же самом условии.**
2. `wc-address-i18n-reshows-fields-with-an-inline-display-block` — **`address-i18n.js` на каждом
   `country_to_state_changed` делает `field.show()`**, то есть пишет ИНЛАЙНОВЫЙ `display: block`,
   который бьёт классовое правило без `!important`. Коварство в тайминге: сразу после переключения
   строка действительно прячется, и быстрая проверка проходит; возвращается она на следующем проходе
   локали. Проверять надо так: применить класс, **принудительно дёрнуть проход локали**
   (`dispatchEvent(new Event('change'))` на поле страны) и только потом читать
   `getComputedStyle(row).display` — не `offsetParent`.

Побочно оттуда же: поле, скрытое через локаль, WooCommerce **очищает**. Прятать «через локаль вместо
CSS» нельзя нигде, где значение обязано доехать до заказа.

# 🧠 Процессные уроки s81 — они сэкономят тебе проход

- **Реализация и риговая проверка сериализуются.** Риг отдаёт рабочее дерево, снапшота у него нет:
  агент, дописавший вызов метода, которого ещё нет, положил риг целиком — на любой запрос, включая
  `wp eval-file`. Параллелить можно только агентов, не трогающих одни и те же файлы. Дописано в
  готчу `rig-serves-the-working-tree-branch-switch-reverts-fixes`.
- **Живой прогон, который «прошёл», — не доказательство, пока не понимаешь, ПОЧЕМУ он прошёл.**
  Мой первый успешный заказ прошёл лишь потому, что клик по радио заранее обновил сессию через
  `update_order_review`. Codex это увидел и назвал P0 — справедливо: фильтр
  `woocommerce_checkout_fields` срабатывает на `get_posted_data()` (строка 1381), а `update_session()`
  только на 1385, и поля к тому моменту уже закэшированы в `$this->fields`.
- **Критику стоит доверять, но каждую находку проверять по коду.** Из трёх находок за две сессии
  две оказались реальными (P1 про `get_control()`, P0 про сессию), и обе я подтвердил чтением
  исходника прежде, чем что-то менять.

# ⚠️ Ловушки, всё ещё в силе

1. Мутация тестов через `perl` молча не применяется в CRLF-дереве — мутировать через `Edit`.
2. `ReflectionProperty::setValue()` на приватном свойстве — guard `setAccessible()` по версии PHP.
3. WooCommerce определяет страну свежего гостя ГЕОЛОКАЦИЕЙ с фолбэком `US`.
4. `Woodev_Setting::get_value()` кэширует — хендлер строить ПОСЛЕ подмены `get_option`.
5. JS-тесты ИЗ BASH; `git add -A` подметает чужое — перечислять файлы явно.
6. Стековые PR: `stacked-pr-github-mechanics`.
7. `billing_city` на риге — select2 старого демо §8, его источник подсказок ничего не отдаёт. Это НЕ
   наш слой, но он мешает оформить заказ через UI. Оформлять заказ надо POST-ом на `/?wc-ajax=checkout`
   с подставленным значением — s81 так и делала.
