# ⚠️ Ловушки, до первой команды

**1. Риг отдаёт РАБОЧЕЕ ДЕРЕВО.** wp-env монтирует репозиторий: чекаут другой ветки мгновенно
откатывает правки первой, а переключение фикстуры убирает данные, на которых виден симптом.
Прежде чем просить кого-то посмотреть — назови ветку И константы. Готча
`rig-serves-the-working-tree-branch-switch-reverts-fixes`.

```bash
git branch --show-current
npx wp-env run cli wp config list --fields=name,value | grep WOODEV_TEST
```

**2. Локальный jest считает воркдеревья субагентов.** Достоверный итог только так:

```bash
npm run test:js -- --roots "<rootDir>/tests/js"
```

Проверять `ls .claude/worktrees/`, а не `git worktree list`. Готча
`jest-scans-agent-worktrees-inside-the-repo`.

**3. Никогда `npx jest`** — теряет jsdom, печатает фантомные падения. Готча
`npx-jest-bypasses-wp-scripts-jsdom`.

**4. В бриф исполнителю — ВЕСЬ набор проверок.** s57 заказала `composer phpcs`, забыла
`composer test:unit`, и исчерпывающий i18n-тест упал в CI. Если задача трогает PHP —
`composer test:unit` обязателен в бриффе, не подразумевается.

**5. Codex на этой машине НЕ ЧИТАЕТ ФАЙЛЫ** (`CreateProcessAsUserW: Access denied`). Диффы и
контекст давать ТОЛЬКО инлайном в промпте — иначе он честно откажется рецензировать, и это будет
выглядеть как сбой. Готча `codex-shell-sandbox-broken-windows`. Работает: записать дифф в
скретчпад, дать субагенту прочитать его и вложить в промпт codex текстом.

**Риг медленный, и это НЕ наш код:** `/wp-json/` ~16.7 с, листинг точек 7–13 с. Под viewport это

# Что стоило ошибок в s57

**«Брать последним» — это порядок, а не разрешение не брать.** Я не начал #226, решив за оператора,
что он скоро проснётся. Не решать за него, что успеется: если пункт в объёме — он в объёме.

**Записанный КОНТРАКТ — не записанный ПЕЙЛОАД.** Карточка #226 читалась исчерпывающе (эндпоинты,
обе ловушки, пагинация, таблица полей), но `geo`/`address` в ней были только ИМЕНАМИ ключей. 22
теста проходили против записи, которой ни один перевозчик не присылал. Одна живая выемка исправила
шесть допущений, три из них — настоящие баги. Прежде чем строить по чужой форме — проверь, есть ли
в источнике НАСТОЯЩИЕ БАЙТЫ.


**Замер, а не рассуждение — снова.** В #225 было три гипотезы; верной оказалась третья и наименее
очевидная («тождество объектов»), а первые две выглядели правдоподобнее. Инструментированная
проба на риге решила вопрос за один прогон. Не начинай чинить по самой красивой гипотезе.

**Самая опасная починка — почти правильная.** Лечение осиротевшего снимка по одному `key` группы
прошло все 776 тестов и при этом молча подменяло карточку ДРУГИМ ПВЗ посреди чтения, потому что
`key` — это координата, а не идентичность точки. Поймал критик, не тесты. Когда «чинишь
идентичность» — проверь, что сравниваешь именно идентичность.

**Устранение гонки может сделать неправильным собственный охранник.** Когда параллельные запросы
по одной точке стали невозможны, проверка «владею ли замком» на пути ПРИМЕНЕНИЯ ответа
превратилась из симметрии в потерю данных. Владение решает, кто ОТПУСКАЕТ замок; идентичность
решает, чей ответ ЛОЖИТСЯ. После каждой правки гонки перечитай ВСЕ охранники, которые её касались.

**Исполнителям явно давать право противоречить заданию.** Работает пятую сессию подряд. Этой
ночью исполнитель отверг предложенный критиком `Promise.resolve().then(...)`, потому что тот
сдвигает вызов dataSource на микротаск и ломает существующий контракт — и был прав.

**Карточку — ДО работы**, и двигать её в «В работе». Всё сделанное за ночь имело карточку.
