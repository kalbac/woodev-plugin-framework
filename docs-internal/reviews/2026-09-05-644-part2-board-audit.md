# #644 part 2 — every open board card verified against the code, s119 (2026-09-05)

**Scope:** all 60 open cards on board №6 (the 61st is #644 itself). Split across three parallel
read-only auditors run through Orca orchestration — group A the pickup/map, checkout-field and
location layers (18), group B framework core, payment gateway, licensing, the shipping model and the
release gates (17), group C infrastructure, tooling, docs and the «После v2» ideas (25).

**Method.** Each card's factual claim about the code was extracted from its body and comments, then
checked against the tree as it stands today — never against another document. Every verdict except
«НЕ ПРОВЕРЯЕТСЯ КОДОМ» carries a `path:line`, a symbol or a commit. Where a worker could not
establish an answer it says so instead of guessing; those admissions are kept verbatim below,
because they are the part of an audit that is usually quietly dropped.

**Acted on in s119:** #113, #148 and #381 closed as completed — each independently re-verified by
the coordinator before closing, never on a worker's word alone; #779 filed for the two Orca
capabilities #381 never covered; #182 and #652 narrowed by comment; the freeze condition written
onto all seven frozen map cards, which the board rule requires and none of them carried; #382 moved
to «Ждёт оператора», because its whole remainder is six questions for the operator.

**Two findings worth more than their cards.** #652's four unmeasured checkout scenarios turned out
to be three answered by code and one genuinely needing the rig — three-quarters of an operator task
removed before he spent a minute on it. And half of #182 describes `class-warehouse.php`, a file

**The pattern this audit exists for.** #113 and #148 both already carried a «кандидат на закрытие»
verdict from an earlier pass, and both stayed open for a month afterwards. Verifying a card and
acting on the verdict are two different steps, and the second is the one that gets skipped.

**A correction the audit produced against its own brief.** Group A's report notes that the brief it
was given said «семь карточек» while listing eight numbers. The brief was wrong; the licence to

## Пояснения к карточкам с особым вердиктом или важным нюансом

**#148 — УСТАРЕЛА, кандидат на закрытие.** Ровно то, что уже нашёл предыдущий проход (31.08): PR
#232/#234/#238/#248 (закрыты 08-09.08.2026, ни один не ссылается на #148) добавили постоянный
подписчик на `updated_checkout`, который для каждой ОТКРЫТОЙ сессии пикера вызывает
`session.refresh()` — тот забывает детали точек и перезапрашивает их заново, то есть вердикт
`selectable` пересчитывается после смены способа оплаты. Карточка при этом помечена
«Заморожено» батчем от 02.09.2026 («map tech-debt, ждёт pickup-слоя нового карьера») — сама
карточка НЕ называет это условие (см. общее замечание про заморозку ниже), а раз баг уже почищен
попутно, вопрос об условии заморозки для неё уже не актуален. Рекомендация: закрыть как
выполненное.

**#165 — УСТАРЕЛА-кандидат, но нужен риг.** Общий гейт `_cameraFit` в `focusGroup()` (PR #177,
07.08.2026) закрывает ровно тот класс гонки, который гипотеза Codex-критика описывала для этой
карточки, и код не изменился с 31.08. Но сам симптом карточки — маркер `resting` вместо `active`
после клика по строке списка — был воспроизведён 1 раз из 8 попыток ДО фикса и ни разу не
проверялся ПОСЛЕ. Рекомендация: закрыть как вероятно выполненное, но только после короткой
риговой проверки (это явно вне зоны read-only аудита) — не закрывать вслепую по одному чтению
кода.

## Важные находки, не меняющие вердикт (ПОДТВЕРЖДЕНА), но которые оператору стоит увидеть

**#182 — половина карточки стала мёртвой темой.** С момента последнего прохода (31.08.2026)
`class-warehouse.php` был целиком удалён коммитом `258b23c` (02.09.2026, PR #726 «remove the
warehouse scaffold», closes #141) вместе с `Warehouse_Store`, `Abstract_Warehouse_Store`,
`Warehouse_Admin` и `Abstract_Warehouses_Controller` — решение спеки §17 «склады — забота
карьера, не фреймворка». Пункт карточки про `Warehouse::from_array()` (`class-warehouse.php:126-133`
в исходной формулировке) описывает файл, которого больше нет. Живая половина —
`Pickup_Point::from_array()`, опциональные поля `short_address`/`locality`/`postal_code`/`phone`/
`instruction`/`work_time`/`point_short_name` — подтверждена дословно, каст всё так же без
`is_scalar()` (`class-pickup-point.php:99-138`). Рекомендация: переписать карточку, оставив
только `Pickup_Point`-половину; ссылка на `Warehouse` вводит в заблуждение.

**Заморозка восьми карточек (148, 151, 152, 165, 173, 174, 181, 182) — условие не названо ни в
одной из них.** Бриф этой сессии называет причину заморозки внешне («до появления pickup-слоя
нового карьера — пилот СДЭК/Яндекс»), и по проверке #144 это условие ДЕЙСТВИТЕЛЬНО ещё не
наступило (ни одной production-реализации `Point_Source` в репозитории нет, только фикстуры). Но
ни тело, ни комментарии ни одной из этих восьми карточек саму эту причину не называют — это
ровно тот «unstated freeze condition», который правила аудита просят зафиксировать как находку.
Также замечание по счёту в брифе: он говорит «семь карточек», но перечисляет восемь номеров
(148, 151, 152, 165, 173, 174, 181, 182) — просто фиксирую расхождение, на вердикты не влияет.

**#170 не входит в вышеописанный батч заморозки** (бриф явно перечисляет только 8 других), хотя на
доске у неё тот же приоритет «Заморожено». У неё СВОЁ, задокументированное прямо в коде основание
остаться открытой: буквальный триггер карточки («4-й колбэк») сработал, но автор осознанно не стал
делать групповой рефакторинг — докблок `Pickup_Controller::__construct()` объясняет, что
`$location_context` отвечает на другой вопрос и группировка с тремя исходными колбэками не убрала
бы риск их взаимной перестановки. Решать оператору: считать ли эту записанную-в-коде причину
достаточной или обновить формулировку карточки.

**#652 — код заранее отвечает на 3 из 4 незамеренных сценариев, риг подтверждает четвёртое.**
Карточка сама помечена «не баг-репорт, список непроверенных сценариев» — итоговая проверка требует
живого нажатия «Оформить заказ», это вне read-only аудита. Но статический код уже даёт сильные
сигналы по трём пунктам:

- *Сценарий 3 (адрес обязателен при ПВЗ)* и *сценарий 4 (индекс)* — оба уже РЕШЕНЫ в коде, и явно
  задокументированы как fix для готчи `js-hidden-checkout-field-is-still-required-server-side`:
  `class-checkout-field-policy.php:558-559,574-580` (адрес) и `:501-503,570,578-579` (индекс) —
  `hide_for_pickup`/`remove` всегда сопровождаются `required => false` (никогда `unset()`), причём
  для ОБОИХ чекаутов (блочный — через `woocommerce_get_country_locale`, классический — через
  `woocommerce_checkout_fields`). То есть худший исход карточки («блокирует оформление») по коду
  не должен воспроизводиться — стоит сказать это оператору ДО траты времени рига именно на эти два
  пункта.
- *Сценарий 2 (dadata + related-list)* — подтверждён кодом как продуманное архитектурное решение,
  не баг: `interface-location-provider.php:411-413` прямо документирует, что DaData «cannot
  enumerate (query-driven API only)», а `class-location-provider-registry.php` (докблок у
  `offered_field_modes_for()`, ~1346-1375) фиксирует операторское решение от 24.08.2026: ось
  населённого пункта вообще никогда не предлагает `related-list`, ни для какого провайдера.
- *Сценарий 1 (популярные города без региона)* — единственный, где код отвечает НЕ так, как
  предполагает сама карточка. Докблок `Location_Service::get_popular_settlements_for_country()`
  прямо говорит: «MEASURED, not the plan's original guess» — таблица популярных НП скоупится по
  СТРАНЕ, а не по `region_key` (такого поля в текущей логике вообще нет, хотя оно, видимо, есть в
  сидированных на риге тестовых данных). Клиентский скоуп по региону делает
  `location-cascade.js:1269-1273,1433-1435` (`scopeKeyFor`) — и его же докблок отвечает на прямой
  вопрос карточки: «null (no region selected, or the region field is not yet a confirmed record)
  means "unscoped", every entry stays». То есть при отключённом поле «Регион» популярный список,
  по коду, не падает и не пустеет — он показывает ВСЕ записи страны без скоупа (Москва и СПб
  вперемешку), а не какую-то одну из них и не пустоту. Это стоит проверить на риге как ЕДИНСТВЕННЫЙ
  из четырёх пунктов, где статический код даёт содержательный, но не окончательный ответ.
