## BLOCKER

### BL-1 — the `<select>` branch removes the only thing that made a stale `entry.unresolved.settlement` harmless; a region or country change now leaves the address field permanently unlocked with no settlement

`woodev/shipping-method/assets/js/frontend/location-cascade.js:3282-3284`

```js
if ( 'SELECT' === el.tagName ) {
    return !! entry.unresolved.settlement;
}
```

The docblock added above it asserts, as fact:

> *"Nothing about a `<select>` lets the customer change its committed value WITHOUT one of those
> two events firing … so there is no divergent state this presence check could miss."*

That is an inference, and it is **false**. The marker's lifetime is not owned by those two
events. Exactly three places in the file ever null `entry.unresolved[ level ]`:

- `onSelectFor()` — `location-cascade.js:2731` (a real pick at that level);
- `handleFieldChanged()` — `location-cascade.js:3818`, and **only for the level whose own field
  fired `change`**, never for descendants;
- `carryChainStateToIncomingNodes()` — `:1079`, `:1121` (the Rule 7c section-switch carry-block).

Neither `clearDescendants()` (`:3543-3583`) nor `clearCountryScope()` (`:3675-3712`) touches
`entry.unresolved`. Both null `entry.records[ level ]` and blank the field, and **both are the
ordinary consequence of a parent edit**. Under the `<input>` rule the blanked field text stops
matching the marker on the spot — which is precisely the protection the pre-existing
`isAddressLocked()` docblock (`:3208-3217`) says the live-DOM comparison exists to provide. The
`<select>` branch throws that protection away and replaces it with the claim quoted above.

**Falsifiable failure scenario (measured, not argued).** Mode: `settlement: 'ajax-select2'`
(`related-list` behaves identically via `language.noResults`). Chain `region → settlement →
address`, RU.

1. Customer types `Тьмутаракань` in the settlement select2. The search completes with zero
   suggestions → `onAbandon` → `entry.unresolved.settlement = 'Тьмутаракань'`.
   Address unlocks. **Correct — this is the #350/#517 fix working.**
2. Customer realises the region was wrong and changes the region field.
   `handleFieldChanged()` → `clearDescendants()` blanks the settlement `<select>`
   (`el.value === ''`, asserted in the probe) and nulls `entry.records.settlement`.
   `entry.unresolved.settlement` **survives**.
3. `refreshAddressLocks()` runs. `scopeKeyFor( entry, 'address' ) === null`, so the amendment is
   consulted → `'SELECT' === el.tagName` → `!! 'Тьмутаракань'` → **`true`** → address **stays
   unlocked**.

Observable wrong outcome: the address field is editable, in a region the customer never
searched, with an empty settlement `<select>` and no settlement record. The customer types a
street, picks it, and the pickup choice is never persisted — the exact state #337's lock was
built to remove by construction.

The same happens on a **country** change (`clearCountryScope()`), which is strictly worse: the
marker names a town in the country the customer just left.

Because nothing else ever clears the marker, the unlock is **permanent for the page** unless the
customer eventually makes a real settlement pick.

**Reproduction (temporary probe, run and then reverted — tree is clean):**

```
CRITIC PROBE #517
  × PROBE A1 (<select>): a REGION change after an abandoned settlement search must re-lock
      expect( billing_city.value ).toBe( '' )        → passed  (field IS blank)
      expect( addressField().disabled ).toBe( true ) → FAILED: received false
  × PROBE A2 (<select>): a COUNTRY change after an abandoned settlement search must re-lock
      expect( addressField().disabled ).toBe( true ) → FAILED: received false
  √ PROBE A3 (<input> CONTROL): the same REGION change DOES re-lock the baseline typeahead
```

**A3 is the control that makes this a finding rather than an opinion:** the identical sequence
against the plain-`<input>` typeahead re-locks correctly. The divergence is introduced by this
PR's `<select>` branch and by nothing else.

**Severity.** BLOCKER. Reachable by a customer in three ordinary interactions; the observable
outcome is #337's original defect; there is no recovery short of a real settlement pick. It is a
NEW defect — on `main`, `onAbandon` never fired in these modes at all, so the marker was never
set and the lock behaved correctly (over-strictly, which is what #517 set out to fix).

**Note on direction.** The `<select>` rule is monotonically *weaker* than the `<input>` rule — it
can only ever unlock more, never lock more. So the failure mode is always "unlocked when it
should not be", never a customer newly stuck. That is what makes BL-1 the only place worth
looking, and it is also why the brief's `writeSilently` scenarios are not defects (see below).

**Suggested direction (not a fix — the operator decides).** Two shapes that would both close it,
in order of how little they disturb the existing contract:

1. Clear `entry.unresolved[ node.level ]` in `clearDescendants()` and `clearCountryScope()`
   alongside the `entry.records[ node.level ] = null` they already do. This is a statement the
   `<input>` path can also honestly make (a blanked field carries no proven-unresolved text
   either), it fixes the marker's real lifetime rather than the predicate that reads it, and it
   makes the added docblock's claim true instead of aspirational.
2. Or store the marker with the identity it was proven against (region/country scope key at
   abandon time) and let `settlementTextIsKnownUnresolved()` reject a marker whose scope no
   longer matches.

## What the brief asked about `writeSilently` — settled, and NOT a defect

I walked all five call sites (`:1113`, `:1702`, `:1706`, `:1764`, `:3634` at this head) against
the state "`entry.unresolved.settlement` set AND `entry.records.settlement === null`":

- **`:1113` (`carryChainStateToIncomingNodes`, Rule 7c).** Cannot fire for settlement in this
  state: `carried` is `record ? … : ''` and `record` is `entry.records.settlement`, which is
  `null` — so `carried === ''` and the `'' !== carried` guard blocks the write. **Ruled out.**
- **`:1702`/`:1706` (`backwardsFill`).** These CAN fire — an address pick writes settlement text
  silently while the marker stands. But the divergence goes the *harmless* way: the old
  `<input>` rule would re-lock the address the customer has just successfully filled; the new
  rule leaves it unlocked. That is better UX, not a defect. **Not a finding.**
- **`:1764` (`handlePickupAddressReplacing`).** Same shape, same direction. **Not a finding.**
- **`:3634` (`restoreClearedDescendants`).** Restores descendants of `level`, so it never targets
  settlement when `level === 'settlement'`. It *can* target settlement when `level === 'region'`,
  but that path sets `unresolved.region`, not `unresolved.settlement`, and it writes only when
  `entry.records.settlement` was non-null at clear time. **Ruled out for this state.**

**The `<select>` value-write trap the brief flagged is real but does not bite here.** Writing
`.value` on a `<select>` with no matching `<option>` yields `''` (gotcha
`a-select-value-write-with-no-matching-option-submits-nothing`) — but `writeSilently()` does not
write `.value`; it routes through `applyValueToElement()` (`:1449-1538`), which already handles
`<select>` with the three-try match/synthetic-option ladder that gotcha produced. Nothing in the
#517 diff assumes a bare `.value` write worked. **No finding.**

## MAJOR

### MJ-1 — `related-list` now fires `onAbandon` per keystroke, where the typeahead fires it once on blur; the `restoreClearedDescendants()` snapshot is consumed mid-typing

`woodev/shipping-method/assets/js/frontend/location-select-modes.js:454-467`

`language.noResults` is a **render-time** hook: select2 calls it every time a filtered result set
comes back empty, i.e. on the keystroke that first stops matching, and again on each keystroke
after it. `onAbandonFor()` (`location-cascade.js:2816-2830`) is not a passive recorder — it calls
`restoreClearedDescendants( entry, 'settlement' )`, which **consumes the snapshot**
(`entry.clearedByEdit[ level ] = null`, unconditionally, `:3615`).

The baseline typeahead deliberately fires this on **blur only** (`location-typeahead.js:938`,
`handleBlur`) — a customer who types straight through a non-matching prefix to a real match never
triggers a restore at all.

**Failure scenario.** Settlement = `related-list`; the customer had previously picked `Москва` and
filled `ул. Тверская, 1`. They now edit the settlement to change town:

1. The edit's `change` runs `clearDescendants()`, snapshotting `billing_address_1 = 'ул. Тверская, 1'`.
2. They type `Тве` — no local match yet → `noResults` fires → `onAbandon` → the address field is
   **restored to `ул. Тверская, 1`** and the snapshot is consumed.
3. They keep typing, find `Тверь`, pick it.
4. `onSelectFor()` sets `entry.clearedByEdit.settlement = null` — but the restore has already
   happened. The address field now shows a Moscow street under Тверь.

Under the typeahead the same sequence restores nothing, because the abandon never fires.

The same shape applies to `ajax-select2` (`:394`), where a debounced intermediate query with zero
results fires the abandon mid-typing too — and, via BL-1, that intermediate query alone is enough
to set the marker permanently.

**Severity.** MAJOR: customer-visible wrong address text, reachable in one ordinary edit, and it
multiplies BL-1's trigger surface from "the town is genuinely uncarried" to "any intermediate
keystroke had zero matches". Not a blocker on its own, because the customer can see and overwrite
the wrong address text.

### MJ-2 — `attachRelatedListSettlement` no longer normalises `options.list()` to a promise; a synchronous return now throws out of `attach()`

`woodev/shipping-method/assets/js/frontend/location-select-modes.js:936-941`

```js
fetchEntries: function() {
    return options.list();
},
```

The removed wrapper was `Promise.resolve( options.list() ).then( null, … )`. The `.then( null, … )`
half is genuinely dead weight for this renderer and removing it is correct — but `Promise.resolve()`
was doing a second job the docblock does not mention: **normalising a non-thenable return**.
`buildSelectField()` calls `strategy.fetchEntries( '' ).then( … )` directly (`:834`).

**Failure scenario (measured).** A caller whose `options.list()` returns an array synchronously —
which the file docblock's own renderer contract never forbids, and which any test double or
plugin-side `related-list` consumer would naturally write:

```
PROBE C1: attachRelatedListSettlement with a SYNCHRONOUS options.list() return
  → TypeError: strategy.fetchEntries(...).then is not a function
```

The throw escapes `attach()` and lands in `location-cascade.js`'s `attachOne()`, where the field
is left as a bare `<select>` already swapped in for the `<input>` but never populated and never
select2-enhanced.

This is **not reachable through the framework's own wiring** — `listFor()`
(`location-cascade.js:1353-1377`) always returns a `fetchJson().then(…)` promise. It is a contract
regression for third-party `options.list` implementations and for tests. Restoring
`Promise.resolve( options.list() )` (without the `.then( null, … )` swallow) keeps both the #517
behaviour and the old robustness at zero cost.

**Severity.** MAJOR as a contract regression, MINOR in practice for this repo's own callers. I
would take the one-token fix rather than argue the severity.

## MINOR

### MN-1 — D's "no worse than the typeahead" argument is not true; the sub-floor gap is NEW relative to the baseline widget

`woodev/shipping-method/assets/js/frontend/location-select-modes.js:379-384` (docblock)

> *"The floor this leaves unclosed (`minimumInputLengthFor('settlement') === 2`) is no worse than
> `location-typeahead.js`'s own `DEFAULT_MIN_CHARS`, so this is not a NEW gap relative to the
> baseline widget."*

The floor **values** match — `DEFAULT_MIN_CHARS = 2` (`location-typeahead.js:200`),
`minimumInputLengthFor('settlement') === 2` (`location-select-modes.js:258`). But the typeahead
has no gap at that floor, because it explicitly closed it: `handleBlur()` reports
`onAbandon( { query, resolved: false } )` for a below-`minChars` blur
(`location-typeahead.js:953-961`), added by the 17.08.2026 follow-up for exactly this reason.
So the select modes re-open a gap the baseline widget does not have. The comparison as written
compares the wrong two things.

The **technical** half of the scope cut is sound and I could not break it: select2's search box is
`$el.data('select2').dropdown.$search`, an undocumented private field, and neither `select2:close`
nor `select2:closing` carries the raw term. Declining to reach for it matches `activeAbort`'s own
stated policy. Keep the cut; fix the argument.

Practical reach is narrow: it needs a settlement whose full name is one character. Real for the
general contract, close to nil for RU. **Card, not a blocker** — but the docblock sentence should
not survive as written, because it will be read later as a settled equivalence.

### MN-2 — `entries && 0 === accepted.length` conflates "provider carries nothing" with "we rejected every row the provider returned"

`woodev/shipping-method/assets/js/frontend/location-select-modes.js:394`

`accepted` is `applyEntries()`'s output, which drops any entry with no `record`, no `key`, or an
explicitly-empty derived `entry.value` (`:640-646`). A response with rows that all fail that filter
produces `entries.length > 0, accepted.length === 0` — and is reported as
`onAbandon({ resolved: true })`, i.e. "a completed search proved the provider has nothing for this
exact town".

It did not. The provider had something; this layer could not derive a submittable field value for
it (`fieldValueFor()` returning `''` — described in the cascade's own docblock as "the lesser of
two evils", not an absence of data).

**Failure scenario.** The provider returns settlement rows whose `record` carries no usable
component or label at the settlement level for some locale/provider combination → every row is
filtered → address unlocks and (per BL-1) stays unlocked, on a search that actually found the town.

Argued the other way: from the customer's side there is nothing to click either way, which is the
same argument `onAbandonFor()`'s own docblock makes for collapsing `resolved: true`/`false`. That
argument is fair for the *lock* and unfair for the *marker's meaning*. I would gate the abandon on
`entries.length === 0`, not `accepted.length === 0`, and let a fully-filtered response fall through
to "no results shown, lock stands". **MINOR**, narrow reach.

### MN-3 — the `attachOne()` notice-placement docblock is now stale in a way that matters

`woodev/shipping-method/assets/js/frontend/location-cascade.js:2247-2258`

> *"neither wires an empty/no-results message of any kind, `related-list:settlement` being a plain
> pre-populated `<select>` and `ajax-select2` never reading `options.emptyText` at all"*

As of this PR, `related-list:settlement` **does** read `options.emptyText` and **does** wire a
no-results message (`location-select-modes.js:465`). That paragraph is the recorded justification
for the D7 cancel-notice being a DOM-anchor notice rather than a listbox row — a future reader
weighing that decision now reads a false premise. Not a behaviour defect; a doc-accuracy one, on a
docblock whose whole purpose is to carry a decision forward. Update it in this PR.

### MN-4 — `noResults` returning `''` renders an empty message row instead of select2's own default

`woodev/shipping-method/assets/js/frontend/location-select-modes.js:465` — `return seed.emptyText || '';`

`emptyText` is server-supplied and, for the settlement level, is `i18n.noResults`
(`location-cascade.js:3019`), so `''` only happens when the server sent no string at all. In that
case a real select2 renders an **empty** results row where its own built-in `noResults` would have
rendered `"No results found"`. Arguably the honest outcome for a layer that routes every
customer-facing string server-side (an untranslated English literal at a Russian checkout is
worse). Flagging it as a deliberate choice worth being explicit about, not as a defect.
**Opinion, not a finding.**

## Hypotheses B and C — attacked and NOT broken

### B — `listLoadFailed` captured by value: sound as written, I could not break it

`ensureSelect2()` has exactly three call sites (`location-select-modes.js:831`, `:836`, `:842`).
`:831` is the `strategy.ajax` branch, which never assigns `listLoadFailed`. `:836` and `:842` are
the success and failure callbacks of the one-time non-ajax load, and `:840` sets
`listLoadFailed = true` **before** `:842` calls `ensureSelect2()`. `select2Initialized` (`:777`,
set at `:801` only after `.select2()` returns) makes every later call a no-op. So the by-value copy
at `:797` is always the settled value.

I checked the three escapes the brief named:

- **`updated_checkout` re-attach / `detach()` then re-attach** — `reconcileAfterCheckoutUpdate()`
  tears down and calls `attachOne()` again, which calls `buildSelectField()` afresh. New closure,
  new `listLoadFailed = false`, new one-time fetch. No stale copy survives.
- **A second `applyEntries`** — `applyEntries` never calls `ensureSelect2()`.
- **A flag set after the seed is built** — impossible: the only assignment is at `:840`, six lines
  before the only `ensureSelect2()` that can observe it.

A getter would be equivalent here, not strictly more robust — but it *would* be cheaper to keep
true under future edits, since it removes the ordering constraint entirely. That is a taste call,
not a finding.

**One adjacent gap, pre-existing and NOT introduced by this PR:** if `detach()` runs while the
one-time list fetch is still pending, the `.then` still calls `ensureSelect2()` on a `<select>`
already removed from the document. That was true before #517 too. #517 adds only that the orphan
config now closes over `seed.onAbandon`; since the orphan widget is not in the document it never
renders and `noResults` never fires. Worth a card, not this PR's problem.

### C — the un-swallowed rejection: customer-visible outcome is identical; the path is real

The non-ajax error branch (`:838-843`) does exist and does what the docblock claims:
`logError( error )` → `listLoadFailed = true` → `applyEntries( [], true )` → `ensureSelect2()`.
Before the PR, the wrapper caught, called the *same* `logError()`, and returned `[]`, which took
the *success* branch to `applyEntries( [], true ); ensureSelect2()`. Same log, same empty
`<select>`, same select2 init. Nothing else observed the old swallow — the wrapper's `.then` was
its only consumer.

So C is clean **except** the promise-normalisation regression, which is MJ-2 above.

### Two test-hygiene notes

- `tests/js/location-cascade.test.js`, the test titled *"related-list:settlement control:
  language.noResults for a term that actually matches an option must never be observed as a

### Re-entrancy from a render-time hook: checked, safe

`language.noResults` runs inside select2's render. `onAbandon` → `onAbandonFor()` →

back into the settlement `<select>` or its options during its own render, and the address level is
always the baseline typeahead (`config.location.mode` has only `region`/`settlement` axes). No
re-entrant write during render. **No finding** — but this is exactly the property that would break
if a future card adds an `address` mode axis, and it is worth a line in the docblock.

one synchronous browser event dispatch, so no ajax response can land between `close` (which sets
`dropdownOpen = false`) and `select` (which clears the candidate). For a late zero-result response
to fire immediately *after* a completed pick, that response would have to belong to a request still
in flight at pick time — and select2's own abort contract kills the previous request when the next
query starts, with our transport returning `{ abort }` so it actually does. A customer cannot pick
from a list that a zero-result response is about to replace.

### MN-E — `handleSelect2Close()` schedules a 0 ms timer on every close even when the option is OFF

`woodev/shipping-method/assets/js/frontend/location-select-modes.js:1093-1098`

The gate is at the recording site, not the scheduling site, so with the option off every dropdown
close still arms a macrotask whose `fireAbandonNow()` finds `pendingAbandon === null` and returns.
Harmless — `detach()` cancels it (`:1220`), and it can never fire anything. Recorded only because
the brief asked for "no deferred flush scheduled, no timer left pending", and the precise answer is
*a timer is scheduled and no-ops*, not *no timer is scheduled*.
