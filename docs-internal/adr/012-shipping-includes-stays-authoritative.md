# ADR-012: `Shipping_Plugin::includes()` Stays Authoritative — Not Replaced By The Class-Map

**Status:** accepted

**Date:** 2026-09-05

## Context

Issue #138. Since the s27 runtime autoloader (`Woodev_Framework_Autoloader` +
`woodev/class-map.php`, generated by `bin/generate-class-map.php`), any framework class resolves
on demand — most of the framework carries no eager `require_once` list at all. But
`Shipping_Plugin::includes()` (`woodev/shipping-method/class-shipping-plugin.php`) kept a
hand-maintained `require_once` list, and it had drifted badly: measured before this decision, the
list covered 39 of the 71 real class/interface files under `woodev/shipping-method/**` — a
**31-file gap**, not the "six classes" the card's own description estimated. Four prior file
deletions on `feat/pickup-map` each left a dangling `require_once` on a file that no longer
existed — a fatal on a real vendored boot, invisible to the unit suite (see gotchas
`dispatcher-files-unwired-in-includes`, `box-packer-interface-unwired-in-includes`). The tree was
inconsistent with itself and no rule said which side — `includes()` or the class-map — was
supposed to win.

The card posed two options: (A) delete `includes()` and let the class-map be the only wiring, once
proven that load order never matters; or (B) keep `includes()` authoritative, backfill it
completely, and add a test that guards the direction the existing `ClassMapCompletenessTest` does
not — a class-map entry with no matching `require_once`.

## What was measured

- **`woodev/shipping-method/**` file count vs. `includes()` coverage**: 74 PHP files total; 2 are
  `admin/views/*.php` HTML templates (`include`d at render time from
  `class-shipping-admin-order.php` / `class-shipping-plugin.php`, correctly outside `includes()`'s
  scope — they declare no class and have no class-map entry); 1 is `class-shipping-plugin.php`
  itself. Of the remaining 71 class/interface files, only 39 were required. **31 were map-only**,
  spanning `api/`, `checkout/` (incl. `presets/`), `location/` (the whole "popular settlements"
  family), `map/` (both concrete providers), `pickup/` (the entire SP-5 selection engine —
  `Pickup_Handler`, `Point_Query`, `Constraint_Checker`, `Selection_Result`, `Pickup_Selection`,
  `Address_Target`, `Provider_Selection_Scope`, both pickup interfaces), `rest-api/` (all four REST
  controllers), and `settings/` (the tools-tab framework: `Shipping_Tool`, `Tool_Result`,
  `Shipping_Tools_Registry`).
- **Class-map staleness**: `php bin/generate-class-map.php` regenerated against the current tree
  and produced a byte-identical `woodev/class-map.php` (`git diff --stat` empty). The map itself was
  not the problem — it was already complete and current.
- **Interface/trait coverage**: the generator's token extraction treats `T_CLASS`, `T_INTERFACE`
  and `T_TRAIT` identically (`bin/generate-class-map.php`); confirmed against the six interfaces
  actually declared under `woodev/shipping-method/**` (`Shipping_API`, `Location_Adapter`,
  `Location_Provider`, `Map_Provider`, `Point_Source`, `Selection_Scope`) — all six are present in
  the map with correct paths. No trait currently exists in the shipping tree, but the generator's
  mechanism does not special-case classes over interfaces/traits, so this is not a gap specific to
  option A.
- **File-scope side effects**: searched `woodev/shipping-method/**` for top-level
  `add_action`/`add_filter`/`define`/`do_action`/`apply_filters` calls and for
  `class_exists( ..., false )` no-autoload guards outside a class body — zero matches. No file in
  the tree does anything at parse time that depends on being eagerly `require`d rather than
  autoloaded on first touch.
- **Autoloader registration order**: `Framework_Resolver::load_plugins()` (fired on `plugins_loaded`)
  registers `Woodev_Framework_Autoloader` against the winning framework copy as the **very first**
  action of its very first loop iteration — before `invoke_plugin()` is called for *any* registered
  plugin, including the winner itself. Every path that can end up constructing a `Shipping_Plugin`
  subclass (the `callback`-style fixtures' `require_once` chain, and the `main_class`-style
  `class_exists()` + `new $main_class()` / `::instance()` path) runs through `invoke_plugin()`,
  which always runs after that registration. The one documented pre-autoloader window in this
  codebase (gotcha `a-loader-definition-cannot-use-a-framework-class-constant`) is earlier still —
  inside the loader-definition array literal built before `Woodev_Loader::register()` even requires
  `bootstrap.php` — and does not overlap `Shipping_Plugin::includes()`, which only runs once a
  concrete plugin's main class is actually constructed.
- **Which suite catches which failure — measured by the coordinator on `2fadd19`, not inferred.**
  The two directions are caught by different gates, and the asymmetry is the whole justification
  for the pair of tests. Injecting `require_once $path . '/does-not-exist-probe.php';` into
  `includes()`, then separately deleting one real `require_once` while leaving its file on disk:

  | failure | unit, without the new tests | unit, with them | integration |
  |---|---|---|---|
  | dangling `require_once` (file deleted) | **caught** — `Tests: 3523, Errors: 3` via `tests/unit/YandexPilotFixtureTest.php:76` -> `class-framework-resolver.php:170` | caught | **caught** — bootstrap dies: `Failed opening required '.../does-not-exist-probe.php'` |
  | class-map entry never required | not caught | **caught** — the only gate that does | **not caught**: `OK (143 tests, 530 assertions)` |

  Two consequences worth stating, because the obvious reading of each is wrong.
  **A dangling `require_once` was never invisible** — `YandexPilotFixtureTest` drives the real
  `Framework_Resolver`, so the unit suite does reach the runtime resolution path for the fixture
  plugins, and both suites already fatal on a missing file. `test_every_required_shipping_file_exists()`
  therefore buys a readable failure message rather than new coverage, which is a real but modest
  benefit; it is kept on that basis and not because the failure would otherwise escape.
  **The reverse guard, by contrast, is genuinely alone.** Integration stays fully green with a
  class missing from `includes()`, because the runtime autoloader resolves it from
  `class-map.php` regardless — so the eager list can rot to a 31-file gap without any suite
  objecting. That is exactly how it did rot, and
  `test_every_shipping_classmap_entry_is_wired_into_includes()` is the only thing now standing
  against it.

## Decision

**Keep `Shipping_Plugin::includes()` authoritative.** All 31 map-only files are now required from
it (grouped to match the file's existing per-feature comment style). Two new tests in
`ClassMapCompletenessTest` guard both directions, because they catch two *different* incidents and
neither substitutes for the other:

- `test_every_shipping_classmap_entry_is_wired_into_includes()` — a class-map entry under
  `woodev/shipping-method/**` (excluding `class-shipping-plugin.php` itself) with no matching
  `require_once`. This is a class ADDED to the tree and forgotten in `includes()`.
- `test_every_required_shipping_file_exists()` -- a `require_once` in `includes()` whose target no
  longer exists on disk. This is a file DELETED from the tree with a stale `require_once` left
  behind -- the incident the card describes as having fired four times. Note precisely what this
  test does and does not add: per the measurement above, that failure was ALREADY fatal in both
  suites, so this guard replaces a bootstrap-level fatal buried in a 143-test run with a named
  assertion and a one-line message. It is kept for the diagnostic, not because the failure would
  otherwise escape. Round 2 of this card's review established both halves of that.

Either gap now fails a **unit** test immediately, by name. For the deleted-file direction that is
a better message for a failure the suites already produced; for the map-only direction it is the
only signal that exists at all.

This decision is scoped to the shipping module. It does not reopen s27's choice to leave the rest
of the framework autoload-only — that code has no file-scope side effects tying it to eager
loading either, and reversing it is out of scope for #138.

## Why option A was not chosen

Not because a load-order hazard was found — none was, after the checks above. It was rejected
because the one measurement that would actually **prove** load order never matters for a real
vendored boot could not be run from the worktree (no `wp-env`) at the time the decision was
taken, and the static checks above, while
consistent with safety, cover only the failure modes this project has already hit
(file-scope side effects, `class_exists(..., false)` guards, pre-autoloader windows) — not
every possible one. Given that the measured gap was 31 files, not the 6 the card described, and
given that this exact class of mistake (a dangling reference invisible to the unit suite) has
already caused four real incidents on `feat/pickup-map`, the responsible call is to not delete a
safety net on a hazard nobody has actually excluded, and let the reverse-guard test carry the
weight `includes()` used to carry alone. If a future session runs the integration suite against
this branch and it proves the class-map alone is sufficient, that is new evidence and a new ADR —
this one is not a permanent bar to reopening the question, it is what the evidence supported
*here*.

## Alternatives Considered

- **Option A — delete `includes()` entirely.** Rejected: unproven under the one suite (integration,
  against real WordPress) that can actually verify a runtime vendored boot with no Composer
  classmap covering the gap; see "Why option A was not chosen" above.
- **Backfill `includes()` but skip the reverse-guard test.** Rejected: this is exactly what already
  happened once (the module presumably started fully wired) and drifted to a 31-file gap with
  nobody noticing across many sessions. A one-time backfill without an enforcement mechanism would
  recreate the same problem the next time a class is added.

## Consequences

- Adding a new class under `woodev/shipping-method/**`, or deleting a required one, now fails one
  of the two new unit tests immediately — this is the intended friction; it replaces a silent
  runtime fatal with a fast, local, always-run signal, in both directions.
- `includes()` is longer (71 requires, up from 39) and will keep growing with the module. That cost
  was accepted explicitly in exchange for the two guards.
- **Integration has since been run and is green** (— coordinator, 05.09.2026, commit `2fadd19`):
  `OK (143 tests, 530 assertions)`, identical to the `main` baseline, with the shipping fixtures
  loaded. phpcs clean, phpstan level 3 clean, unit 3524 / 8647 / 1 skipped. So this ADR is
  integration-verified, not only measurement-based. What integration does NOT do is validate the
  eager list itself — see the matrix above: it stays green with a class missing from
  `includes()`, which is why the reverse-guard test exists.
