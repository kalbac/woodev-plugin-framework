## #469 — the payload was right and the screen was wrong

`Checkout_Handler::inject()` overrides `type`, which moves the field out of WooCommerce's `state`
render branch — the only branch that emits `data-input-classes`. `country-select.js:103` then reads
`undefined` and concatenates it into a class list at line 120, which is the rig's
`class="state_select undefined"` fingerprint.

The card's proposed fix looked landed: a `wp eval-file` probe showed
`custom_attributes => [ 'data-input-classes' => '' ]` sitting in the checkout-fields array. The HTML
fetched over HTTP in the same minute carried no such attribute. The cause:

```php
// wc-template-functions.php:3367 (WooCommerce 11.0.1)
$args['custom_attributes'] = array_filter( (array) $args['custom_attributes'], 'strlen' );
```

An empty-string attribute is dropped outright. WooCommerce's own `state` branch emits
`data-input-classes=""` only because it writes the attribute *literally*, outside `custom_attributes`
— which is why IT can and we cannot. And WC core sets no `input_class` on any address field, so the
empty case is the **only** one a stock install hits.

Fixed with a single space, chosen by measurement rather than reasoning: with `data-input-classes=" "`
WooCommerce's own rebuild produced `class="state_select"`, byte-identical to the `""` control.

The client half **reverses a deliberate #466 decision** ("carried verbatim, never fabricated"):
leaving the attribute unset is precisely what makes WooCommerce read `undefined`.

**Codex found one real LOW here that I had not:** we overwrote a theme-declared
`data-input-classes`. WooCommerce's `state` select branch interpolates `custom_attributes` *before*
its literal attribute, and an HTML parser keeps the first of two identical attributes — so on
WooCommerce's own render a theme's value already wins. We were inverting that. One-line fix, two
tests.

Rig-verified in the browser: `document.querySelectorAll('.undefined').length` went 2 → 0, with the
«Ship to a different address» box both checked and unchecked so each column was measured.

## #449 — cancellation, and the leak nobody had looked for

Two of the card's three gaps were already on `main`. The third — real cancellation — was left with an
inline note saying it was out of scope. The worker threaded a real `AbortController` through
`options.fetch( query, { signal } )`.

Rig proof, typing `Новосибирск` one character at a time: **10 requests, all carrying a signal, 9
superseded ones genuinely aborted** (`rejected:AbortError`), only the last *requested* term
surviving — which is the card's own stated requirement.

Codex's MEDIUM was the better find: `detach()` never called the transport's `abort()`, and
selectWoo's AJAX adapter has no `destroy()` override that aborts `_request` either. This layer tears
widgets down on **every** `updated_checkout`, so a request in flight at teardown ran to completion —
the same paid call on a far more common trigger.

The residual (teardown inside the 250 ms debounce window) was deliberately left, and I **measured
that the documentation matches reality**: exactly one request still fires, un-aborted, as documented.

## #488 slice 1 — three rounds, five critic passes, and one fix I had to take back

`CAPABILITY_RESOLVE_KEY` + `resolve_key( string $key ): ?Location_Record`. The whole slice turns on
one thing: spec D6 **deletes the stored row** when the answer is `null`, so `null` must mean exactly
one thing.

- **Round 1** (worker): the capability, both providers, tests. Its own good instinct — throw rather
  than return `null` on transport failure — was the right discipline.
- **Round 2** (Codex, two HIGH): the implementation *leaked other outcomes into `null`*. A malformed
  row read as "gone". And DaData mints a **derived** key when a record has no `fias_id`; that key can
  never match a FIAS lookup, so every such record was one verification away from deletion. Codex also
  caught a CDEK transport stub that ignored the URL and query args — a test that would pass against
  the wrong endpoint.
- **Round 3** (my finding): round 2 detected a derived key with `/^[0-9a-f]{20}$/`. A heuristic about
  identity — the same class of mistake as `isWcManagedField()`'s `/(^|_)state$/`. Replaced with a
  marker stamped where derived keys are minted. The persisted-format change is licensed by an
  operator decision already on record (`specs/2026-08-21-settlement-search-design.md` decision 1: no
  migration, no live consumers).
- **Final pass** (Codex, one HIGH + one MEDIUM): `find_by_id_address()` returned
  `$suggestions[0] ?? null`, so `{"suggestions":[null]}` collapsed into "gone". Real; fixed.

### The fix I reverted an hour after writing it

For the MEDIUM (the marker is a bare prefix, and native ids may legitimately contain colons —
`relation:59195`, `way:1247091839` are measured DaData values) I made `compose()` refuse the reserved
prefix. The re-check rejected it, correctly: **DaData's mapper composes every record it maps**, so
refusing makes such a native id *unrepresentable* — a real locality degrades into an unmappable
record. I had traded a misclassification for data loss on ingest.

Reverted. The proper fix is an escaping scheme that preserves every native id, which changes what
`parse()` returns and needs its own review. Filed as **#494**, and the gap is documented at the
constant rather than left silent.

**Merged with that MEDIUM open, deliberately.** No measured native id of either provider can begin
with `derived:`, the branch strictly improves on the shape guess it replaces, and the rejection is
recorded as a PR comment rather than hidden. This is the "reject with evidence" the overnight rule
allows — not self-certification.

### #490 — three independent causes, and the third only showed up as a 1-in-5

My own overnight write-up of #490 was **too coarse and I corrected it**: the carry mechanism existed
and was *partly* working. Measured properly: the region never carried in either direction
(deterministic), the settlement carried in some runs and not others.

Three causes, each found only by executing:

1. **`adoptChain()` narrows the record.** After every successful `/select` it reduces
   `entry.records[level]` to `{ key, confirmed: true }`, so `fieldValueFor()` had no `name`/`label`
   to read and returned `''`. The region is always picked first, hence always narrowed before a
   toggle — hence deterministic.
2. **A post-detach DOM read finds a stale element.** `buildSelectField()` swaps `<input>`→`<select>`
   on attach and `detach()` restores the ORIGINAL input verbatim, so reading the outgoing value
   after detach always found an empty input for the settlement.
3. **The `/select` queue is per-ENTRY, not per-level.** Picking the settlement behind an in-flight
   region pick queues it; the region's response then narrows *every* level, including one it could
   not have named. This was the residual that survived fixes 1 and 2.

**The signal I should have read sooner:** fixes 1 and 2 each moved the failure rate without closing
it — 0/2, then 4/5. *A partial improvement in a flaky measurement means more than one cause.* Now a
gotcha.

Codex's contribution was the sharp one: it found no static poisoning path by reading, but noticed
**neither test reproduced the real direction-B sequence** (initially checked → preliminary uncheck →
fill billing → check), which is exactly where the residual lived. That framing is what turned round 3
from another blind attempt into a deterministic repro.

### #488 slice 2 — four critic passes, and the last finding was our own scar

The table, the store, the enrolment path. Every round found something real:

- `null` must mean exactly one thing, because D6 deletes the row on it;
- **the feature was inert twice.** Nothing in this repo constructs `Shipping_Admin_Order` — a carrier
  plugin does — so injection could never reach it. Fixed by DEFAULTING a null store rather than
  reading it as "enrolment off";
- **provider identity was not preserved**, so a merchant switching providers between checkout and
  export made `enroll()` throw *after the carrier order already existed*;
- **the last HIGH was a re-hit of our own gotcha.** The checkout listener gated on the ACTIVE
  provider's capability while a settlement record can belong to the FALLBACK provider
  (`a-level-served-can-come-from-the-fallback-not-the-active-provider`). Wrong in both directions.
  I fixed it myself — the card was at its round cap — and Codex approved the fix.
- **Three tests would have passed against a broken implementation**: a fake that ignored the SQL, a
  test that never drove `export()`, and an upsert fake that hard-coded the semantics it verified.
