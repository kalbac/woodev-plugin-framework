## Что сделано

### #745 — CLOSED (PR #748). Устаревший код ПВЗ больше не уезжает в заказ

Серверная половина, как требует готча
`the-checkout-required-rule-has-two-halves-and-fixing-one-leaves-the-other`: значение ПВЗ-поля, чей
метод не выбран, выбрасывается до `persist_field()` и до всех трёх хук-нагрузок. Предикат
**переиспользован**, а не заведён второй — тот же ленивый список `$requires_pickup_methods ??
Checkout_Config::pickup_method_ids()` и тот же `chosen_method_matches()`, что у бэкстопа в
`validate()`. `validate()` видит несокращённые значения, поэтому его вердикт не меняется.

Известный предел задокументирован и осознанно НЕ чинится: фолбэк `pickup_method_ids()`
общефлотовый, поэтому сценарий двух перевозчиков полностью покрыт только для плагинов, объявивших
свои id. Вывести методы хендлера невозможно — измерено в s113.

### #746 — CLOSED (PR #750). Молчаливый откат адресации ПВЗ на имя стал громким

`_doing_it_wrong()` под `WP_DEBUG`, когда `Pickup_Handler` построен без `$plugin`, **а слой
локаций активен** — гейт на активности слоя, а не на одном `null`: в магазине без провайдера
деградировать не с чего. Флаг «уже сообщил» ключуется по id плагина.

Вторая фикстура получила `$this`, поэтому риг гоняет основной, ключевой путь. Докблок фикстуры,
выдававший свойство одной фикстуры за гарантию фреймворка, переписан.

### #749 — CLOSED (PR #753). Последний голый процессный флаг в этом файле

Найден воркером #746 сверх задания и **проверен по коду** перед заведением карточки.
`reconcile_pickup_scope()` — сверка пометодная, а флаг был один на процесс: первый же вызов
выключал сверку для всех остальных методов и плагинов. Хуже: флаг взводился ДО
`if ( ! $scope_says_pickup )`, то есть единственный выстрел тратился на случай, где сверять нечего.
Ключевание по `$method_id`, взведение после проверки по существу.

### #744 — CLOSED замером. Дефекта нет, и ответ дал КОД, а не риг

`Pickup_Controller::get_points_data()` возвращает пустой список **до обращения к источнику**, когда
`Point_Query::from_request()` даёт `null` (нет ни `locality`, ни валидного `bbox`) или стратегия не
совпала. `attach_location_context()` выполняется ПОСЛЕ этого гейта — значит **сохранённая запись
покупателя не может спасти неадресованный запрос**. Пустой ответ s112 означает, что запрос ушёл без
локации; диагноз s113 подтверждён.

Замер с контролем через `rest_do_request()`, без единой мутации рига: при наличии `locality`
пустого ответа не бывает ни у одного перевозчика.

### #104 — сделано, PR #751 ОТКРЫТ. Ждёт формулировок

Карточка называла не то место. Зеркальный случай (наша v2-копия выиграла rendezvous) построен —
тумбстон B-1. Не был построен обратный: когда выигрывает ЛЕГАСИ v1-копия,

общая формулировка без пути и без догадки. Заодно из текста тумбстона убрано слово «фреймворка» —
нарушение правила «никакого жаргона мерчанту».

- **Ревью координатора нашло в двух ветках из четырёх `@since 2.0.3`** при потолке проекта `2.0.2`.

  «проверять адресацию через второго перевозчика» стал неверным сразу после мержа #746: у
  подключённого перевозчика **запись покупателя старше параметра `locality`**, и его ЗНАЧЕНИЕ
  инертно. Значение имеет только НАЛИЧИЕ параметра. Перемерено и исправлено в тот же вечер.
- **#106 закрыта, а не начата** — сверка по коду дешевле реализации.
