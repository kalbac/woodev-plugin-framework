## Два фикса, найденных риг-проверкой, не входившие в план

1. **Полоса приоритетов пресета сдвинута с `10–60` на `40–90`.** Замер на риге: исходные числа
   спеки сталкивались с блоком имени WC (`first_name 10`, `last_name 20`, `company 30`) и рисовали
   «Имя · Страна · Фамилия · Регион · Город …» — имя покупателя разрезано пополам. Контроль с
   выключенным пресетом дал нормальный порядок WC. Сдвинул в адресную полосу самого WC, сохранив
   требуемый относительный порядок (Страна > Регион > Город > Адрес > Кв. > Индекс).
2. **Общий баг настроек: клиентская валидация блокировала Save любой секции вкладки «Доставка»**,
   если у активного провайдера локации есть обязательное+секретное поле (обычный случай — у CDEK
   и DaData оба). `Field_Schema` маскирует секрет в `''` независимо от того, настроен ли он на
   сервере; клиентская проверка `required` этого не знала и блокировала запрос ДО того, как он
   вообще строился — хотя путь отправки и так корректно пропускает нетронутые поля. Нашёл вживую,
   пытаясь сохранить настройку карты через реальный REST. Фикс — `validateField()` получил
   `isTouched`; не общий для #362, явно помечено как выходящее за рамки задач 8/9.

## Механика мержа — три PR превратились в шесть

`ci.yml` триггерится только на `pull_request` в `main` (`branches: [main]`), поэтому у стековых PR
(#365 на #363, #366 на #365) полная матрица физически не запускалась — только `Label PR`/
`Markdown Lint`. Хуже: когда #363 смержился с `--delete-branch`, GitHub **закрыл** #365 (не
перетаргетил на `main` — так GitHub обращается с PR, чья база удалена), а закрытый PR нельзя ни
переоткрыть, ни перенацелить. Тот же цикл повторился для #366 после мержа #367. Оба раза
пересоздавал PR с той же веткой прямо на `main` (#365→#367, #366→#368) — сама ветка при этом жива,
теряется только PR-обёртка. При пересоздании три-точечный `git diff main...branch` показывал уже
смерженный контент как новый (разрыв истории squash-мержа) — доверял только `git diff main..branch`
(две точки, прямое сравнение деревьев). Реальные `git merge main` при пересоздании (нужен был перед
пушем каждый раз) давали `add/add`-конфликты на файлах, которые Task 4 создавал заглушкой, а
последующие задачи наполняли — все проверил построчно, все оказались чистым надмножеством, брал
сторону ветки. Один раз забыл закоммитить пересборку JS-бандлов ПОСЛЕ коммита мержа — словил
несоответствие в уже запушенном PR, поймал по `git status`, исправил вторым коммитом до того, как
CI успел провалиться. Всё задокументировано как готча `stacked-pr-github-mechanics` (+ дополнение к
`git-squash-onto-stale-origin-main-diverge`), чтобы не наступать снова.
