## #358 — the provider seam now reports what it did with a parent

The analysis found three things the card did not have:

1. **The defect is one value, not the field.** Of `within_status`'s six values, five are honest
   refusals. Exactly one, `applied`, covers two opposite provider outcomes. The rest of the
   vocabulary is fine and was left alone.
2. **The CDEK fixture contradicts itself** on one state: from the same `region_code_from_scope()
   === null`, `list_localities()` answers `[]` (`:283`) while `suggest_settlements()` answers
   country-wide (`:527`). Both defensible alone; from outside they are two different silences about
   the same fact.
3. **The verdict is not knowable before the request.** DaData branches deterministically, but the
   CDEK components path goes through `region_code_for_name()`, which walks the upstream dictionary.
   That killed the cheapest-looking design — "let the provider declare up front whether it can
   narrow" — before a line was written.

Shipped: a THIRD independent field `scope_narrowing` (`exact` / `degraded` / `none` / `unreported` /
`not_applicable`), `within_status` and `within_applied` untouched. The precedent is the project's
own: `perform_suggest()`'s docblock already says those two are read independently "so a future
change to one can never silently desync the other" — a third stage wants a third field, not a new
value bolted onto an existing one. `unreported` exists because `Location_Provider` is a public
extension point: a provider that never spoke must not have a claim made on its behalf.

Mechanism: `Location_Scope::for_provider()` returns a clone with a fresh write-once verdict slot,
stamped per provider CALL (a D15 fallback chain hands one scope to more than one provider).
`report_narrowing()` never throws — the controller turns any `\Throwable` from a provider into a
502 "источник подсказок недоступен", so a bookkeeping mistake would reach the customer as an
upstream outage that never happened.

**Critic (Codex, `gpt-5.6-terra`), canary 3/3.** Its must-fix — that `/list` has a success return
without the new field — was REJECTED with evidence: `handle_list_request()` has exactly one 200
return and it carries the field; every other exit is a `WP_Error`. The critic had flagged its own
uncertainty ("the supplied diff cannot expose its exact unchanged array line"). Its test finding was
real and accepted: the `exact` verdict was asserted without asserting the filter actually applied,
so neutering the guard at `suggest_settlements():527` would have left the verdict correct and the
narrowing gone with no test going red.

## #356 — closed in three parts

### Part 1 (PR #665) — the forget primitive and WP privacy

Measured, not assumed: `wp_privacy_personal_data_erasers`/`_exporters` were registered NOWHERE in
the framework and `delete_user_meta` appeared nowhere in the location layer. A WP erasure request
did not touch `woodev_customer_location`, and an export did not show it.

`forget( ?int $user_id = null )`: `null` → the current visitor, both sinks; an explicit id → **meta
only**, because the eraser runs in wp-admin and `$this->session()` there belongs to the ADMIN, not
to the erased shopper.

Two real critic findings. **`delete_meta_chain()` discarded `delete_user_meta()`'s result and
returned an unconditional `true`** — so the session was cleared, `ACTION_FORGOTTEN` fired, the
eraser answered `items_removed: true`, and the row survived on disk to re-seed the session on the
next read: a location resurrecting *after* we reported it deleted under a privacy request. And the
verbatim `raw` payload went into the export with no boundary — kept (a personal-data export must be
complete) but behind `FILTER_EXPORT_RAW`, with the provider author's obligation written into the
docblock.

### Part 2 (PR #666) — the shopper's clear now reaches the server

**The control was the whole measurement.** A first browser pass "showed the record coming back" —
but that was the shop's `fixed` default policy (`implicit: true`, Москва), not memory of the
shopper. Re-measuring with an explicitly persisted Санкт-Петербург (`implicit: false`) proved the
real thing:

```
persist test-cdek:137 explicitly  -> implicit:false
country := KZ                     -> client blanks state and city
country := ''                     -> client blanks everything
reload                            -> boot: current=test-cdek:137, implicit=FALSE
                                     fields: country=Russia, state=EMPTY, city=EMPTY
```

Diagnosis, sharper than the card's: `clearCountryScope()` clears WooCommerce's own address fields
and WooCommerce persists that clearing; woodev's chain does not follow. Two server-side stores
disagreeing — rates and pickup points ran on Санкт-Петербург while the shopper saw an empty field
and could not correct it.

Shipped `POST woodev/v1/location/forget` (same nonce barrier as `/select`) and one POST per
country-change gesture. Verified on the rig: after the gesture `current = test-cdek:44,
implicit = true` — only the shop default remains, and the fields agree.

**The critic's must-fix here was refused by the WORKER, with a citation, and the worker was
right.** It claimed a programmatic country change to a different value now erases memory without a
shopper gesture. Gotcha `a-programmatic-parent-change-must-not-run-a-destructive-cascade` records
that this file's boundary has always been the real transition of a remembered value, never the
actor — and the country field is WooCommerce's own select2, so `writeSilently()`'s namespaced-
trigger mechanism does not reach it. The deciding argument was the one neither had stated: **on that
same path WooCommerce has already erased its own memory** via `update_checkout`, so refusing to
follow leaves woodev the sole disagreeing store — the very defect the card exists to close. Recorded
in the `sendForget()` docblock and as a dated paragraph in the existing gotcha.

Also measured, because the catastrophic variant had to be excluded: an explicit record **survives a
plain page load** on the fix. No boot-time erasure — at boot the country settles to the same value
and the `entry.resolved` guard catches it.

### Part 3 (PR #667) — retention by `saved_at`

`saved_at` was written, carried forward through three call sites, and never compared to anything.

The rule that governed the work: **the framework must not silently delete a shopper's data on a
schedule the merchant never chose.** So the default is DERIVED — the worker read WooCommerce's own
`class-wc-privacy.php` and anchored on `woocommerce_delete_inactive_accounts`, replicating
`WC_Privacy::delete_inactive_accounts()`'s own `empty( $option['number'] )` guard — and nothing
expires when the merchant configured nothing.

**Three critic must-fixes, all in that single dangerous class**, all confirmed against the code
before being passed on:

- `(int) $filtered` turned `false` / `''` / `'bogus'` / `[]` from a site's filter into `0` — a TTL
  of zero, erasing anything older than a second. Now only `null` or a positive int is accepted;
  everything else is `_doing_it_wrong()` and read as "no TTL". The refusal always falls toward
  keeping data.
- `strtotime()`'s `false` was not checked, and `time() - false` silently equals `time()`.
- `wc_parse_relative_date_option()` was called unconditionally and **fatals when WooCommerce is
  absent** — breaking a documented property (`set()`'s docblock: the meta sink needs WordPress, not
  WooCommerce). Worse, six stubs the worker had added to unrelated test files were HIDING exactly
  that dependency. The proof is now a `@runInSeparateProcess` test that does not stub the function
  at all.

The worker disputed part of the second finding with its own measurement and was right: `time() -
false` yields a TTL of ~56.7 years and the comparison is `age > ttl`, so no real `saved_at` could
trip it. The guard is correct anyway; the test reaches `retention_ttl_seconds()` by reflection,
because through visible behaviour the difference is invisible.

Live confirmation on the rig, which is worth more than the unit test: the rig's
`woocommerce_delete_inactive_accounts` is `['number' => '', 'unit' => 'months']` — the
not-configured shape — and an explicit record survived a reload untouched.
