## #410 — the two questions the card left to measurement

The card explicitly deferred two decisions to "замер, не оператору". Both were measured, not argued.

**Live computation, no stored flag.** On the rig, `get_default_locality_policy()` +
`get_default_locality_record()` + `get_active_provider()` together cost **0.0083 ms and ZERO
database queries** (all three land on WP's autoloaded-options cache); cold call 0.17 ms; a bare
`get_option('blogname')` is 0.00106 ms, so the whole check is ~8 of those. A stored flag would also
need `update_option_*`/deactivation hooks that structurally cannot catch a direct-SQL migration —
and #406 already deleted exactly such a dead flag pair.

**Non-dismissible.** Under live computation the notice self-clears the moment the cause goes away;
this was *demonstrated* on the rig (restore the provider → the notice disappears), not asserted. A
dismiss flag in user meta would only let a merchant permanently hide a condition that is still true.

**Scope:** provider MISMATCH only. The "policy is fixed but nothing was ever picked" case stays on
the «Локация» section's own description note.

## The thing the green suite could not see

PR #661 arrived with 14 new tests, all falsified, `composer check` green, and the notice **invisible
on every page**. The rig pass is what caught it.

A delayed notice renders into the footer with a literal `style="display:none;"` and is relocated and
unhidden by one line of inline jQuery. That line targets
`.js-wc-{slug}-admin-notice-placeholder` — and the slug came from a *different plugin* than the one
that echoed the placeholder, because two independent statics guard them:
`$admin_notice_placeholder_rendered` is claimed by the first handler to run on `admin_notices`
(notices or not), `$admin_notice_js_rendered` by the first handler that actually HAS notices. In a
fleet those differ, `insertAfter()` matches nothing, the chained `.show()` applies to nothing.

Measured on the rig: JS pointed at `woodev-test-shipping-method`, the DOM only ever held the
`woodev-test-plugin` placeholder, and **both** notices had `offsetHeight: 0` — including the
long-shipped `debug-in-production` one. Confirmed by control: re-running the identical line against
the placeholder that exists took both to `display: block`, 60px and 41px.

So it is not a regression from #410 — **delayed framework notices have not been visible in a
multi-plugin fleet at all**, and a fleet is this framework's normal case. On a single-plugin site
both statics resolve to the same plugin, which is why it survived. Filed as #662, fixed in #663.

I judged this in scope rather than "not my card": #410's whole purpose is that the merchant sees
something, so shipping it alone would have delivered nothing. It went into its own PR because the
defect predates #410 and deserves its own history.

## Critic round — Codex, two must-fix, both accepted after I verified them

Canary passed on all three facts (`location-default-locality-stale`, `@since 3.0.0`, `5b2db1b`).

1. **`null === $active` treated as a mismatch.** With no provider resolving at all, the notice tells
   the merchant to "выберите её заново" when there is nothing to pick with — and being
   non-dismissible it becomes a permanent, unactionable banner. My parity-with-the-settings-note
   argument was weaker than I thought: sharing the *predicate* is right, but a passive settings note
   and a section-wide banner do not carry the same cost. Fixed so the shared predicate keeps its
   arm (settings note unchanged) while the NOTICE additionally requires a real active provider.
2. **`sanitize_key()` on `$_GET['page']`.** Verified by measurement, and it breaks both ways:
   `Woodev-Settings` → `woodev-settings` (false positive on someone else's page) and
   `edit.php?post_type=shop_order` → `editphppost_typeshop_order` (false negative on a legal
   submenu slug). WP core itself uses `wp_unslash()` + `plugin_basename()`, no sanitising. Now
   compares the raw unslashed value, with a specific `phpcs:ignore` naming why comparison-only use
   against trusted slugs is safe.

Non-blocking note Codex raised on the #663 fallback test (asserts selector text only) is real but
bounded by the medium — a PHP unit test cannot observe a DOM move. The rig covers it.

## CI caught what no local run could

PR #661 went red on **Unit Tests (PHP 7.4) and (PHP 8.0)** while 8.1/8.2/8.3 passed:
`ReflectionException: Trying to invoke protected method … from scope ReflectionMethod`.

The worker had reasoned about the version span and still got it backwards — it dropped
`setAccessible()` believing 8.1 deprecated it. **8.1 made it a no-op; it is 8.5 that deprecates it.**
Local PHP here is 8.5.1, so the local suite could never have shown this.

Fixed by removing reflection entirely in favour of the public-wrapper fixture idiom the sibling
test file already uses — version-proof, no guard to get wrong. This is the SECOND instance of the
s98 gotcha `the-local-php-is-four-versions-above-the-ci-floor`, so that file was updated rather than
a second one opened.

failures start. #358/#356 were therefore NOT run in parallel, as I had first intended.
