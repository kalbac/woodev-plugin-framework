## #676 — the challenge-cookie jar is scoped by origin now

`Woodev_API_Base` kept its bot-protection challenge cookies in a flat `name => value` map with no
host binding, so `add_challenge_redirect_cookies_to_request_args()` attached them to any outgoing
request of the instance. Two commits:

- `5b2c02d` — jar re-keyed as `origin => [ name => value ]`; a new private static
  `get_uri_origin()` reuses the normalisation `is_same_origin_uri()`/`get_uri_port()` already
  encoded rather than writing a second, subtly different one; the disabled path short-circuits
  **before** the filter, so a client that never opted in fires no hook at all; `..._updated` fires
  only when that origin's jar actually changed. Both hooks take the origin as an added argument —
  names unchanged, no deprecation shim, per the clean-break policy for an unreleased mechanism.
- `e870355` — the caller's own `Cookie` header now wins over the jar.

## The critic earned its round — twice, on things the card never mentioned

Codex confirmed the design and then found two defects that predate it, both from PR #674:

- **#686** — `parse_challenge_redirect_set_cookie()` keeps only the text before the first semicolon
  (`class-api-base.php:475-479`). So `Max-Age`, `Expires`, `Path`, `Domain` and `Secure` are all
  discarded, and a server's deletion `name=; Max-Age=0` is stored as `name => ''` — the entry never
  goes away and is re-sent forever. Origin keying fixes host leakage; it does not touch cookie
  semantics, and the two should not be confused.
- **#687** — `resolve_challenge_redirect_uri()` treats **any** `Location` containing `://` anywhere
  as absolute (`:262-264`), so a valid relative `/challenge?return=https://provider.example/` is
  rejected as cross-origin; and a query-only `?challenge=1` resolves to the parent directory instead
  of the current resource (`:286-288`), against RFC 3986 §5.3.

Neither was folded into #676. Both are bigger than it and independent of it.

## #683 — the operator refused the diagnosis, and he was right

s107 recorded that a Codex worker could not reach the Orca CLI from its shell, that its shell is a
Linux one, and that an Orca worktree therefore needs its `.git` rewritten to a relative `gitdir` as
step 0. His answer: «Codex мы использовали с самого начала, и он отлично работал из-под CLI Orca…
Поэтому, я не верю, что Codex вот так вот просто на ровном месте перестал работать, а ты теперь
начал "костыли" строить.»

A clean experiment — native `worker-start --agent codex` into a fresh worktree, no ritual, no WSL,
no `.git` edit:

| s107 claim | s108 measurement |
|---|---|
| the CLI is unreachable, `ORCA_CLI_COMMAND` empty | **reachable** — the worker ran `orca status --json` itself, `runtime ready` |
| the tool shell is Linux `bash` | **PowerShell 7.6.5** — its own tool calls use `Get-Content`/`ForEach-Object`; `uname` is not a cmdlet |
| the worktree needs a relative `gitdir` first | **`git rev-parse --show-toplevel` succeeded with `.git` untouched** |
| `worker-start --agent codex` fails three times in four | started on the **first** command; a real Codex TUI, `gpt-5.6-terra` by default, `permissions: YOLO` |

The one thing that did block it was **Codex's own update dialog** (`0.150.1 -> 0.151.0`), which eats
the injected prompt. The operator updated Codex, removing the cause rather than the symptom.

**The real defect is different, and it was reproduced:** the dispatch body does not always reach the
prompt. The worker received the Orca preamble and no task, and said so plainly — "No substantive
assignment reached my prompt". Re-delivering the brief with `terminal send` fixed it instantly.

That is almost certainly what happened in s107 to the worker that "traded the task for a receipt":
**it never had a task.** Its own explanation was recorded as a measured fact and never verified —
which is exactly the failure the project has a rule against.

Corrected as a result: `codex-in-wsl-needs-a-relative-gitdir` (the whole causal chain is downstream
of one variable — which shell Codex got — so measure that first; the rewrite is a conditional
remedy, not a step 0) and `starting-codex-under-orca-needs-four-steps-not-one` (the extra steps were
the update dialog, not an Orca requirement).

## What this session is worth remembering for

A worker's account of **why** it failed is a hypothesis, not a measurement — and it is the most
tempting kind to write down, because it arrives already phrased as a finding. s107 promoted one into
a card, two gotchas and the wiki in a single session. The operator caught it by refusing to take a
plausible story on trust, and the cost of checking was one worktree and about twenty minutes.
