## #676 — the challenge-cookie jar is scoped by origin now

`Woodev_API_Base` kept its bot-protection challenge cookies in a flat `name => value` map with no
host binding, so `add_challenge_redirect_cookies_to_request_args()` attached them to any outgoing
request of the instance. Two commits:

- `5b2c02d` — jar re-keyed as `origin => [ name => value ]`; a new private static
  `get_uri_origin()` reuses the normalisation `is_same_origin_uri()`/`get_uri_port()` already
  encoded rather than writing a second, subtly different one; the disabled path short-circuits
  **before** the filter, so a client that never opted in fires no hook at all; `..._updated` fires
  only when that origin's jar actually changed. Both hooks take the origin as an added argument —
  names unchanged, no deprecation shim, per the clean-break policy for an unreleased mechanism.
- `e870355` — the caller's own `Cookie` header now wins over the jar.

## The critic earned its round — twice, on things the card never mentioned

Codex confirmed the design and then found two defects that predate it, both from PR #674:

- **#686** — `parse_challenge_redirect_set_cookie()` keeps only the text before the first semicolon
  (`class-api-base.php:475-479`). So `Max-Age`, `Expires`, `Path`, `Domain` and `Secure` are all
  discarded, and a server's deletion `name=; Max-Age=0` is stored as `name => ''` — the entry never
  goes away and is re-sent forever. Origin keying fixes host leakage; it does not touch cookie
  semantics, and the two should not be confused.
- **#687** — `resolve_challenge_redirect_uri()` treats **any** `Location` containing `://` anywhere
  as absolute (`:262-264`), so a valid relative `/challenge?return=https://provider.example/` is
  rejected as cross-origin; and a query-only `?challenge=1` resolves to the parent directory instead
  of the current resource (`:286-288`), against RFC 3986 §5.3.

Neither was folded into #676. Both are bigger than it and independent of it.

## PR #688 — four rounds on one mechanism, and what each round cost

#686 (cookie deletion/expiry) and #687 (RFC 3986 Location resolution) were built together: same
file, same mechanism, so one worker and one PR rather than two agents in one file. Six commits.

| round | what it fixed | whose error |
|---|---|---|
| 1 | the two cards as written | — |
| 2 | `Path` applicability; strict-digit `Max-Age`; empty base path and empty `Location` | critic found; one was a re-priced decision |
| 3 | multi-cookie header; structured persistence hooks; whitespace-only `Location` | **the coordinator's own contract, twice** |
| 4 | verification only — one LOW finding, rejected with reasoning | — |

**The coordinator was wrong twice, and both were contract errors rather than code errors:**

1. "Flatten the jar to `name => value`, preferring the longer path" was written for the HOOK payload
   and applied by the worker to the OUTGOING HEADER as well — a fair reading. RFC 6265 §5.4 requires
   every path-matching cookie, longest path first, and duplicate names in a `Cookie` header are legal.
2. Requiring the hooks' payload to stay a flat `name => value` map — a constraint carried over from
   #685 — made the persistence hook unable to persist. A PHP request does not outlive itself, so that
   filter/action pair is the ONLY way a challenge cookie reaches the next request. A persistence
   mechanism that cannot represent what it persists is a design error, not a simplification. The
   payload became the structured per-origin jar; the shape changed twice in one PR, deliberately, on
   an unreleased mechanism.

**`Path` was implemented after being explicitly refused one round earlier, and the reason is worth
keeping:** the refusal was priced when the code parsed no Set-Cookie attributes at all, so honouring
`Path` meant building a parser. Commit 1 added that parser. The price fell from "build a cookie jar"
to "a prefix match", and a decision priced at the old cost has to be re-taken. The critic rated it
HIGH; that was rejected — a same-origin over-send is not high severity — and it was built anyway for
the cost reason, not the severity one.

**One critic finding was rejected on the merits and filed as #689:** equal-length `Path` ties are
ordered by jar-iteration order rather than RFC 6265 §5.4's creation time. Verified against the code
rather than argued: the jar is keyed `name → path → entry`, so a same-name tie needs two identical
paths, which is one key. Ties are therefore only ever between DIFFERENT names, where a `Cookie`
header is parsed into a map and order is unobservable. Real deviation, no reachable consequence.

s107 recorded that a Codex worker could not reach the Orca CLI from its shell, that its shell is a
Linux one, and that an Orca worktree therefore needs its `.git` rewritten to a relative `gitdir` as

| s107 claim | s108 measurement |
|---|---|
| the CLI is unreachable, `ORCA_CLI_COMMAND` empty | **reachable** — the worker ran `orca status --json` itself, `runtime ready` |
| the tool shell is Linux `bash` | **PowerShell 7.6.5** — its own tool calls use `Get-Content`/`ForEach-Object`; `uname` is not a cmdlet |

The one thing that did block it was **Codex's own update dialog** (`0.150.1 -> 0.151.0`), which eats
the injected prompt. The operator updated Codex, removing the cause rather than the symptom.

**The real defect is different, and it was reproduced:** the dispatch body does not always reach the
prompt. The worker received the Orca preamble and no task, and said so plainly — "No substantive
assignment reached my prompt". Re-delivering the brief with `terminal send` fixed it instantly.

That is almost certainly what happened in s107 to the worker that "traded the task for a receipt":
**it never had a task.** Its own explanation was recorded as a measured fact and never verified —
which is exactly the failure the project has a rule against.

Corrected as a result: `codex-in-wsl-needs-a-relative-gitdir` (the whole causal chain is downstream
of one variable — which shell Codex got — so measure that first; the rewrite is a conditional
remedy, not a step 0) and `starting-codex-under-orca-needs-four-steps-not-one` (the extra steps were
the update dialog, not an Orca requirement).

Two corrections he made to me in the same conversation, both recorded in `AGENTS.md`:

1. I turned one answer into a universal rule — "every label names an action". He does not work that
   way: **the label carries the short essence, the control type carries part of the meaning, and the
   `desc_tip` carries the explanation.** Naming the action suits a mode `select`, not a checkbox.
2. Our `description` rule was written too narrowly ("reserved for interactive elements").
   `description` and the tooltip **coexist**; `description` earns its place when the text must be
   followed, copied, or simply SEEN — because a tooltip is not always read.

And one error of mine inside that: I claimed «Зафиксированная локация требует повторного выбора» was
a visible option needing a shorter name. It is not visible at all — it is registered without a
control. I had read `'name' => __(…)` as proof of rendering. The discriminator is
`register_control()`, and I got that wrong twice in a row before measuring it properly.
