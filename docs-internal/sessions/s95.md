## #405 — the code was right, the measurement was wrong

CURRENT-STATE has carried this since s83:

> With a deliberately bogus CDEK client id — confirmed in wp-config, transient cleared, measured
> against a control — the provider returned the same results as with valid keys and never threw.

That is false, and it took four runs with a control on each side to see why. The fixture reads its
credentials through `get_integration_option()` — i.e. the **WooCommerce integration settings array**
`woocommerce_woodev_test_shipping_method_settings`. The rig also carries a standalone
`woodev_location_cdek_client_id` option with the same value in it, and **nothing reads that one.**
Every earlier probe had been writing the decoy.

| Condition | region `Мос` | settlement `Зеленоград` |
|---|---|---|
| valid keys, token transient cleared | OK, 2 | OK, 5 |
| bogus key in the **decoy option**, both transients cleared | OK, 2 | OK, 5 |
| bogus key in the **integration settings**, regions transient warm | OK, 2 | **THREW** |
| bogus key in the **integration settings**, both transients cleared | **THREW** | **THREW** |

Two more things were masking it even once the right value is written: `token()` returns a cached
`woodev_test_cdek_token` before it looks at credentials at all, and the REGION level answers from
`woodev_test_cdek_regions_{country}` without touching the network — so on this rig, whose region axis
is «Предустановленный список», **the region axis can never demonstrate a credential failure.**

`#405`'s contract is correct and demonstrable. Rig restored to its exact prior state, control
re-verified green afterwards. Gotcha:
`the-cdek-fixture-credentials-are-not-the-option-they-look-like`.

## #531 — the guard, and the hole the critic found in its tests

The worker built it on the seams that already existed (`location_service()`, `effective_fields()`,
`posted_country()`), mirrored `fieldValueFor()`'s settlement branch in PHP, reused
`Location_Controller::normalize_for_stale_pick_comparison()`'s normalization rather than inventing
one, and extracted `Checkout_Config::location_i18n_strings()` so the guard and the JS config share
ONE filtered defaults array instead of two copies that drift.

**The critic pass is what earned its keep.** It verified the three load-bearing claims by hand and
then mutation-tested the suite with four independent mutations. Three were caught. One was not:

> Deleting the `$section` match from `settlement_field_id_for_section()` left **all 13 tests green.**

That method implements Rule 7c — the billing-vs-shipping column choice — the single highest-risk
piece of the PR, since picking the wrong column blocks a legitimate checkout. The diagnosis was
precise: every existing test either collapsed to one column or omitted the other column's POST key,
so the blank-value short-circuit fired before the section logic was ever reached.

Fixed by a second worker with two tests where **both** columns carry a settlement field with
different non-blank values. Re-applying the mutation now reddens. `2813 → 2815`.

## #529 — the question worth answering slowly

The worker verified reachability first (as briefed) and then asked a real question rather than
guessing: ~11 tests boot the `related-list:settlement` renderer **as a vehicle** to pin regressions
in machinery that is still alive (`resolveAndSelect()`'s `lastHandledKey` guard,
`resetWidgetGuard()`'s silent-write routes). Delete them, or port them to `ajax-select2`?

Answered: **port them.** #529 is about removing an unreachable MODE, not about removing coverage of
reachable code, and using a dead-code cleanup to quietly drop 11 regression tests would leave the
repo worse than it started. The porting risk it named is real and has a direct answer — a port that
passes but no longer catches the original bug is worse than deletion, because it looks like
coverage. So: one at a time, break the targeted mechanism, confirm the ported test reddens for the
same reason, restore. And if a test is genuinely inseparable from the dead renderer, remove **that
one** and name it as a gap.

It landed that way. Reachability was disproved first with a citation — `offered_field_modes_for()`
never offers `related-list` for the settlement axis, and `get_field_mode_settlement()` clamps a
stored value away **unconditionally** on read, so no store configuration could reach it (verified
independently by the coordinator before merging a deletion). Seven tests were ported to
`ajax-select2` and falsified one at a time; 21 with no surviving equivalent were removed and
accounted for individually. The worker also **reversed one of its own deletions mid-task**:
`listFor()`/`options.list` looked dead, and its own test proved it is a renderer-agnostic extension
seam, so it was restored.

jest goes DOWN here on purpose: `1549 → 1529`, which is `-20` removed plus the `+4` #549 added under
it. That accounting is in the PR body test by test — a falling test count is exactly the number that
must never be waved through.
