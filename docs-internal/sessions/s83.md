## Orca — what we adopted

Read `orca skills get orca-cli` and `orca skills get orchestration` (both complete; `--full` returns
byte-identical output, so nothing was missed). Compiled into
`wiki/orchestrating-agents-with-orca.md`, which is now the single place this lives.

Adopted: orchestration runs/tasks/dispatch as the subagent path, `worker-start --agent claude
--model sonnet --effort high` for workers and `--agent codex` for critics, `worker-read` for
provenance, `ask`/`reply` so a worker can block on a decision instead of guessing, and worktree
comments for operator-visible progress. **Not** adopted, with reasons recorded: artifacts (gated,
no audience), automations (nothing recurring), Linear (the board is GitHub Projects), emulator (no
mobile). The built-in browser was tried once against the rig and dropped — the first `snapshot` of a
WP admin page returned `runtime_unavailable`; the runtime recovered and live workers were
unaffected, but debugging it while the same runtime carries workers is the wrong trade.

Measured, not assumed: agent hooks are **enabled** for claude/openclaude/codex (my first hypothesis
that they were off was wrong); Codex's hooks **fail** at runtime (`PostToolUse hook (failed)`), which
is the likely reason `worker-read` degrades to scraping the terminal; there are **no** managed Claude
accounts, Codex runs on the system oauth; Codex's weekly rate limit was at **0%**, so the Pro
allowance really is idle.

## The three defects the tooling produced — all mine as orchestrator

1. **Serena path in the brief.** All three briefs repeated the `CLAUDE.md` rule verbatim, which names
   `D:/Projects/woodev_framework` — the main checkout. Workers therefore had git in their worktree
   and every Serena edit in mine. Two of three hit it; one recovered alone, one was caught when stray
   paths appeared in `git status` on main. Nothing lost, only because main was committed. Gotcha
   `serena-activate-path-must-be-the-worker-s-worktree`; rule fixed in all three places that carry it.
2. **`input_accepted` is not proof a worker started.** Three of five agents accepted their task and
   executed nothing, with the prompt sitting unsubmitted in the TUI while every liveness signal read
   healthy. It cost two full nine-minute wait windows. Every occurrence was a Codex launch — its MCP
   startup swallows the Enter. Gotcha `input-accepted-is-not-proof-a-worker-started`.
3. **A `UserPromptSubmit` hook timeout looked like the cause and is not** — a later dispatch printed
   the same timeout and ran anyway. Recorded as settled inside the same gotcha so nobody re-derives it.
