## Orca configured properly — the second half of the session

The operator pushed back on the first Orca pass: it had come from the CLI-bundled skills, not the
product docs at <https://www.onorca.dev/docs>. He was right, and the real docs carried the thing that
mattered — a repo config file the skills never mention.

**A fresh worktree is now gate-capable with no install step at all.** Two checked-in files:
`orca.yaml` (`worktree.sharedDirectories: [node_modules]`, symlinked) and `.worktreeinclude`
(`vendor`, `.mcp.json`, `.wp-env.override.json`, `.claude/settings.local.json`, copied).

`vendor` **must be copied, never shared** — Composer bakes `$baseDir = dirname(dirname(__DIR__))`
into its autoloader and PHP resolves a symlink to its real path, so a shared `vendor` makes the
classmap load the primary checkout's sources while the bootstrap loads the worktree's: every class
declared twice. Found by measuring, not by reading. Gotcha
`sharing-vendor-breaks-composer-autoload-in-a-worktree` (173 total).

Measured on throwaway worktrees: **2475 unit / 6112 assertions, 1260 jest, phpstan clean, zero
installs**, against **411 seconds** for a `composer install` there.

**Worktrees moved into the project** at `.orca/worktrees/` — the operator set it globally as a
relative path, so every repo gets the same layout inside itself. Safe here because every gate is
path-scoped (phpcs `./woodev`, phpstan `paths: woodev`, phpunit `./tests/unit`): with a worktree in
place the main tree still reports 2475 unit tests, not one double-counted. `/.orca/` is gitignored
and Serena honours that via `ignore_all_files_in_gitignore`. Residual cost, stated not hidden:
`.wp-env.json` maps the whole repo root, so worktrees land inside the rig container.

Cleanup: `C:/Users/maksi/orca` and `D:/Projects/_woodev_wt` both held **0 files** and were removed;
all 11 stale worktrees left the registry (#414 closed). #408 closed too — the setup script it asked
for is obsolete now that the config does it for free.

**Three UI settings I named were wrong.** I mapped internal JSON keys to invented Settings labels
and presented guesses as fact. Only two of five existed: Worktree directory and Agent hibernation.
`experimentalAgentDashboardShowIdle` lives on the dashboard itself, not in Settings;
`refreshLocalBaseRefOnWorktreeCreate` and `terminalScrollbackRows` are not exposed at all.

**A session no longer needs to be told it is in Orca.** Asked how to avoid writing "you work under
Orca, use worktrees" every time, I started building a `SessionStart` hook; the operator called it a
workaround and was right. The real gap was that only `orca-cli` was installed as a skill, so
`orchestration` was invisible to a fresh session. One command fixes it natively:
`orca skills install --skill orchestration --skill orca-cli --skill computer-use --agent claude-code`.
All three now surface on their own, Orca already injects its own preamble for a dispatched worker,
and `CLAUDE.md` carries the three facts no skill can know — no install step in a brief, the worker's
own Serena path, and `input_accepted` not being proof. The hook and its script were deleted.
