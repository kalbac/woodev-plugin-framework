## #472 — the fourth round, licensed by a decision rather than by another try

The handoff was explicit: three rounds were spent, and a fourth was allowed only because the
operator had settled **Rule 7c**. Two fixes were named, and both were right:

1. **Replace `_doing_it_wrong()` with a documented precedence.** The notice fired on a *legitimate*
   configuration — the §8 demo declares `billing_state` and Rule 7b's own fan-out re-claims it — and
   `_doing_it_wrong()` asserts the developer called something wrong, which nobody did. It was
   `WP_UnitTestCase`'s caught-doing-it-wrong assertion that turned it into five integration
   failures. The rule now: **a direct declaration beats a fan-out variant whatever the registration
   order**, same-kind claims fall back to first-wins, and the winner inherits the loser's position
   so field order never depends on who won.
2. **Carry the chain's RECORDS across a column swap, not just the widget.** `entry.records` keys by
   LEVEL and survived on its own, which is exactly why round 3 looked finished — but `entry.resolved`
   keys by FIELD id, and the incoming column's field was never seeded, so the next programmatic
   `change` compared against `undefined`, read as a customer edit, and dropped the level's record:
   *filled fields plus a re-locked address*, the #337/#459 failure.

Read from WooCommerce's own source rather than assumed: `checkout.js` binds the toggle to
`trigger_update_checkout` and `ship_to_different_address` (which only slides the fieldset), and
`update_order_review` returns order-review and payment fragments — never the address fieldsets. **WC
does not copy one column's address into the other in the DOM.** The copy Rule 7c refers to is
`WC_Checkout::get_posted_address_data()`, server-side at submit. Carrying is ours.

### The critic earned its round

Codex REJECTed with two HIGH findings. Both were real, and I verified each rather than taking them:

- **Descendant invalidation.** Dropping only the contradicted level's record left its descendants
  describing a locality the customer had just disowned — and the empty-field branch then *wrote one
  in*: billing holds Москва plus a picked address, the customer types Жуковский into `shipping_city`,
  toggles, and the shipping column silently receives a street belonging to Москва. Fixed: a
  contradiction blocks every deeper level, dropping identity but never the customer's own text.
- **The Rule 7c consequence**, which my own measurement had found independently — see below.

## #481 — the measurement that made #472 worth looking at

Before handing the operator a rig pass I measured what the fan-out actually produced. It produced
this:

```text
shipping_state     section=shipping  level=region
shipping_city      section=shipping  level=settlement
billing_address_1  section=billing   level=address
shipping_address_1 section=shipping  level=address
```

No `billing_state`, no `billing_city` — the §8 demo owned those ids and a direct declaration wins.
With the toggle unchecked (the RU default) `isNodeActive()` refuses a widget to a shipping-section
field, so **region and settlement had no live cascade at all** on the default checkout view. Rule 7c
was unobservable on the very rig meant to demonstrate it.

Not a regression from #472 — before it, the fixture pinned all three to `shipping` and no level
worked — but it meant a rig pass would have been wasted. The operator chose to move the §8 demo onto
`billing_company`/`billing_address_2`, and after the move all three levels exist on both columns.

## What the browser found that the whole suite did not

Self-verifying in the browser before asking the operator to look, I found a defect **the entire
green suite had no opinion about**: `refreshAddressLock()` only ever walks the chain's *current*
address node, so once round 3 made that node move between columns, the field left behind kept
`disabled` and the locked class forever. `billing_address_1` is a **required** field, and a disabled
input is not submitted — the customer could not have completed checkout. Fixed and re-verified live
in both directions.

## The operator's own pass found two more

Both were pre-existing and both were only *reachable* because #472/#481 had finally put the cascade
on the active column.

**#484 — an address suggestion overwrote the region.** `backwardsFill()`'s cross-provider guard is
falsy-guarded, and the server was publishing `owners.RU.region = ""`. The settlement level was
untouched in the same session because its owner *was* set — that asymmetry was the whole clue. Root
cause: in `related-list` mode this layer's own injector fills `woocommerce_states` (measured: 87 CDEK
regions), so `$states_present` was always true and the #294 arbitration stood the layer down from its
own list, taking the owner with it.

An earlier, broader version of that fix also forced `levels['region']` true — and was **caught by an
existing test** that pins the `false` deliberately. It was right to: `levels` means "is this a
typeahead target", and under related-list the answer genuinely is no. `owners` and `levels` answer
two different questions.

**#486 — the settlement axis still offered «Предустановленный список».** Removed the server-side
gate (#404's premise — that a region-scoped list is likely complete — was disproven on 24.08 by a
scoped list returning exactly 500 = `LIST_HARD_CAP`). Measured two options offered. **And the admin
still showed three.** The client had its own half: `getLiveSelectOptions()` replaced the settlement
axis's options with the REGION's whenever the region axis sat at `related-list`. The REST payload and
the rendered control disagreed, and only the rendered control is what anyone can see.

## Three tries to write one honest test

The replacement test for #486 passed against a deliberately broken implementation **three times**,
and only the control caught it each time:

1. it asserted against a **closed** custom select — options live in a popover portal and are absent
   from the DOM either way;
2. my control patch edited the `radio` branch, then the `select` branch with a placeholder label the
   assertion never looked for;
3. opening the popover leaks a state update outside `act()`, and `@wordpress/jest-console` turns that
   into a failure of a *different* test later in the file.

**A control that passes is not a control.** Recorded as its own gotcha.

## The brainstorm — #437's first open question, closed

Settled with the operator and written up as `specs/2026-08-24-popular-settlements-design.md`
(card #488). The load-bearing decisions: an entry is a whole `Location_Record` (so a popular-list
pick is literally the same object down the same `/select` path as a search pick); **two clocks**
rather than one, because usage and freshness pull in opposite directions and a single clock would
fail exactly on the most-ordered settlements; a new `CAPABILITY_RESOLVE_KEY`, because **no method in
the contract today accepts a key**; verification **lazy at the moment of pick** instead of a
validating cron, because the operator's own observation is that big cities never change identity and
the ones that do get ordered twice a year and age out anyway; cron reduced to deleting rows and
making zero provider calls.

Also measured and struck off that spec's open list: **`WC()->checkout()` IS reachable in wp-admin**
(session and cart instantiate, `get_checkout_fields()` returns the full set).
