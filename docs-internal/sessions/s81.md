## Задача 10 — как устроена и почему так

Круг, который пришлось разорвать: доступность настройки = «резолвит ли цепочка кого-нибудь на
уровень `address`», а гейт = «если выключено, цепочка не должна резолвить никого на `address`». Если
гейт спрашивает значение, которое само считается обходом цепочки, получается рекурсия. Разложение:

- `get_address_suggestions_raw()` — сырой сохранённый флаг, **его и читает гейт**;
- `Location_Service::is_level_servable()` — обход цепочки в обход И гейта, И фильтра
  `FILTER_PROVIDER_FOR_LEVEL`; его читает админка, потому что ей нужна СПОСОБНОСТЬ, а не текущий
  ответ: магазин с выключенным переключателем обязан видеть контрол активным, если включение что-то
  даст;
- `is_address_suggestions_enabled()` — `raw && available`, спековое «эффективное значение»; гейт его
  не читает.

Гейт стоит ДО обхода цепочки внутри `provider_for_level()`, поэтому `get_levels_for_country()`,
`get_level_owners_for_country()`, `is_country_supported()` и REST-маршрут `/suggest` соглашаются
автоматически. Фильтр продолжает срабатывать и при закрытом гейте — шов не убираем.

Воркер прошёл все шесть вызывающих `provider_for_level()` по отдельной просьбе и доказал структурно
(а не утверждением), что снятие уровня `address` не может каскадом утащить НП: `gate_chain()` роняет
только потомков, а `address` — самый глубокий уровень.

## Главная находка сессии — F4

Ни один из четырёх аудиторов её не увидел; она вылезла из вопроса «а что вообще произойдёт, если

`hide_for_pickup` жил только в браузере: `Checkout_Field_Policy` в собственном докблоке заявлял, что

`WC_Checkout::validate_posted_data()` проверяет НАЛИЧИЕ, а не видимость. Замер на риге
(`hide_for_pickup` + pickup-метод + `pickup_replace_address = 0`, POST на `/?wc-ajax=checkout`):

```
{"result":"failure"}
Billing Street address is a required field.
Billing Postcode / ZIP is a required field.
Shipping Адрес (Location Provider) is a required field.
Shipping Postcode / ZIP is a required field.
```

Четыре ошибки про четыре поля, которых покупатель не видит и заполнить не может. Обычно это
маскируется тем, что выбор ПВЗ вписывает адрес и индекс точки в поля, — но `pickup_replace_address`
это штатно выключаемая опция (S7), и план задачи 9 сам просит именно эту конфигурацию как
контрольный прогон. То есть конфигурация поддерживаемая, а не экзотическая.

Готча: `js-hidden-checkout-field-is-still-required-server-side`. Правило на будущее: **что браузер
прячет — то сервер обязан перестать требовать, в том же самом условии.**

## Второй дефект той же фичи — CSS

Найден при доведении риг-матрицы до конца, и его легко было не заметить: сразу после переключения
метода строки ДЕЙСТВИТЕЛЬНО прячутся, поэтому быстрая проверка проходит. Возвращаются они на
следующем проходе локали — то есть на другом взаимодействии.

`woocommerce/assets/js/frontend/address-i18n.js` на каждом `country_to_state_changed` (загрузка
страницы, смена страны, любой `update_checkout`) делает для каждого поля локали:

```js
if ( true === fieldLocale.hidden ) { field.hide().find( ':input' ).val( '' ); }
else if ( 'state' !== key )        { field.show(); }
```

`.show()` пишет ИНЛАЙНОВЫЙ `display: block`, который бьёт классовое правило без `!important`.
Замер: все четыре строки несли свой класс И инлайновый `display: block`, вычисленное значение
`display: block`, высота 115px — политика молча не работала. С `!important` — `display: none`,
высота 0, при том же инлайновом стиле. Противник тут — сам WooCommerce, а не враждебная тема, так
что `!important` здесь несущий, а не привычка.

Побочно из того же куска WC: поле, скрытое через локаль, WooCommerce ОЧИЩАЕТ. Поэтому спрятать
строку «через локаль вместо CSS» нельзя там, где значение обязано доехать до заказа — а обе эти
опции именно про это.

## Codex-критик — два прохода

**Проход 1** (задача 10): P0 нет, одна P1 — `$setting->get_control()` может быть `null`, потому что
в этом же файле две настройки намеренно регистрируются без контрола. Проверил по коду
(`Woodev_Setting::$control` не инициализировано, `Field_Schema` страхуется тем же null-check'ом) —
подтвердилось, починено.

**Проход 2** (серверный фикс + CSS): **P0, и справедливая.** Я сам её не увидел, а мой живой тест
её замаскировал. Фикс читал только `WC()->session->get('chosen_shipping_methods')`, а по исходнику
WC:

- `get_checkout_fields()` строит массив полей ОДИН раз за запрос и кэширует в `$this->fields`;
- фильтр `woocommerce_checkout_fields` срабатывает внутри `set_checkout_fields()`;
- `process_checkout()`: строка 1381 `get_posted_data()` (тут и срабатывает наш фильтр) → 1385
  `update_session()` → 1396 `validate_checkout()` на УЖЕ закэшированных полях.

То есть в момент решения сессия ещё держит то, что было ДО сабмита. Мой прогон прошёл только
потому, что клик по радио заранее запустил `update_order_review`, и сессия совпала с POST по
случайности порядка. Опасны обе стороны, и вторая тише: сессия pickup + POST курьер → мы снимаем
`required` → заказ с пустым ВИДИМЫМ адресом проходит. Исправлено так, как это делает сам WC в
`update_session()`: POST накладывается на сессию по индексу пакета.

Урок не про Codex, а про меня: живой прогон, который «прошёл», — не доказательство, пока не
понимаешь, почему именно он прошёл.

  пустым адресом пройдёт тихо. Спека #362 мультипакетность не описывает вообще, поэтому выбор
  правила — решение, а не починка.
- **#370** — машинные поля «Зафиксированная локация» и «…требует повторного выбора» редактируются
  вручную в админке, хотя код регистрирует их без контрола именно чтобы этого не было.
  `Field_Schema::from_handler()` не исключает бесконтрольную настройку, а лишь кладёт
