## Что сделано

- **#843 (PR #937).** `match=any` → «период И перевозчик И (ф₁ ИЛИ ф₂ …)» — его решение 27.09.
  `Orders_Id_Resolver` получил лист статуса заказа (коррелированный `EXISTS` по `wc_orders.status` /
  `posts.post_status`); при ИЛИ со статусом нативный `status` расширяется до полного списка; ИЛИ живёт
  только в запросе id. Оракул `ShippingOrdersQueryRowSemanticsTest`: 144 заказа × 540 запросов × 2
  хранилища, мутации ловятся. Клиент: токен `{{select /}}`, `match` из URL уходит в REST.
  Мой Playwright-зонд на риге: 6/6, реальные числа delivered 34, completed 69, «Все» 6, «Любое» 97 =
  34 + 69 − 6. Критик Codex terra — PASS (своя мутация `>= 2 → >= 99` поймана).
- **#936 (в том же PR #937).** Упавший запрос id пишется в `error_log`, отказ остаётся закрытым.
  Интеграционный тест гоняет настоящий SQL резолвера против оракула на ОБОИХ хранилищах в одном
  прогоне (переключение `woocommerce_custom_orders_table_enabled` на кейс): 57 заказов × 720 запросов,
  три мутации красные. Ветка стояла на #843, поэтому коммиты сложены в PR #937 — стековый PR развалился
  бы после squash.
- **#916 (PR #938).** Неоднозначный download id → новый код `woodev_license_ambiguous_plugin` / 409;
  `woodev_license_unknown_plugin` / 404 не тронут; диспетчер конверта — отдельный путь. JS не менялся.
  Текст — предложение, его слово. Критик Codex luna — PASS.
- **#935 (PR #939, смержен).** Замер на 10 тыс. и 100 тыс. заказов: ни проталкивание статуса/периода в
