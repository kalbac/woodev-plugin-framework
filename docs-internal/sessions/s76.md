## #337 — lock the address field until a settlement is picked (PR #345, awaiting the operator)

- The rule, exactly as the operator narrowed it: lock ONLY when the chain carries both a settlement
  and an address field AND the provider serves the `address` level for that node's own country.
  Everywhere else the address field stays an ordinary input.
- **The chain, not `depends_on`.** A location-kind field carries no `depends_on` at all — the chain
  is assembled from `location_level`. "Linked" and "scoped by" are therefore the same fact, and it
  is `scopeKeyFor()`/`isNodeActive()` that answer it, which also guarantees the lock and the widget
  can never disagree about which country's coverage applies.
- Nothing explains the lock (no `title`, no aria, no caption) — the standing rule, same as #274.
  Client-side only; the server stays the authority.
- Re-applied on every transition that can change the answer: boot, the settlement pick itself
  (optimistically, before `/select` answers), the server's own chain repair, a text edit without a
  pick, country/section arbitration, a checkout re-render.
- **Bug found on the rig mid-fix** — `disabled` was invisible: the theme's own `input` rule erases
  the browser's greying, so the field looked exactly like its editable twin. Added a
  `woodev-location-locked` class plus one flat rule in `location.css` (dimmed + `not-allowed`),
  the single deliberate exception to that file's own "never style the input" discipline. Gotcha
  `disabled-alone-is-not-a-visual-signal`.
- Rig-verified end to end in one run with the control in the same pass: locked on a fresh guest →
  pick the settlement → unlocked immediately; unlocked straight after a reload that restored a
  settlement record; re-locked on a settlement text edit without a pick; ordinary input under AM.
- Both directions of the predicate pinned by mutation (6 and 8 failures respectively).

## #343 — a live CDEK provider on the rig (PR #347, merged)

- Read CDEK's docs through Context7 BEFORE implementing, as the card required. Their Locations API
  has exactly three endpoints (`/location/regions`, `/location/cities`, `/location/suggest/cities`)
  and **no address/street suggestion at all** — which is what makes scenario A real rather than
  assumed.
- The fixture keys off CDEK's own dictionary codes, never FIAS — even though Moscow's `fias_guid`
  is byte-for-byte DaData's (measured). Borrowing another provider's identifier space would hide
  the very seam the fixture exists to expose.
- The one derived rule is splitting CDEK's `full_name` composite into display components; identity
  never depends on it. A federal city carries no region part, and its region is recovered by an
  exact lookup in CDEK's own region dictionary — confirmed, not derived.
- **Scenario A measured live** (CDEK active, DaData unconfigured): `levels.RU.address = false`, the
  address field is a plain input with no widget attached, and the whole path works — settlement
  picked, address free-typed, pickup point chosen, and after a reload `current = test-cdek:44` with
  `carrier_pickup_point` intact. The pickup selection survives a reload on a provider that has no
  address level at all.
- **Scenario B measured live** (both configured, CDEK active): the address suggest goes out with
  `within=test-cdek:44` and DaData answers it correctly narrowed. The handover works because
  `build_scope()` resolves `within` against the customer's chain into a real record and providers
  read `parent_components()` — components, never keys. Keys never mix. Gotcha
  `a-cross-provider-within-is-handed-over-as-components`.
- **Correction to my own expectation:** scenario A is NOT reachable merely by making CDEK active —
  D15's chain falls back to DaData for the address level, and `levels` honestly reports the LAYER's
  coverage, not the active provider's. Gotcha
  `a-level-served-can-come-from-the-fallback-not-the-active-provider`.
- Credentials stay out of the repo despite being publicly published by CDEK — same wp-config
  constant bridge the DaData token uses.

## #325 — single-package as a configuration outcome (PR #348, merged)

- Multi-package cart NOT built (YAGNI, no consumer). Surveyed where "one" was actually baked in and
  found exactly one place: `Checkout_Handler::validate()`'s pickup backstop took the FIRST
  `is_pickup_slot` field and stopped, while `placeSlots()` has always mounted a trigger per
  declared slot — so a second declared slot got a trigger and no validation, silently. The backstop
  now enforces every declared slot; nothing changes for today's plugins.
- Everything else was already parameterised: `mark_pickup_slot()` is per-field, and
  `Pickup_Selection`'s map is keyed `(locality, type)` with its own eviction cap — a package would
  be a third key, not a rewrite.
- The two places that genuinely still carry one package's state now say so in their own docblocks
  as an accepted limit with a named extension point: `Pickup_Handler`'s single logical order-meta
  field, and the missing package dimension in the selection key.
- `woodev_checkout_pickup_slot_fields` is the boundary seam, deliberately without a consumer. A
  malformed filter return leaves the framework's own answer standing.
