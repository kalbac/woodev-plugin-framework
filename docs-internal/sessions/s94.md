## The stacked-PR mechanic, hit with the gotcha already written for it

Squash-merging #535 with `--delete-branch` removed the branch that was #537's BASE. GitHub closed
#537 on the spot, and neither recovery works:

```
gh pr reopen 537  → Could not open the pull request.
gh pr edit 537 --base main → Cannot change the base branch of a closed pull request.
```

Retargeting needs the PR open; reopening needs the base branch to exist. **A closed PR whose base
branch is gone is permanently closed.**

Recovery took one command — `git rebase --onto origin/main d966b00` — dropping the two #530 commits
the squash had absorbed, verified by the diff-stat against `main`, then a new PR (#543) carrying the
old body plus a comment on #537 pointing at it.

**This was already in `gotchas/stacked-pr-github-mechanics.md`, and I did not read it first.** The
session-start protocol says to scan the `[topic/*]` tags relevant to the task; merging a stacked PR
is squarely `[tooling/git-merge]`. The gotcha now carries the recovery path and the cheap
prevention (merge the base WITHOUT `--delete-branch`, retarget the downstream while it is still
open, delete the branch last).

## #541 — the cause was an asymmetry, not the queue

The operator had already named the reference: *«этот сценарий уже работает, если у региона тип
„Список с поиском“»*. Following that literally is what found it.

Under `ajax-select2` the record IS the pick — `resolveAndSelect()` looks it up in its own
`dataByKey` and calls `options.onSelect()` synchronously, so every piece of s90's busy/lock
machinery runs in the same tick as the click. Under `related-list` the region `<select>` is
WooCommerce's own and carries nothing but label text, so the renderer must match that text against
`GET /location/list` — **9.7 s cold on the rig** — before it has a record to hand over at all. For
all of that time nothing had been told a pick happened.

The seam is therefore a pick announced by **level**, not by record: `options.onResolving()` returns
a `release()` for the case where the identity never arrives. Optional exactly as `onAbandon` is;
`ajax-select2` neither needs nor calls it.

Descendant locking needed no new mechanism — `refreshDependentLocks()` already locks every level
deeper than the busy one. **That is why the marker must not be `queued`:** a queued marker means
"the request has not left, it confirms nothing" and `hasUnconfirmedParent()` ignores it on purpose,
whereas this one asserts what is true — the level's identity is unknown. Raising it as `queued`
shows the spinner and silently drops the lock, i.e. exactly the half of #541 the operator saw.

## #539 part 1 — and a frame that would have been worse than the defect

The rig measurement **corrected the card**: select2 does not replace the list while a query runs.
`showLoading()` PREPENDS its message and leaves the previous results below it, so the field went on
offering «Санкт-Петербург» and «Репино» for 9.6 s to someone who had typed «Пушк».

Narrowing the popular list locally fixes that. The near-miss: a term matching NO popular entry
narrows to `[]`, and select2 asks `language.noResults` for that render — so with the in-flight flag
raised after the narrowing, «Выборг» rendered «Поиск не дал результатов» **instantly, over a search
that had not been sent**. Same conflation #405 exists to prevent. → gotcha
`an-empty-list-while-the-search-runs-is-not-a-zero-result`.

**The test that could not see it.** The first version sampled `language.noResults` after
`transport()` returned, by which point the flag is `true` in both orderings — the probe stayed
GREEN across all 149 tests while the rig showed the defect plainly. select2 asks the hook DURING
the render (`selectWoo.full.js:3586-3600`), so the harness now asks it from inside `success`. Then
the probe goes red. Third time on this branch that a green suite hid a real defect.

The double `success()` was read out of the rig's own vendored `selectWoo.full.js` before being
relied on, not assumed.
