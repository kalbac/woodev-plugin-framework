## The unblock the session turned on — #510

Codex had been critic-only on the main checkout since s91, because its git died in every Orca
worktree. Measured in the first ten minutes: rewriting the worktree's `.git` file from an absolute
`gitdir: D:/…` to a relative one makes it readable by Linux git while Windows git keeps reporting
the same toplevel. That made Codex a full **worker** in a worktree for the first time, and four of
the session's cards were built by Codex workers.

Also measured, and the sharper half: **`git config worktree.useRelativePaths` is NOT the fix.** It
writes the relative gitdir AND an `extensions.relativeWorktrees` line into the shared repo config,
which git 2.43 refuses outright — taking the main checkout down with it. Unsetting the first does
not remove the second.

### …and the correction, same day

The gotcha as first written asserted "Codex under Orca runs in WSL" as a flat fact. The gotcha
`orca-terminal-command-bash-lands-in-wsl-on-windows` (s97) had already established the opposite and
still holds. The operator corrected it: **Orca's default terminal here is PowerShell, and Orca
decides where things land from his settings** — nothing should be hand-routed through `wsl`.

The accurate statement is two layers, not one: the TERMINAL Orca creates is PowerShell; the shell
**Codex's own tool calls** execute in is a Linux bash, which is where `/mnt/d/…` and the unreadable
gitdir come from. Worse than the wrong label was the consequence — the brief template hard-coded
`cd /mnt/d/Projects/…`, forcing the very shell that causes the problem. Rewritten to run from the
worktree root with no absolute prefix, so it survives a change of runtime setting. PR #679.

## The other correction — pace

Mid-session the operator stopped the wave: "то 1-2 воркера, то почти 10". Free RAM was down to
7.54 GB consumed, and Codex had taken 7 % of the weekly and 54 % of the five-hour allowance in one
sitting. Two things were wrong, and only one of them was the count:

- **Released workers were not being cleaned up.** Eight terminals and nine worktrees were alive at
  the peak while only two were doing work. Closing five terminals and removing seven worktrees
  returned **5 GB** of RAM by itself. Cleanup is not tidying — it is the capacity.
- A Codex terminal starts ~11 MCP servers, so an idle one is not cheap.

Standing shape afterwards: two workers, cleaned up the moment each `worker_done` lands.

## What the workers found that the coordinator would not have

- **#318** — the card proposed dropping response headers from the cache. The worker measured first
  and refused: a shipped Edostavka consumer reads `X-Current-Page`/`X-Total-*` from it. It kept
  non-secret headers and redacted the rest through the log's existing seam instead.
- **#147** — swept 15 guard sites across 7 files and traced each to its hook **against WooCommerce's
  own source**, concluding there is no live bug: `WC()->countries` and `WC()->shipping()` are
  unconditional in `WooCommerce::init()`. Verified independently from the rig container:
  `$this->countries = new WC_Countries();` is unconditional, `wc_load_cart()` is behind
  `is_request('frontend')`. The deliverable was nine docblocks, zero behaviour change.
- **#322** — swept 13 orderings and found the defect already fixed by #606; closed by measurement,
  not by a patch. Its side finding became #673.

## Measurements worth keeping

- **The isolation sweep beats seed-hunting.** #673 arrived with `--random-order-seed=2` as its
  repro; that seed is green on `main`. A seed shuffles the test SET the tree holds, and the tree had
  gained nine tests — so the same number is a different order. Running all **210** unit files one at
  a time found exactly **one** failure, the real one. Gotcha
  `a-random-order-seed-is-not-a-portable-repro`.
- **#499's fold was proved on real MySQL, not on the fake `wpdb` its unit tests use.** Rig probe:
  two rows (counts 7 and 5), `replace_record()` on the loser with the survivor's key → one row left,
  `order_count` 12, later `last_ordered_at` kept. Also confirmed the table and the server default
  are **InnoDB**; on MyISAM the transaction and `FOR UPDATE` would be silent no-ops and the fold
  would stop being atomic without a single error.
- **CI is the phpstan gate now.** Every brief said so: the repo is public, so Actions minutes are
  free, while locally phpstan needs `--memory-limit=4G` and several workers running it at once
  exhausts the machine. No PR suffered for it.

## Traps paid for again

- `worker-start --agent codex` failed on three of four launches (`agent_prompt_blocked`,
  `agent_readiness`, and one bare PowerShell terminal). The four-step recipe still applies; a
  retry needs an explicit `--worktree id:<…>` selector or it defaults to the coordinator's.
- A `check --wait` that exceeds the tool timeout is **backgrounded**, and a backgrounded waiter
  starves every later one. Keep windows under the limit.
- One Codex worker could not reach the `orca` CLI from its shell, and — reading its brief
  literally — did **no work at all** rather than work without being able to report. A brief must say
  the WORK is the deliverable and the lifecycle message is not a precondition for it.
