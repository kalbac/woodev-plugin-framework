## What shipped, round by round

### Round 1 — #824, the «Действие» column

The card carried a measurement and three open questions. Two of them dissolved against the code
before anything was built:

- **«Обновить» has no framework implementation, and cannot get one here.** In all three shipped
  plugins that verb means *pull the carrier's current state and sync the local status*
  (`WC_Edostavka_Shipping_Order::update_order()` fetches the remote order and its history; Почта's
  own title says «Force update order information like as delivery status»). Spec §D4 parks that sync
  in SP-8. So the framework ships the SEAM — `supports_update()` / `update()`, inert by default — and
  the button is not offered until a carrier overrides them. A dead button would have been worse than
  no button.
- **#860 had to be folded in.** The whole gate stands on the predicate «выгружен», and `EXISTS` on
  `carrier_order_id` counted a FAILED export (which writes an empty id) as exported. A failed export
  would have offered «Обновить/Отменить» instead of «Выгрузить».

Design settled before dispatch, so the workers would not each invent it: `Order_Actions::for_order()`
is the single declaration of the set — a pure «order + provider → available actions», no rendering
and no HTTP — because it must later feed the bulk actions and the metabox (#856) unchanged.

### Round 2 — the Codex critic's four findings

All four verified against the code by the coordinator before acting, and all four real:

1. **Double cancellation (HIGH).** `cancel()` changed no stored state, so «Отменить» stayed on the
   row and a destructive carrier cancellation could be sent twice. Fixed by clearing
   `carrier_order_id` on a successful cancel — which is what edostavka's own `is_exported()` does
   (false for `CANCELED`), and which #860's fix makes compose correctly: the cancel/update buttons
   go, «Выгрузить» returns.
2. **A replaced provider descriptor kept the previous carrier's handler (HIGH)** — the new carrier's
   buttons would have executed the old carrier's handler.
3. **A carrier's own declared action rendered and always 502'd (MEDIUM)** — the seam was advertised
   and non-functional; `dispatch_action()`'s default is now a real filter.
4. **A late action response could resurrect a row into a re-filtered table (MEDIUM).**

**Plus one the coordinator found reading the merged diff**, which is the most instructive of the
five: the row returned after a successful action was built from the same `WC_Order` instance the
action ran on. `Woodev_Order_Compatibility::update_order_meta()` branches — HPOS writes through
`$order->update_meta_data()`, the legacy CPT store calls `update_post_meta()` **around** the object.
So on a CPT shop a just-exported order came back with `is_exported` false and the pre-action buttons,
inviting a second export. **Invisible to a mocked unit test and invisible on the rig, which is HPOS.**

## The CI question, and what it turned out to be

The operator asked why nearly every PR had started going red. Measured over all 600 `ci.yml` runs,
first CI run per branch, dependabot excluded:

| week | green first try | red | rate |
|---|---|---|---|
| W35 (25–31.08) | 90 | 5 | **95%** |
| W36 (01–07.09) | 55 | 2 | **96%** |
| W37 (08–12.09) | 19 | **7** | **73%** |

The monthly average (94% → 89%) hid it. **Seven of the eight reds since 05.09 are two gate families,
both about generated artefacts** — the translation catalogue (#791 ×4, #771 ×1) and assets parity
(×3) — and they are the collision of two rules that are each correct alone: a worker in a worktree
must NOT build bundles, and `lint:i18n-sources`/`lint:i18n` extract msgids from `woodev/`, which
INCLUDES the built bundle. A Russian string added in a `.tsx` is invisible to every gate the worker
can run. Before SP-10 this rarely bit, because the work was mostly PHP, where the worker's gate and
CI's gate are the same gate.

**`.githooks/pre-push`** now rebuilds the bundles, asks the exact question the assets-parity job asks,
and runs the three catalogue gates **by exit code** — 18 s + 4 s, and only when the push touches
`src/` or `woodev/`. All four paths were exercised before committing. It fired for real on its own
first push. Card **#871**.

## What went wrong, and what it teaches

**Three of my own probes reported working features as broken.** In order: a `thead th` selector that
finds zero headers for every column (`TableCard` renders no `<thead>` — the header row lives inside
`<tbody>` with `role="columnheader"`); a wait on `tbody tr` satisfied by that same header row in the
loading skeleton, so the page was measured before a single data row existed; and a fixed 1.2 s/4 s
pause that caught the preview's spinner and read as «stuck loading» while the route was answering
200 with full data. **Suspect the check before the code** is in the handoff for a reason, and it cost
three rounds here anyway.

**A SCSS nesting bug that compiles silently.** `&--destructive` nested inside
`&__button.components-button.has-icon` expands to `…has-icon--destructive` — `&` is the whole
compound selector. Sass accepts it; the icon was simply not orange. Only the screenshot showed it.

**`tsc` caught what jest and the rig both passed.** `icon={ 'upload' }` is typed `IconType`, which a
bare string does not satisfy — rendered correctly at runtime the whole time.

**I pushed a red `lint:i18n` after reading `tail -3` of a `;`-chained run.** The failing lines had
scrolled past. Read the exit code. The pre-push hook now does exactly that, and its own first draft
died with `printf: --: invalid option` — a format string starting with `--` is read as an option —
which only surfaced because the refusal path was actually exercised.

**I confounded my own integration measurement** by starting a second run while the first was still
going, on the assumption it had hung. Two integration runs share one database; the log carried
`Lock wait timeout` and `Deadlock`, and the «1 error, 1 failure» was mine, not the code's.

## i18n: the s7 gotcha was half wrong, and now is not

The bulk messages need `_n()`, and the existing gotcha said to avoid `_n()` entirely because «there
is no ru_RU catalog, Russian IS the source». **That premise is dead** — the catalogue holds 864
entries and **14 plural entries were already relying on it**. Measured both states with `wp eval`
rather than reasoned:

| n | domain not loaded | loaded, ru_RU |
|---|---|---|
| 1 | 1 заказ | 1 заказ |
| 2 | 2 заказ**ов** ❌ | 2 заказ**а** ✅ |
| 21 | 21 заказ**ов** ❌ | 21 заказ ✅ |

So in **PHP** `_n()` is correct once the entry carries all three `msgstr` forms — and `make-pot`
emits only two, so the third is added by hand. In **JS** it can never be fixed: `wp_set_script_translations()`
is called nowhere and there is no `make-json` step, so `@wordpress/i18n`'s `_n()` always falls back to
its binary rule. The one live JS plural survives only because «для» takes the genitive and 2 and 5
inflect identically there — recorded in the function's own docblock, because rewording it would break
the string silently. Gotcha `russian-source-i18n-plural-n` rewritten.

⚠ The rig runs `WPLANG=en_US` deliberately, so these strings show the wrong form THERE. Not a defect.
