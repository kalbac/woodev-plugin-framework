## Why a framework 2.0.3

Both plugins vendored framework **2.0.1**, while `main` after the v2.0.2 tag carries #1332 (block-checkout pickup restore),
#1334–#1336, #1330, #1326, #1345, #1353 — the code the rig and the acceptance ran against. A ZIP from the v2.0.2 tag would
ship without them, and a ZIP from `main` would carry new code under an old version number. So: PR #1356 bumps
`Woodev_Plugin::VERSION` to 2.0.3 (+ `planned-release` 2.0.4, docs that name the released version). **Merging #1356
publishes the framework release (tag, ZIP) — the plugin release workflows fetch `woodev/` from tag `v2.0.3`, so it goes first.**

15-min timeout, concurrency; one script builds the ZIP locally and in Actions, refuses a framework/loader mismatch, and is
byte-reproducible.

## Lessons

- A shared brief spreads one design flaw to every worker: the release-trigger and README-in-ZIP mistakes came from the
  common brief; a terminal note to the still-running CDEK worker stopped half of it.
- A fix worker can silently undo an earlier round's decision (Yandex fix round 2 re-added README.md to the ZIP) — diff
  every fix round against ALL prior decisions, not only the newest findings.
- `npx run-local-ci` without `-y` hung on «Ok to proceed?» — already gotcha `run-local-ci-requires-run-subcommand` (s184 addition).
- Codex sol stopped on «Selected model is at capacity»; a `terminal send` «continue» resumed it.
