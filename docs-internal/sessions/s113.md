## What was done

### #736 — CLOSED (PR #740). The one real product defect, and it hid a second one

The card was right: `reconcile_pickup_declarations()` compared `Checkout_Config::pickup_method_ids()`
— a FLEET-wide list — against one handler's own declarations by set **equality**. Every carrier
legitimately declares only its own methods, so the check could never pass on a shop with two Woodev
plugins, and its message accused the plugin author of a defect that did not exist.

**The card's proposed fix does not work, and measuring that first is what saved the round.** It
suggested giving `pickup_method_ids()` a per-plugin filter. But `Shipping_Method::get_plugin()` is
`abstract protected` (unreachable from outside), and the handler's only identity is the constructor's
free-form `$hook_prefix`, which has no derivable relation to a plugin id — measured against both rig
fixtures: `woodev_realistic_shipping` vs plugin id `woodev-realistic-shipping` (underscores vs
dashes), and `woodev-test-shipping-method` vs its method id `woodev_test_shipping` (unrelated
entirely). Ownership cannot be inferred. So the check became **soundness** (every declared id must be
a member of the fleet truth) plus **agreement** (this handler's Pickup_Field list vs its explicit
backstop), which needs no ownership information and is exact.

**The second defect, which the card never named:** `$pickup_declarations_reconciled` was a single
process-static bool. Its docblock argued for it — "once per REQUEST, not once per handler" — and that
is right about the logging and wrong about the check: with two plugins only the FIRST handler built
in a request was ever reconciled, silently. The rig notice proved it empirically (it named the
realistic carrier's lists and had plainly never looked at the test carrier's). Now keyed by
`plugin_id()`, reset beside `$native_field_registry` — which was **already** keyed that way, ten
lines below. Gotcha
[a-process-static-once-per-request-gate-checks-only-the-first-plugin](../gotchas/a-process-static-once-per-request-gate-checks-only-the-first-plugin.md).

Rig-verified with a control: the notice sat in `debug.log` at 13:39 pre-fix; post-fix, after a
marker, a checkout render that demonstrably exercised the pickup layer (200, 290 KB, 5 pickup
markers) logged nothing.

### #474 — CLOSED (PR #739). Decided by measurement, against the card's own preference

`CURRENT-STATE` had already reclassified this as architectural — decide by measurement, do not ask.
The card offered two options and preferred option 1 (make `source_location()` and
`set_takeover_condition()` mutually exclusive, throwing `\LogicException`).

The measurement: `woodev/shipping-method/checkout/` holds **17 `_doing_it_wrong()` calls against
exactly one `throw`** — and that throw (`Checkout_Field_Settings::effective():211`) is a failed
lookup with nothing to return, not a builder-conflict report. Every conflicting builder configuration
in the layer is reported, never thrown. The layer's discipline is also explicitly reasoned in two
places: `class-checkout-handler.php:2469-2473` records a `_doing_it_wrong()` that was REMOVED because
it fired on a legitimate configuration and asserted a developer error nobody had made, and
`class-field.php:113` records one deliberately not added because the call is harmless.

So option 2: `Checkout_Fields::normalize()` drops `takeover_condition` on a location-source field and
reports it once. Option 1 would have been the first and only throw in the layer.

### #111 — CLOSED (PR #742). The two "candidate" files were not a pair

The s112 audit flagged both `woodev-payment-gateway-frontend.js` and `.css` as deletion candidates
and called the CSS a "paired asset, same reasoning". Measurement contradicted that half:

- The **JS is load-bearing** — the only definition of `window.Woodev_Payment_Form_Handler`, which
  `class-payment-gateway-payment-form.php:28` names as `$js_handler_base_class_name`. Deleting it
  would have removed the only copy of a class the payment form needs.
- The **CSS is genuinely unreferenced** by any PHP, and the paired style the enqueue actually asks
  for (`woodev-payment-gateway-payment-form.css`) exists and resolves. Deleted on the operator's call.

### #738 — filed and CLOSED the same day (PR #742)

Found while measuring #111. `enqueue_payment_form_assets()` builds the script src from `$handle`, so
it enqueues `woodev-payment-gateway-payment-form.js` — **a file that does not exist**. The CSS at the
same handle resolves; the JS 404s, and `localize_script()`'s params never attach either. Fixed by
pointing the src at the file that exists while KEEPING the handle (third parties may depend on it),
with a comment saying why the two no longer match.

**Latent, not an outage, and inherited rather than a v2 regression:** nothing in `plugins-reference/`
declares `FEATURE_PAYMENT_FORM`, so no shipped gateway reaches the path today — and shipped v1 has
the identical mismatch at `class-payment-gateway.php:406`.

### #163 — PR #743 open, HELD for the operator's rig pass

His fork, chosen from three: the anchor is the centre of the **initial viewport**, set once when the
picker opens, not following the map. Distance text and distance ORDERING are both live from the first
render (the card only named the text; `orderGroups()` returning `groups.slice()` on a null anchor was
the other half).

The live-map-centre reading of the spec was rejected on measurement: `boundsChange` is emitted on the
`viewport` strategy only, so `bulk` has no event to follow and "one rule, not two modes" would have
become exactly two.

The seam the worker added is a synchronous `getCenter()` on the provider, read once on the first
`visibleChange` — the one point where BOTH strategies have already settled their opening camera move,
which is what keeps the known async-camera trap out of it.

Rig-verified by the coordinator before handing it over: modal opened **without** a search shows 3
rows, distances rendered on all three (`1.0 mi`, `1.9 mi`, `1.9 mi`), ordered ascending. Control: the
same click on `main` showed 3 rows and no distances at all. The miles are the English rig locale, not
a defect (`ymaps-locale-region-drives-units`). NOT verified live: that dragging does not re-order —
pinned by jest only, and named as the one thing worth his eyes.

## Corrections the next morning — three of s113's own findings were wrong

The operator merged #743 himself, then asked what remained on #734/#737. Checking #734 to answer
him surfaced that it already contained a measurement contradicting mine, and pulling that thread
overturned three things this session had written down.

**1. `test-cdek` is not a fixture dictionary.** It is a client of the LIVE CDEK test contour
(`https://api.edu.cdek.ru/v2`, `API_BASE` in its own file). The grep that "proved" it knows only
Москва and Санкт-Петербург had matched comments and labels. Measured:
`suggest('Краснодар') -> 5 rows`, first is `test-cdek:435 Краснодар / Краснодарский край` — exactly
what #734 had already recorded and this session failed to read.

**2. The locality is gated by the REGION field, not by the record.** The region `<select>`'s option
VALUES are upper-case (`МОСКВА`, `КРАСНОДАРСКИЙ КРАЙ`). Writing `'Москва'` into `billing_state`
leaves the select EMPTY, the chain unresolved, and the request goes out with no `locality` at all.
`Location_Service::set_customer_record()` alone changes nothing, because the FIELDS drive the
request. Both of this session's failed attempts to reach Краснодар were this same self-inflicted
mismatch — the first blamed the record, the second blamed the WooCommerce session.

**3. #150 does not reproduce — CLOSED.** With a matching pair (`КРАСНОДАРСКИЙ КРАЙ` + `Краснодар`)
the modal fetched `?locality=Краснодар` and got exactly one point, the degenerate case the card is
about. **Tiles rendered fully — streets, house numbers, Yandex POIs, the marker, the copyright. No
grey.** `maxZoom: 18` plus `checkZoomRange: true` do work; the card had honestly flagged that as
unverified, and now it is verified. `_openPlacemarkBalloon()` was not exercised separately.

**#741 is closed as `not planned`** — it was filed on finding 1 and never had a real premise.

The gotcha was rewritten rather than deleted: it now leads with what was wrong in its first version,
because a gotcha that once said the opposite is exactly the kind a future session would trust.

⚠ **Restoring the rig took three attempts and the first two "verified" restores were false.**
