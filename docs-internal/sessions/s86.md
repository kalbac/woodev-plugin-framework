## The finding that reorganised the front

s85 left five checkout defects (#455, #457, #459, #460, plus the #449 harness) that read as five
independent bugs. **They are mostly one disease: the layer has two value spaces and writes across
them without translation.**

- `location-select-modes.js` put the PROVIDER KEY (`dadata:0c5b2444-…`) into the `<option>` value.
  That `<select>` carries the original input's `name` (`shipping_city`), so the provider key was
  what the checkout form submitted.
- `location-cascade.js`'s `fetchFor()` stamps the OTHER space onto every entry —
  `fieldValueFor( record, level )`, the bare component name — and `backwardsFill()` writes that
  into ancestor fields.
- Writing a value into a `<select>` that has no matching `<option>` selects **nothing**
  (`selectedIndex = -1`, `.value === ''`), so the field is dropped from the POST.

That single mechanism explains #455 (visible key), #447 (measured data loss), and #460 (the region
never persisted, so WooCommerce's `RU:*` default survived and the *rendered* field was empty for a
reason that had nothing to do with rendering). New gotcha:
`a-select-value-write-with-no-matching-option-submits-nothing`.

### The s85 white spot is closed

s85 could not find a server path writing the provider key into the rendered `input`, having
excluded usermeta, `wp_woocommerce_sessions` and the cascade store. **There is no server path —
the key never leaves the client.** The `<select>` *is* the field; select2's own selected
`<option>` carried `entry.key`, and #447's seeding derived the visible label from that value.
Consistent with every s85 measurement.

**Proved by execution, not argument:** the worker reverted only the source fix, reran, and
reproduced both `entry.key` leaking as the submitted value and the exact `TypeError` predicted
for #457.

## PR #461 — ajax-select2 value space (#455, #449, #457). OPEN, green, critic-cleared

Round 1 fixed all three. Codex **REJECTed** with two BLOCKING findings, both **proved by
invoking the renderer**:

1. `entry.value || entry.key` — a falsy fallback. An entry whose derived value is `''` fell
   straight back to the provider key, reintroducing #455 in the case hardest to notice.
2. `dataByKey` keyed by the submitted name — two same-named localities collided and a pick
   resolved to the WRONG record (persisting the wrong locality).

Round 2 separated the two concerns properly: the `<option>`'s submitted VALUE stays the field
value, while record identity moved to `entry.key`, resolved through select2's own
`select2:select` event (`e.params.data`). Empty-derived-value entries are now excluded from the
selectable set rather than given a fallback. `minimumInputLength` became per level (region 1,
others 2) since no universal invariant existed.

Re-critic: **APPROVE WITH NOTES** — both defects closed. Note: of the four new tests, the
second-pick control passes pre-fix; the first-pick and empty-value regressions genuinely fail.

**#449 is only half closed and the PR says so:** the returned handle's `abort()` marks a
superseded result stale (killing the blink) but does not cancel the underlying `fetch()`. Real
cancellation needs an AbortController threaded through `location-cascade.js`'s `options.fetch`.

## PR #462 — region survives a reload (#460). OPEN, green, critic-cleared

The worker **measured** the rig's live config and found region+settlement run in `ajax-select2`,
not the `related-list` my brief guessed — and said so. Root cause: `writeSilently()`'s bare
`el.value =` on a select-mode ancestor. Fix: `applyValueToElement()` matches an existing option
by value, then by text, and only otherwise appends a synthetic one.

Codex **REJECTed** on a finding I had asked it to look for and would not have caught myself: the
value-match branch changes `selectedIndex` without firing `change`, and **selectWoo only redraws
on `change`** — so the customer sees a stale widget while the form posts the restored value. It
also spotted that this becomes the *common* path the moment PR #461 lands, because #461 makes the
option values match the space this module writes.

Round 2 fires `$el.trigger( 'change.select2' )`. A namespaced trigger reaches only handlers whose
namespace is a superset, so it hits select2's listener and **never** this module's own
un-namespaced change gate — which matters because that gate runs a destructive cascade clear.
Verified against jQuery's own dispatch logic, not inferred. Synthetic options are now marked and
reused instead of accumulating.

Re-critic: **APPROVE**, no findings. It independently traced the full display path and confirmed
the subtle asymmetry — selectWoo's `childList: true, subtree: false` observer catches a freshly
appended option by itself, while a *reused* one needs the trigger.

## #459 — narrowed by measurement, still open

Worker B wrote an integration test it could not execute (no wp-env in a worktree — correct call).
**I ran it in the primary checkout: `OK (12 tests, 45 assertions)`.** It persists a settlement via
a real `/select` and reads it back through a fresh `Location_Service`.

It **passes**, so the chain does survive and the server does return it. The s85 handoff's guess
("the cascade does not restore records at bootstrap") is wrong twice over: `prefill()` →
`adoptChain()` restores deliberately, and the server really does supply the chain. #459 is
therefore **client-side**, and down to three places — the rendered config block not carrying
`chain`/`current`, `refreshAddressLock()` gating on something else, or a later re-lock via
`updated_checkout`.

## #458 — answered, and it is not what it looked like. Needs an operator decision

`shipping_` is **not** hardcoded in the framework. `Field::set_section()` is plugin-supplied,
`Checkout_Field_Policy` iterates `[ 'billing', 'shipping' ]` in two places, and
`location-cascade.js` is fully section-aware (`activeAddressSection()` reads the ship-to-different
checkbox). The three location fields are pinned to `shipping` **by the rig fixture**, deliberately,
so the location demo would not disturb the pre-existing billing demo.

The real gap is an asymmetry: `pickup/class-address-target.php` already encodes this exact rule
(`billing_only` → `billing`) and its docblock says outright that always writing `shipping_*`
"would write nowhere visible for merchants running `billing_only`, which is the recommended
configuration in Russia and the CIS". **The location module has no equivalent.** Fork posted to
the card: (a) warn when the chosen section is inert, or (b) derive the section as `Address_Target`
does. Recommended (b); it changes a public contract, so it waits for the operator. Card moved to
`Инбокс`.
