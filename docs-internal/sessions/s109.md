## #483 — the card's own diagnosis was wrong, and the mechanism matters

The card said `set_label()` "never reaches the markup". Measured on the rig instead:
`Checkout_Handler` *does* push the label into WC's field array, and the card's own server probe had
already confirmed `get_checkout_fields()` returns it. What actually happens is later and
client-side — WooCommerce's `assets/js/frontend/address-i18n.js` overwrites the rendered `<label>`
on `country_to_state_changing` from the country locale, and `get_country_locale()['default']`
carries a label for `state`, `city`, `address_1` and `postcode`:

```
default.state     label=State / County
default.city      label=Town / City
default.address_1 label=Street address
RU.*  -> no label key at all
```

Those are exactly the three labels the card observed. **A final-DOM reading cannot tell "never
rendered" from "rendered and then replaced"** — that distinction is the whole finding. It also
strengthens the operator's variant A: a framework label would compete not only with a shop's own
rename but with WooCommerce's own locale system.

The existing `wc-address-i18n-reshows-fields-with-an-inline-display-block` gotcha was EXTENDED
rather than duplicated — same handler, same schedule, one branch apart.

## The rig session — what he found, and what it changed

### The phone mask was unusable, and the fix was two decisions, not one

He turned #503's mask on and it fell apart: it masked `billing_phone` only (`shipping_phone` is
real on WC 11.0.1 — measured), and typing `8` produced `+7 (8`, typing `8800` produced
`+7 (777) 008-8`. *«Полная каша. Полем пользоваться не возможно.»*

He named the fork — take a library or rewrite ours — and asked me to go and look. Two separate
questions came out of it, and they have different answers:

**Who owns the input mechanics.** IMask, vendored. Caret after a backspace mid-number, overtyping a
selection, paste — the exact things the hand-rolled version got wrong, and the reason mask
libraries exist. 15.8 KB gzip against Inputmask's 55.2.

**Who owns the per-country format.** He sharpened the requirement mid-session: the mask must match
the country's real structure, prefix AND digit count. *«не допустимо, например "+998(925)123-45-67"
тут строка не подходит не по её началу не по количеству символов.»*

That second requirement was already broken, and the check found it:

```
TM   '+993 # ######'  = 7 national digits
     real               8
```

**Eleven of twelve hand-typed templates were right; the twelfth made every Turkmen number
impossible to enter.** Written by one agent, reviewed by me, country list approved by him — and
still wrong, because a table of formats is a table of facts about the outside world and reading it
carefully proves nothing.

So the table is generated now (`bin/generate-phone-masks.mjs`) from libphonenumber metadata at DEV
time, and libphonenumber stays a devDependency: 44.5 KB gzip of data about ~240 countries has no
business in a browser answering twelve questions. Decision and the measured sizes: **ADR-011**.

One measurement is worth carrying because it inverted my own recommendation twice in one session.
`AsYouType('RU')` returns `8 (929) 600-80-90` nationally and `+7 929 600 80 90` internationally —
neither is the `+7 (929) 600-80-90` he asked for. I first read that as "presets are useless here",
which was right about *formatting* and wrong about *structure*. His clarification («не принципиально
"+7" или просто "8"») separated the two, and the answer became: take the structure, override the
cosmetics, and let the generator refuse any override that changes a digit count.

### Two admin defects, and one of my own fixes causing the second

**Tooltip icons jumped on checkbox rows.** The cause was deliberate — `_field.scss` pins the tip to
the label column for a normal field and leaves it inline for a toggle. He named the two acceptable
fixes and picked "make the checkbox behave like any other control", so boolean rows now join the
same grid.

**Then I broke the alignment again in the fix for it.** He asked for a 200px label column; I applied
it to the boolean row only and left the ordinary field grid on the 182px token, so the two columns
stopped matching — the exact misalignment the change existed to remove. It is one
`$settings-label-col` read by both grids now. A width that two selectors must agree on is one
number or it is a bug waiting.

**Grouped blocks needed an exception**, which he had to tell me: `.woodev-field__option-group` is
its own bordered card with no label column to line up with.
