## #551 round 1 — green, falsified, CI-clean, and completely wrong

The fix derived the region via `resolve_key()`. Six tests, **each falsified**. `composer check`
2826/6913/66. Nineteen green CI jobs. Rig-measured by the coordinator before handing it over:

```
region key=test-cdek:r482  label=Галисия      <-- Spain. Should be Москва.
```

`resolve_key()` returned the SAME wrong region for two different keys. Shipping it would have been
worse than the bug: `within=test-cdek:r482` scopes every search to Galicia.

The code was fine. The provider was broken — and the unit tests mocked the provider, so the mock
encoded the exact assumption under test. Gotcha:
`a-mocked-provider-proves-the-mock-not-the-contract`.

## The operator corrected the root cause, and the correction mattered

The coordinator wrote «CDEK ignores the `region_code` filter». **Wrong.** From CDEK's docs:
`/v2/location/regions` has **no `region_code` parameter at all** — only `country_codes`,
`fias_region_guid` (deprecated), `size` (default 1000), `page`, `lang`. `region_code` belongs to
`/location/cities`. The API behaves correctly; the fixture sends a parameter that does not exist, it
is dropped, and `$rows[0]` of an unfiltered 1000-row page is Галисия.

That reframing was not cosmetic — it changed the fix from "work around a flaky upstream" to "stop
inventing a parameter and use the call that already works in this same file".

Worse, the false claim was **written into a docblock as fact and a capability declared on it**:

> both `/location/regions?region_code=` and `/location/cities?code=` are exact single-row lookups
> […] so no scope/country hint is needed

Half true, half inferred by symmetry — and that sentence closed the question for three rounds of
#488 critics and for this coordinator. Gotcha:
`the-fixture-docblock-asserted-an-api-parameter-that-does-not-exist`.

The correction was pushed to the running worker mid-task, and the #553 card body was amended so
nobody inherits the wrong cause.

## Round 2, and the guard that outlives it

`resolve_region()` now searches the same per-country dictionary `regions()`/`list_localities()`
already trust. The derivation prefers `CAPABILITY_LIST` (measured correct) with `resolve_key()` as
fallback — the round-1 rationale (DaData never declares LIST) still holds, so this is a fallback
chain, not a swap. And regardless of path:

```php
// Never surface a region the settlement does not actually descend from.
return null !== $region && in_array( $region->key(), $ancestors, true ) ? $region : null;
```

That line rejects Галисия on its own, with no test and no working provider.

**Re-measured independently with the coordinator's OWN probe**, not the worker's — round 1 had also
reported success:

```
region key=test-cdek:r81  label=Москва
resolve_key(test-cdek:r81) => Москва ; resolve_key(test-cdek:r82) => Санкт-Петербург
```

No separate critic was run, deliberately: round 1 was code-clean and still wrong, so a reviewer
reading code would not have caught it. The rig measurement would, and did.
