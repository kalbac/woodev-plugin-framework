## #352 — mixed provider chain

The rig runs `test-cdek` for region+settlement and the bundled DaData for address. Picking an
address destroyed the settlement record: `rebuild_chain()` keeps a shallower record only when the
new one PROVES kinship, and `parse_ancestors()` requires every ancestor to share the record's own
provider — so cross-provider kinship is unprovable in principle. The settlement key went, and with
it the search scope and the pickup point's filing key.

Operator's variant A: a foreign address record never enters the chain, the address lives as field
TEXT only. Rule #334 untouched.

**The critic caught my over-generalisation.** I widened his rule from "an address from a provider
that does not own the settlement level" to "a record whose provider does not own every level above
it". Codex produced the configuration that breaks: active provider serving only `region`, DaData
serving settlement+address. There the broad rule refused the SETTLEMENT pick itself, so no
settlement record was ever stored and the pickup point could never be filed — strictly worse than
the unfixed code. Narrowed to the operator's own words: the settlement level is the anchor,
refusal only applies to levels deeper than it. A regression test guards against re-broadening.

## #350 — a settlement typed without picking

The customer types a city and leaves without picking. No settlement record exists, so #337 locks
the address field — and for a town the provider does not carry there is no way out, because there
will never be a suggestion to pick.

Two things had to be BUILT before the operator's rule could even be expressed: the widget had no
commit concept at all (`handleBlur()` was a bare `closeListbox()`) and no state separating
"completed with zero rows" from "still in flight" — `items === []` meant both, and `closeListbox()`
wiped it before blur could read it.

Operator ruled mid-implementation that the customer's descendant TEXT must survive an unresolvable
settlement, which turned a pinned-observation test into a real behaviour change: `clearDescendants()`
now snapshots what it wipes and an abandon restores it — only into fields still empty, so a value
the customer typed during the wait always wins, and a real pick discards the snapshot so changing
city still clears the old address.

## #346 + #333 — one gate, not two fixes

Measured first, as both cards demanded.

- **#346** reproduced, and the card's premise was found WRONG: it claims
  `Location_Provider_Registry::reset_for_tests()` is "the only reset", but that method only removes
  hooks and nulls a singleton. There is no server-side forget path of any kind.
- **#333**'s open question ("пусто? мусор? ошибка?") has an answer: none of the three. A foreign
  key still scoped the search — 8 results against 10 for the control — because DaData sees the
  foreign `provider_id`, refuses its `raw` payload and silently degrades to a text constraint on
  the region/city names. It only "works" by accident of the handover shape.
- A key that is not in the chain at all is discarded silently: `within=nosuchprovider:zzzz` gave
  the identical 10 results as no `within`.

Gate: a record is stale when the D15 chain no longer resolves its own level to its own provider, or
when its country no longer matches the customer's. Cascade-ordered, so a dropped ancestor takes its
descendants with it. Never writes. The country authority is call-site aware — REST passes the
request's own country, because ambient `WC()->customer` is unreliable there.

**The critic's three P0s were all real and all verified by me against the code:** the lazy default
bypassed its own gate while the docblock two lines above promised it did not; `gate_chain()` could
keep an address after dropping its settlement; and `within_status: not_requested` was returned even
when `within` had been sent. The second error of mine this session was the docblock claiming the
gate makes a foreign-provider parent "structurally impossible" — it does not, because the region
level is optional, so a carrier may own settlement while DaData owns region. Filed as #358 with
both measured outcomes, so nobody "fixes" it by banning cross-provider scopes and destroys the case
that works.

## Decisions recorded

- **«Основной» (DaData) is about ORIGIN, not arbitration** — bundled and always reachable as a
  fallback; the selected provider still wins any level it serves. The naming differs from the
  code's; the behaviour is identical to what is built. No change follows.
- **«Заблокирована и всё» is an EXCEPTION, not a project rule.** The operator narrowed his own
  remark twice; the second time explicitly. The default is to EXPLAIN a blocked control.
  `refreshAddressLock()` had generalised it into "the same standing operator rule" — corrected.

  abandon path.

## How the work went

Subagent-driven at the operator's instruction: Sonnet workers, Codex as critic. Three critic runs,
three BLOCKs, every one of them justified. The pattern worth keeping: the critic found operator-rule
misreadings that no test could have caught, because the tests encoded the same misreading.

Two verification near-misses worth remembering. A `perl -0pi` mutation silently matched nothing on
this CRLF tree and exited 0 — the suite came back green and would have been reported as "the tests
are vacuous" had the mutation not been grepped back. And the first #346 measurement was taken on
`AM`, where the layer serves no address level at all, so the address field reads unlocked
regardless — the claim would have been "confirmed" by a measurement incapable of testing it.

CI caught one thing four local suites could not: `ReflectionProperty::setValue()` on a private
property needs `setAccessible( true )` below PHP 8.1, so a new test errored on the 7.4 and 8.0 legs
while passing locally on 8.1.
