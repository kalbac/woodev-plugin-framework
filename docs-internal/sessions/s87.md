## The merge train, and the trap in it

The s86 stack merged in the order the handoff named: **#461 → #462 → #464 → #467 → #468**, then #456
closed as absorbed (its commits are inside #461).

**The last three went `DIRTY` the moment #462 landed.** All five had base `main` and all five reported
`CLEAN` with 18 jobs green — but they were clean against the *un-squashed* `main`. #464, #467 and #468
were branched off the **rig aggregate branch** `rig/s86-checkout-fixes`, so each carried the rig MERGE
commits for the PRs ahead of it; once those PRs landed as squash commits, the three-way merge could no
longer be computed. And a `CONFLICTING` PR runs no `pull_request` CI at all, so the green it was
showing was about a commit that no longer existed.

Fix, per PR: `git rebase --onto origin/main <the rig merge commit it sits on>`, force-push, wait for
the fresh CI matrix, merge. Recorded as Symptom 4 in `gotchas/stacked-pr-github-mechanics.md`, with
the cheaper alternative for next time (cherry-pick the rig branch, or keep PR branches off `main`
directly — nothing requires them to descend from the rig branch).

One CI failure on the way was **not** ours: all three integration jobs died on
`HTTP/2 504` from `api.github.com` while composer pulled phpunit inside the wp-env docker build.
`gh run rerun --failed` cleared it.

**Correction to my own opening read:** I reported the s86 docs as unpushed. They were already on
`origin/main` — I had compared against a stale local `main`.

## #466 — the headline: it was never the network, and never WooCommerce

s86 left #466 with both leads dead and the next step named as "a browser network timeline, not more
reading". That was the right instruction and it paid immediately.

Instrumented the rig in a real browser: the renderer registry, every widget's `detach()`, and every
DOM-mutating jQuery method, each with a stack. The timeline:

```
t= 126  ATTACH  shipping_city  ajax-select2  INPUT -> SELECT   (location-cascade.js, on boot)
t= 227  replaceWith #shipping_city
            at ensureText     (checkout-field-classic.js:497)
            at applyTakeover  (checkout-field-classic.js:517)
            at                (checkout-field-classic.js:598)  <- runTakeover()
t=5981  updated_checkout -> reconcileAfterCheckoutUpdate() puts the widget back
```

**Our own §8 adapter destroyed it.** `runTakeover()` walks EVERY field in the store, and
`applyTakeover()` reads "not a takeover field for this country" as "revert to a text input". A
`source_kind === 'location'` field is never a takeover field, so that revert branch was the *only*
thing the adapter ever did to one.

The apparent 3–13 s delay is the length of the FIRST `update_order_review` — the next event that makes
the cascade reconcile. Confirmed by coincidence: in one run the field re-attached at 41480 ms while
that request completed at 41467 ms, 13 ms apart. **The 2.5× spread that made it look like a network
problem was the network — just not ours, and not the cause.**

The region survived only because `isWcManagedField()` matches `/(^|_)state$/` — a NAME heuristic.
`shipping_address_1` survived for a third, unrelated reason (`ensureText()` returns early on a
non-`<select>`). Exactly one field in the layer was exposed, and it was the one with no protective
suffix. **The asymmetry everyone read as "attach timing" was an asymmetry in what got DESTROYED.**

→ **PR #471**, guard by ownership (`store.getField( id ).source_kind`), not by name. Rig-verified:
both fields select2-backed by t=244 ms, no revert, address lock intact. The three regression tests
were checked by DISABLING the guard and re-running, not by reading. Gotcha:
`the-classic-adapter-reverts-a-select-the-location-cascade-owns`.

## The wave — two Sonnet workers, three Codex critics, all critic-only

### PR #470 (#463) — related-list settlement value space. Worker B, one round.

Mirrored #455: `listFor()` in `location-cascade.js` as the `/location/list` analog of `fetchFor()`,
same live scoping and the same `fieldValueFor()` stamping; `attachRelatedListSettlement()` consumes
`options.list` instead of hand-building the URL. No PHP change — `/suggest` and `/list` already share
`to_response_records()`.

Codex: **APPROVE**, itemised across all seven checkpoints, five of them by execution. The strongest:
it invoked the real renderer with two entries both submitting `Alexandrovka` under different keys,
picked the second, and got the second record back — the collision case a critic proved wrong in #461
round 1. Coverage note accepted: the new tests do not assert `.select2-selection__rendered`, but this
patch populates options before widget init and never touches the render/cache path (#467's territory).

Honest gap: the worker did NOT reproduce on the live rig. Doing so needs BOTH axes switched to
related-list and possibly a provider change — `get_field_mode_settlement()` clamps by provider
capability and by the region axis (the #404 cross-axis condition). Left for the operator's pass.

### PR #472 (#458) — the cascade attaches per `woocommerce_ship_to_destination`. Worker A, two rounds.

`Checkout_Handler::effective_fields()` fans a `source_location()` field into `billing_*`/`shipping_*`
(or `billing_*` alone under `billing_only`); `inject()`, `sanitize_posted_data()`, `validate()`,
`save()`, `handle_checkout_get_value()`, `guard_native_field_conflicts()` and the `Checkout_Config`
payload all key off that set. The rig fixture stopped pinning its three demo fields to `shipping`.

**Round 1 was sent back for having no tests at all.** Its own gate numbers were the finding: 2599
tests / 6374 assertions and jest 1318 — byte-identical to the pre-change baseline, for a 237-line
change to a framework contract. Round 2 added six PHP tests and two JS tests and verified each by
reverting the production line and re-running.

**The rig measurement I took on the combined branch is the part that matters.** With
`woocommerce_ship_to_destination = shipping` — i.e. Rule 7b says BOTH columns — billing received the
location layer at the **address level only**:

```
billing_state      -> options   (the old §8 demo)      billing_city -> suggest (ditto)
billing_address_1  -> location / address
shipping_state / shipping_city / shipping_address_1 -> location
```

`effective_fields()` assigns a non-location field directly but merges location variants with `+=`, so
an explicitly declared field always beats a fanned-out variant, in either declaration order —
**silently**. That is exactly how s86 lost the s44 decision: a rule nobody enforces quietly stops
applying.

Codex **REJECTed it**, with two HIGH blockers, both reproduced by execution:

1. **After the live «ship to a different address» toggle, NEITHER column has the cascade widget.**
   `activeAddressSection()` is evaluated only while `buildChain()` builds `entry.chain`; the change
   handler then re-runs `applyCountryArbitration()` over that FROZEN chain, detaches the shipping
   widget and has no billing node to attach. The critic drove the real module with a recording fake
   typeahead: one attachment (`shipping_city`, `detached=false`) → uncheck → same attachment
   `detached=true`, `billing_city` never attached. One click, and the layer is gone.
2. **An existing declaration silently suppresses a fanned variant** — my inference confirmed by a
   two-order runtime probe. No diagnostic anywhere.

It also cleared what I most feared: **no installed-data-contract loss.** The executed shipping-only
pipeline produced `{billing_address_1:"", shipping_address_1:"test"}`, our `validate()` returned
`true`, and a spy on `save()` recorded no plugin-meta writes — both ids are native, and WooCommerce
still owns native-address persistence. `guard_native_field_conflicts()` called `_doing_it_wrong` zero
times.

**One number needed checking rather than believing.** The critic reported 2605 tests / **6662
assertions / 1 skipped** and flagged it as contradicting the PR's claimed 6389/66. I ran it myself in
the primary checkout on the combined branch and got exactly **2605 / 6389 / 66** — the worker's
figures. The test count agrees across all three of us; only the skips differ, so the critic's
worktree executed 65 tests the primary skips. That is an ENVIRONMENT difference, not a false report —
and it is the documented worktree-skip trap pointing the other way: we watch for a worktree that
skips MORE, and this one skipped fewer.

**Round 3 dispatched** with a narrow scope: re-evaluate the section tie-break on the toggle so the
ACTIVE column always has a widget, and make the collision non-silent with a documented precedence.
Full simultaneous dual-cascade is explicitly OUT — it is an architecture-and-product fork (one
location record per customer or one per column? which one drives pickup and rates?), filed as **#475**
in `Инбокс` for the operator. This is the third round, which is the cap; a fourth would need
decomposition or his decision, not another lap.

## How the work went

- **The operator's own instruction from s86 — "a browser network timeline, not more reading" — was
  worth more than any amount of further code reading.** Two workers had already failed to reproduce
  #466 in jsdom, correctly, because `ensureText()` only bites a field that is already a `<select>`
  and jsdom has no real select2. The stack trace found the culprit in one pass.
- **A measurement without a control is worth nothing, and that cuts both ways.** #459 was proven with
  its negative half; #466's fix was proven by disabling the guard; #473's sink was proven by driving
  it; and the one thing I could NOT control for — the live path that empties the select — is exactly
  what keeps #473 a separate card instead of a fix.
- **Sending round 1 of #472 back for tests was the right call and cost one lap.** The gate numbers
  being byte-identical to the baseline is a cheap, mechanical tell that no test was added; worth
  checking on every worker report.
- **Feeding a critic a measurement mid-run works.** The #472 critic picked up the rig dump from a file
  in its worktree and came back having confirmed both of my probes by execution — and then found the
  toggle path, which I had not.
- **Codex's `worker_done` dies when `dispatch --inject` reports `ok:false`.** The brief has to tell
  the critic to print its verdict in the terminal and not to retry the send. Recorded as an amendment
  to `gotchas/dispatch-inject-reports-failure-after-succeeding.md`.

### A defect found on the way, and correctly NOT fixed

First pick of a region leaves the settlement list **empty**: the request goes out unscoped
(`?level=settlement&country=RU`, no `within`), because the scope is read from the persisted chain
and `/location/select` — 4.3 s on this rig — has not landed yet. CDEK deliberately answers an
unscoped settlement scope with `[]`.

**Not a #470 regression** — checked the pre-fix code at `69187e2`, same `options.parentKey()`-if-truthy
shape. Filed as #478 and then closed as **superseded by #437**, whose decision 1 deletes the
settlement `related-list` mode outright. Fixing a race in code with a delete date is waste.

Also seen live, and it is #437's own argument: the scoped list returned exactly **500** =
`LIST_HARD_CAP`. Novosibirsk oblast silently truncated, and the client drops the `truncated` flag.

### #475 settled, and the migration clause dropped

His decision: **(A) — one live cascade that follows the active column.** Recorded as
`AGENT-RULES.md` **Rule 7c** with the rejected alternative and its price, plus five `file:line`
citations proving that `woocommerce_ship_to_destination` never picks the column — the live checkbox
does, and the option only decides whether the checkbox exists (`billing_only`) or what it defaults
to.

He then challenged the spec's "the stored value migrates to search": why, with no live consumers?
**He was right, and the stronger reason is in the code:** `get_field_mode_settlement()` already
clamps on read — `in_array( $stored, $offered, true ) ? $stored : MODE_TYPEAHEAD` — so the empty
field the clause guarded against cannot occur. What is left is a one-line choice inside that clamp,
for whoever writes #437. Amended into the spec so it does not re-assert itself.
