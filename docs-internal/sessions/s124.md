## #813 — четыре порядка объявления, замеренные на риге

Зонд с четырьмя подклассами, отличающимися ТОЛЬКО местом объявления (WooCommerce 11.1.0):

| | объявление | до | после |
|---|---|---|---|
| A | `$this->supports = [ … ]` до `parent::__construct()` | флаг ✓ / контрол ✓ | ✓ / ✓ |
| B | `add_support( BOX_PACKING )` после конструктора | флаг ✓ / **контрол ✗** | ✓ / ✓ |
| C | `add_support( BOX_PACKING )` до конструктора | флаг ✓ / контрол ✓ | ✓ / ✓ |
| D | `add_support( SHIPPING_CLASSES )` после конструктора | флаг ✓ / **контрол ✗** | ✓ / ✓ |

**D — та самая фича, которую доки называют поимённо** (`docs/shipping-method.md:1040`:
«`FEATURE_SHIPPING_CLASSES` — opt-in via `add_support()`»). То есть документированный путь вёл в
тупик, и автор нового плагина (#786) пришёл бы туда первым же действием.

Починка: `add_support()` перезапускает `init_form_fields()`, когда добавленная фича — одна из двух,
формирующих форму (`FORM_SHAPING_FEATURES`), и только если форма уже была построена. Проверено по
исходнику WooCommerce, что `get_instance_option()` падает на дефолт поля для ключа, которого нет в
`instance_settings`, — на этом допущении держится вся починка.

### Что нашёл критик, и что из этого подтвердилось своим замером

1. **Реэнтерабельность — ПОДТВЕРЖДЕНО.** Колбэк фильтра `..._form_fields`, зовущий `add_support()`,
   заново входит в `init_form_fields()`; внутренний проход строит контрол, а внешний затем
   присваивает поверх свой массив, собранный ДО появления фичи. Итог — фича объявлена, контрола
   нет: дефект #813 с другой стороны. Это **не регрессия** (до починки контрола не было и так), а
   случай, который починка обязана покрывать, иначе она верна только для объявлений вне фильтра.
   Починено флагом реэнтерабельности: сеттер помечает перестройку отложенной, а проход, который
   владеет формой, переделывает себя один раз после присваивания. Завершается: у второго прохода
   фича уже объявлена, а формирующих форму фич всего две.
2. **Загрязнение реестра — ПОДТВЕРЖДЕНО, и это была МОЯ ошибка в тесте.** Первый черновик теста
   объявлял три зондовых подкласса. `Shipping_Method::__construct()` зовёт
   `set_shipping_method()`, поэтому каждый оставлял в приватном `$methods` синглтона запись под id,
   который `add_shipping_method()` никогда не регистрировал, — то есть **без ключа `class_name`**,
   который `get_shipping_method_class_names()` читает без защиты, а `get_shipping_method_ids()`
   отдаёт боевому коду (`admin/class-shipping-admin-order.php:486`).

   ⚠ **Полная сьюта при этом была ЗЕЛЁНОЙ** — просто ни один тест сегодня не ходит по этим путям.
   Ровно тот сорт зелёного, который перестаёт быть зелёным потом.

   Переписано на существующую фикстуру: `Woodev_Test_Shipping_Method` объявляет `BOX_PACKING` и НЕ
   объявляет `SHIPPING_CLASSES`, поэтому `add_support()` на построенном экземпляре проходит ровно
   по починенному пути. Плюс тест, прибивающий, что реестр не тронут. **Сначала перебрать
   существующие фикстуры, потом заводить свою** — правило было, я его нарушил, критик и свой же
   разбор поймали.

### Что критик СНЯЛ (полезно не меньше)

- Гвард `! empty( $instance_form_fields )` не обойти пустым `get_method_form_fields()` — база
  всегда кладёт `title` и `description`.
- Один вызов массивом перестраивает ОДИН раз и после добавления всех фич; повтор уже объявленной —
  ноль перестроек.
- `get_shipping_classes()` мемоизирует свой единственный `get_terms()`, поэтому починка добавляет
  **ноль** запросов к БД.

## #814 — карточка называла не тот рычаг

Карточка просила добавить два маппинга `wp-content/plugins/…` в `env.tests`. Сверка по коду до
реализации:

- `tests/bootstrap.php:210` грузит фикстуры **`require_once`'ом из монтирования `woodev-framework: .`**,
  а не из `wp-content/plugins`;
- обе фикстуры находят фреймворк через `WOODEV_FRAMEWORK_DIR`.

Значит предложенные маппинги обслуживают **риг**, а к интеграции отношения не имеют. Нужно было
другое, и в таком порядке:

1. **`require_once` в `tests/bootstrap.php`** — фикстура не грузится сама. Карточка про это не
   говорила вовсе.
2. **Зеркало `…/woodev-realistic-shipping-plugin/woodev`**, какое уже есть у трёх других фикстур.

⚠ **Сделать только (1) — и падение непропорционально причине.** `Framework_Resolver::load_plugins()`
требует `<plugin_path>/woodev/class-plugin.php` у того плагина, до которого дойдёт ПЕРВЫМ (гвард
`class_exists( '\Woodev_Plugin', false )`). Одна незамапленная фикстура кладёт ВСЮ сьюту ещё до
первого теста, и сообщение называет `class-plugin.php` — читается как сломанный `vendor`. Три
правильно замапленные соседки не спасают.

Карточка требовала мерить радиус до решения («часть тестов считает зарегистрированные методы»).
**Замерено: 156 → 163 теста, ни один существующий не потревожен.** Опасение не подтвердилось, но
проверять было правильно.

Маппинг — bind mount, поэтому нужен `npx wp-env start`. Снимок рига до и diff после: **байт в байт**
(опции, 11 строк popular-settlements, пять инстансов методов в зонах, активные плагины,
`zz-rig-yandex-key`), префикс контейнеров не изменился — документированная команда `docker exec …
-tests-cli-1` продолжает работать.

Новые тесты утверждают только то, на что способен НАСТОЯЩИЙ `WC_Shipping_Method`: общая абстрактная
база не схлопывает два метода в один id, курьер и ПВЗ расходятся по типу доставки и
`is_pickup_shipping()` следует за каждым, обе строят настоящую форму настроек, ни одна не объявляет
формирующую фичу, и **починка #813 держится на уровень наследования глубже, чем её прибили** — то
есть на том уровне, на котором будет написан #786.

## #815 — заведена замером

`add_support()` до `parent::__construct()` шлёт экшен с **ПУСТЫМ id метода**
(`woodev_shipping_method__supports_box_packing`), потому что `$this->id` присваивается строкой
позже. Имя общее для всех методов, написанных в таком порядке. Побочно там же выживает вуковский
дефолт `'settings'`, что отменяет намеренное поведение #811. Достижимость низкая (после #813 у этого
порядка не осталось источника, который бы его рекомендовал) — отсюда «Потом», а не «Сейчас».
