## Three measurements that killed three hypotheses

**1. #502's own hypothesis was wrong, and so was the framing of the card.** The card guessed the
`! isNodeActive()` guard opened the address field because the active provider does not serve
`address`. Measured: `levels.RU.address` is `true` — `get_levels_for_country()` walks the D15 chain
and reaches the DaData fallback honestly — so that guard never fired. A control run with `dadata` on
every level behaved identically, so the mixed provider chain is neither cause nor condition.

The real differentiator was `default_locality_policy`: with `off` the address locked correctly, with
`fixed` it did not. The store seeds a settlement record the customer never picked and flags the chain
`implicit`; `prefill()` adopted it like any restored record and the lock lifted. **Neither settlement
renderer writes a seeded record's text**, so the customer saw an empty НП field beside a live address
field — the reported symptom exactly. Spec §4.6/D11 already settles it: *"Implicit records participate
in rate calculation but never suppress 'please choose your locality' prompts."*

**2. `main`'s unit baseline was 2701, not the 2718 every handoff had been quoting.** Found by a critic
reconciling numbers it did not believe. Every brief I wrote that night carried the stale figure.

**3. The #505 PR could not run CI because it was `DIRTY`, not because of a queue stall.** The
re-critic measured that CI had never run on either round-2 commit and correctly ruled out a global
stall — but the cause is only visible from the PR's own `mergeStateStatus`. GitHub cannot build the
merge commit a `pull_request` event needs while the branch conflicts with `main`, so no CI workflow
was ever scheduled, and "Assets build parity" had last verified a pre-fix tree.

## The critic rejected my own fix, and was right

I wrote #502's fix, rig-verified it before and after, ran a real settlement pick end to end, and had
1384 green jest tests. Then an Opus critic rejected it:

> The premise is false. The route persists explicitly, yes — but the `chain` it answers with is NOT
> the thing it just persisted.

`Location_Service::get_customer_chain()` is itself the **lazy trigger for the default-locality
policy**. So a D7 `cancelled` response (which deliberately writes nothing before reading the chain)
and any `persisted: false` response (a guest with no cart cookie) both hand the client the merchant's
default guess — and both `adoptChain()` call sites stamped it explicit. **#502 re-opened one click
after my fix produced the correct state.** The server never published `implicit` on that route at all,
so the client was structurally unable to tell them apart. Round 2 added the key to both response
shapes and passed it at both call sites.

**And the critic's own worked scenario had a wrong step.** It numbered the reachable path as a cancel
of the *settlement* pick; `handleCancelledSelect()` calls `clearChainField()`, which nulls
`entry.records[ level ]`, so a cancelled settlement re-locks the address whatever the flag says. I
found that by writing the control for that shape first and being unable to make it unlock. The finding
is real one level down. Recorded next to the tests so nobody chases the wrong sequence.

## D6 of the tools spec, settled by measurement

The spec deliberately left the registration seam open: a filter (WC's idiom) or a method on a registry
(this codebase's). Measured: `Location_Provider_Registry` — the closest analogue, because contributors
are *independent, uncoordinated plugins* — uses a filter carrying **typed instances**, `instanceof`-checked
with `_doing_it_wrong()` and one bad entry not poisoning the rest. `Map_Provider_Registry::register()` is
a public typed method, but that registry has exactly one caller. Tools come from independent parties, so
the filter shape won, carrying typed `Shipping_Tool` objects.
