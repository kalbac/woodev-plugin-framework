## Verdict

- **Mass limits for the spec §4.2 table:** ONLINE_PARCEL 20 000, PARCEL_CLASS_1 **5 000**, POSTAL_PARCEL 20 000, ONLINE_COURIER 31 500, EMS 31 500 (domestic). PARCEL_CLASS_1 is the surprising one — a 5 kg product. POSTAL_PARCEL's refusal arrives as `TARIFF_ERROR` text, not as a typed code: a plugin that waits for `ILLEGAL_MASS_EXCESS` alone would miss it, so enforce the limit plugin-side from this table (and treat both shapes as «too heavy»).
- **Volumetric rule (spec §8.2 / U10):** v1's rule `ceil( max( packed weight, volumetric ) )` is **valid but needs the divisor 5 000 (cm³/kg)** and is **not required** for correct pricing if the plugin sends `dimension` (cm): the API prices `max(mass, L×W×H/5000)` itself. Two safe designs: (a) send real `mass` + `dimension` and let Otpravka price it, enforcing our own limit on `max(real, volumetric)`; or (b) send `mass = ceil(max(real, volumetric))` without `dimension` — both yield the same `weight-pay`. Do not send both a pre-maxed mass and dimension inconsistently (harmless, still max). The rate shown to the buyer comes from `POST /1.0/tariff`, which must receive the same `dimension`, otherwise the checkout price is too low versus what Otpravka bills.
- **ТН ВЭД (spec §9.2):** the existing sentence «a malformed code is rejected, whether a well-formed non-existing code is rejected is UNVERIFIED» becomes: **a non-existent code is rejected (`ILLEGAL_CUSTOMS_ENTRY_TNVED_CODE`); only real 10-digit leaf codes pass**. The plugin cannot validate the dictionary itself, so the product/export screen should show the Otpravka message verbatim and the admin hint should say «код из 10 цифр, листовой».
- **Declaration (spec §9.2):** KZ/AM/KG forbid it, confirmed both ways for AM and KG. Retry rule is right, but when retrying drop the **whole** `customs-declaration` key (an empty entries list triggers both errors).

## UNVERIFIED (what stays open)

- Whether `dimension` also affects physical acceptance limits at the post office (sum of sides 200 cm etc. for domestic products): the API accepted 110 cm and 130 cm sides, so only the `max` weight is billed; no refusal measured at create, batch not run.
- Domestic dimension limits per product and the ONLINE_COURIER/EMS volumetric limit (a 24 kg-volumetric order was accepted, 31 500 g not exceeded; not tried above it).
- Whether other categories (COMBINED_* to a postamat with S/M/L/XL) use the same divisor or the cell class instead — not tried (dimension-type path, card for postamats).
- The sweep covers countries open **today** and parcel/EMS; SMALL_PACKET was checked only for KZ/AM/KG; a country that opens later may add a new declaration-free destination — the one-time retry covers it.
- ТН ВЭД: which exact leaf codes exist is not measurable here (Otpravka has no dictionary endpoint in our reading); a code accepted at create can still be refused by customs.
- Minimum mass (mass 1–10 g) and mass limits for pickup-point deliveries (partner ППВЗ `weightLimit` 3/10/30/31.5 kg from the passport) were not measured at create.
- The POSTAL_PARCEL `TARIFF_ERROR` shape for overweight appeared at `position` level with a single error code; its HTTP is 200 (partial-success shape), consistent with G.
