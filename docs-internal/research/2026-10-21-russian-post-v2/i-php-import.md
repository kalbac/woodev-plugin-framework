# Task I — importing the Russian Post passport point list in PHP (rig measurements, 21.10.2026)

Feeds brainstorm topic 2. Everything below was measured on the rig's real PHP, not estimated. Nothing in any repo was edited or committed.

**Setup.** `tests-cli` container of this project's wp-env: PHP 8.1.34 (NTS, aarch64, OrbStack), php.ini `memory_limit=128M`, MariaDB 12.3.3 with `innodb_buffer_pool_size` 128 MB, WP 7.1, no external object cache (transients go to `wp_options`). **wp-cli itself sets `memory_limit=-1`**, so every WP-level run enforced a limit explicitly with `ini_set()` (or `php -d`) and printed `ini_get('memory_limit')` to prove it took (64M run printed `ini memory_limit=64M`; a bare 1 MB x 200 allocation loop was killed at 64M). The rig's WordPress baseline is **51.3 MB** peak (WC + both carrier plugins loaded) — a lean shop sits lower, a heavy one higher.
Scripts: kept outside the repo (`dl.php`, `stream.php`, `parse.php`, `import.php`, `transient.php`, `lim.php`). Account: the TEST «Отправка» account; the only live call was the one passport download.

## Proposal: batching on Action Scheduler (design from the numbers above; the resume code itself is not written or measured)

1. **Job A (daily, jittered, after the nightly snapshot):** the passport was generated 20.10.2026 09:18 UTC, so schedule a randomised time after ~10:00 UTC. One HTTPS GET to a temp file in `uploads/` (5.6 MB, ~1.3 s here), `Accept: application/octet-stream` (anything else = 406 and still costs a unit). Unzip with `ZipArchive` to a file or stream directly from the zip. Count against a plugin-side quota counter (the displayed counter lags, fact base §4.2); with backoff and a cap, because every shop hitting `otpravka-api.pochta.ru` once a day is 1 unit but a failure loop is not.
2. **Job B (resumable ingest into a staging table):** loop the stream parser with a **time budget (~20 s) and a row budget**, flush every 500 rows, store `{file offset of the last completed element, rows done}` in an option, and reschedule itself when the budget is hit. On the rig the whole file is one 2 s pass, so on normal hosts it is one job; the budget only matters on slow shared hosting. Resuming at a saved byte offset needs the scanner to start at an element boundary (not written yet — UNVERIFIED).
3. **Job C:** `RENAME TABLE` staging ↔ live in one statement, then drop the old one; delete the temp file. Never serve from a half-loaded table; on failure keep yesterday's table and surface the age in the admin.
4. Only if the host's `max_execution_time` or the 30 s WP-Cron/AS window is hit repeatedly would it be worth splitting by key range; no number here suggests it.
5. The viewport endpoint then reads the table by bbox: Moscow centre 0.5 ms, a whole region ≈15 ms (full scan), country 54 ms in SQL but **167 MB PHP** if hydrated, so cap the bbox/`LIMIT` or cluster server-side.

## Not measured / caveats

- Widget-backend import (skipped on purpose, see row 4); 5–10x slow-host factor; resumable offset code; staging+swap timing; sweep of vanished points; real object-cache behaviour; MySQL vs MariaDB differences (rig is MariaDB 12.3.3 — a shared host may run MySQL 5.7/8 or older MariaDB with different JSON/charset defaults; used `LONGTEXT`-compatible TEXT columns, not the `JSON` type); innodb buffer pool was the rig default 128 MB.
- Quota: exactly **one** Otpravka unit used by this task (the passport download).
- Passport is 13 points without coordinates (they get `NULL,NULL` and never match a bbox) and has **no closed flag** (fact base §4.3).
- **Rig incident:** midway, OrbStack's docker daemon hung for ~15 minutes (Helper at ~50 % CPU) right after repeated wp-cli runs; the coordinator restarted OrbStack, which left all six wp-env containers stopped. I started only this project's six containers with `docker start` (mysql first); `localhost:8973` and `:8974` both return 200 again. Cause of the hang: not established. My first limit runs (64M/80M "passes") were invalid — the edit adding the limit had not been applied after a permission denial — and were redone; only the redone numbers are used above.
