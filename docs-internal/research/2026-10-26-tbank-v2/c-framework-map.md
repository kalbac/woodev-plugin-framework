**Date:** 2026-10-26. **Scope:** read-only framework and T-Bank v1 reference inventory for a hosted loan gateway. **Evidence labels:** READ = inspected in source/docs; MEASURED = command/count output; UNVERIFIED = not established from the inspected evidence. ## 1. What v2 contains

**READ:** `woodev/payment-gateway/` is still a global-namespace legacy subsystem (`Woodev_Payment_Gateway*`), not a v2 rewrite into `Woodev\Framework\*`; see [namespace-migration-legacy-psr4](../../gotchas/namespace-migration-legacy-psr4.md) and the class declaration at `woodev/payment-gateway/class-payment-gateway-plugin.php:32`. It is conditionally loaded by the bootstrap only for a payment plugin (`woodev/bootstrap.php`, gotcha [payment-gateway-conditional-load](../../gotchas/payment-gateway-conditional-load.md)). Most of the existing general gateway engine was carried into v2 with maintenance edits. Concrete v2 changes in the recent history include removal of the US-specific eCheck/ACH payment type and compatibility/dead APIs (`d85a1f92`, `728c6f4`), restoring shared base methods deleted during cleanup (`a7da0ea7`), explicit nullable types (`ef3d067d`), API log secret masking (`ac09b9bd`, `a3d154bb`), and more recent bug fixes. These are targeted edits, not a clean-sheet hosted gateway implementation. **UNVERIFIED:** a full per-method v1-to-v2 diff was not produced.

## 3. Cart and Checkout Blocks for payments

**READ / MEASURED:** no `AbstractPaymentMethodType` subclass, `registerPaymentMethod()` call, or Blocks payment integration exists under `woodev/payment-gateway/`, `woodev/`, or framework `src/`; the existing payment gateway API is WooCommerce’s classic `WC_Payment_Gateway` contract. (Searched symbols and source tree.) This means the framework does not currently provide a Blocks payment-method bridge or a Blocks payment JS bundle.

WooCommerce’s official [Payment method integration guide](https://developer.woocommerce.com/docs/block-development/extensible-blocks/cart-and-checkout-blocks/checkout-payment-methods/payment-method-integration) says the integration has server and client sides: server class extends `Automattic\WooCommerce\Blocks\Payments\Integrations\AbstractPaymentMethodType`, is registered on `woocommerce_blocks_payment_method_type_registration` (typically after `woocommerce_blocks_loaded`), and client code registers via `registerPaymentMethod` on the Blocks registry. Crucially, the guide says standard legacy payment processing remains supported: Checkout Block routes its `payment_data` to `$_POST` and calls the gateway's `process_payment`; the Store API context hook is for advanced cases where that legacy path is insufficient. **Consulted 2026-10-26.**

Minimal framework seam sketch: add optional, separately loaded payment Blocks integration under `woodev/payment-gateway/blocks/` (or a similarly owned submodule), wired by `Woodev_Payment_Gateway_Plugin` only when the payment plugin declares Blocks support. Feature-detect the WC abstract class, register an integration instance on the Woo hook, and enqueue a plugin-built `registerPaymentMethod` bundle plus its settings data. Prefer forwarding to the existing gateway `process_payment()` path; add Store API context processing only if the provider flow requires capabilities that legacy processing does not carry. Keep default behavior legacy-compatible; declare `cart_checkout_blocks` compatibility only if the gateway integration supports it. Tests should cover class absence, registry/assets, redirect/error and callback continuity. This follows the *shape* of SP-11’s shipping adapter (framework-owned integration, script/data and version feature detection; see `docs-internal/specs/2026-10-04-sp11-block-checkout-design.md:340-366`), but payment uses Woo’s distinct payment-method API, not shipping `IntegrationInterface` or `registerCheckoutBlock`.

**GAP G1:** payment Blocks server/client adapter and checkout Store API bridge. **Release 1? no** under current `#639` scope; T-Bank v1 advertises/uses classic checkout and issue #639 requires multiple payment types before broad module decisions. Operator can change this if T-Bank’s release brief requires block checkout.

## 4. Mixed v1/v2 bootstrap: why T-Bank blocks v2 carriers

**READ:** In the incident recorded on #1389, store had CDEK v2 plus Russian Post v1 and T-Bank v1. The issue confirms both v1 plugins stop when the v2 bootstrap wins; for T-Bank there is no v2 replacement, so that merchant cannot move to v2 carriers while retaining the current T-Bank plugin.

The v2 plugin entry uses `Woodev_Loader::register()`; `woodev/loader.php:54-82` resolves the vendored bootstrap, then if the winning `Woodev_Plugin_Bootstrap` lacks `register_loader_definition()` it records the v2 plugin dormant and returns false (`:69-82, 100-115`). Conversely, v2 bootstrap `woodev/bootstrap.php:100-139` retains a variadic `register_plugin()` tombstone for the v1 API: it records v1 plugin as mixed-fleet incompatible and never calls its initialization callback. The notice is rendered from `:148+`. The first loaded vendored `Woodev_Plugin_Bootstrap` class wins via `class_exists()` guard; it cannot merge v1 and v2 registration models.

In the v1 T-Bank reference, `plugins-reference/woodev-vkredit/woodev/bootstrap.php:5` guards class definition with `class_exists`; entry `plugins-reference/woodev-vkredit/woodev-vkredit.php:28` calls v1 `register_plugin(...)`; its hosted gateway is `plugins-reference/woodev-vkredit/includes/class-gateway.php:7`. When CDEK v2 bootstrap won, the tombstone intercepted that registration and suppressed T-Bank’s callback; when a v1 bootstrap wins, v2 `Woodev_Loader` detects missing `register_loader_definition()` and leaves the v2 carrier dormant. Thus plugin load order decides which side is disabled. The v1 bootstrap’s own `load_plugins()` picks the highest v1 plugin version among registrations (`plugins-reference/woodev-vkredit/woodev/bootstrap.php:76-88`), but it never receives v2 loader definitions. This is why #1389’s “update the outdated plugin” copy is factually impossible for T-Bank until a v2 port exists.

**GAP G2:** T-Bank v2 port / truthful mixed-fleet migration notice. **Release 1? yes** for the first v2 T-Bank release; notice wording/rollout is **operator** (issue #1389 asks for his decision on copy).
