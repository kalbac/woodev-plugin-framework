
# Ozon Delivery API diff — 30 Oct 2026 vs 21 Aug 2026

**Verdict.** The current OpenAPI snapshot adds 22 operations across six operational families, most useful to merchant setup and warehouse handover; the key first-release improvement is `shipment-method/search`, which removes the documented need to copy method IDs by hand. For checkout, posting and returns, the wire contract is mostly stable, with three material schema/documentation deltas: pickup-info batch limits, posting storage expiry, and richer return search/info fields. The file is an API-spec comparison, not evidence that new/write operations work live.

Pointers below use JSON Pointer fragments into `ozon-swagger-2026-10-30.json` (`/` in a path token is escaped as `~1`) and August wiki line numbers.

## New path groups and plugin relevance

| Group / current-spec pointers | What it adds; first-release relevance | August assumption changed |
|---|---|---|
| `shipment-method/{create,update,search,info,delete}` — `#/paths/~1v1~1shipment-method~1search/post`, `...~1info/post`; schemas `#/components/schemas/Ozon.Delivery.ShipmentMethod.Search.Request` and `...Types.ShipmentMethod` | Search/filter/paginate and inspect configured methods; create, update and disable them. Search/info can replace a merchant manually copying `shipment_method_id` into settings, and is useful to populate setup choices. Create/update/delete are cabinet administration, not checkout. The returned method includes status, ID, name, type, barcode, address/coordinates, bulky/entrusted-acceptance and arrival-pass flags. | Directly overturns “no API to enumerate shipment methods” and manual ID entry as the only option (`ozon-delivery-api.md:26–34`; `00-PROJECT-OVERVIEW.md:46–49`; `01-API-TO-WOOCOMMERCE-MAP.md:48–50`). It does not prove the method ID is always the barcode number beyond the August cabinet description.
| `dropoff-point/{search,info}` — `#/paths/~1v1~1dropoff-point~1search/post`; schema `#/components/schemas/Ozon.Delivery.DropoffPoint.Types.DropoffPoint` | Find/inspect places where the merchant hands parcels to Ozon, with type, address, coordinates, schedule, bulky/self-acceptance/entrusted-acceptance, capacity and return-point availability. These are merchant handover locations, not buyer delivery points. Useful in shipment-method setup; not needed for buyer checkout in the pickup/locker/courier first-release flow. | Adds dedicated handover-point discovery. August treated the handover location as configured inside a shipment method and did not have this API family (`wiki:28–34`).
| `container/{create,fill-postings,remove-postings,approve,label,search,info,cancel}` — `#/paths/~1v1~1container~1create/post` and `#/components/schemas/Ozon.Delivery.Container.Types.ContainerStatus` | Create a cargo unit for a shipment method, attach/detach postings, approve/cancel, inspect its contents/status and get a PDF label. Supports warehouse consolidation and physical handover; outside basic online checkout. Whether a given shipment method requires containers before handover is not established by the schema, so treat it as a later dispatch-workflow question. | Adds a container/cargo-unit lifecycle absent from the August API map. Posting labels alone remain a separate operation.
| `arrival-pass/{create,update,search,delete}` — `#/paths/~1v1~1arrival-pass~1create/post`; `#/components/schemas/Ozon.Delivery.ArrivalPass.ArrivalPass` | Register, update, search and delete vehicle/driver passes, keyed by shipment method and arrival time; fields include driver name/phone, vehicle plate/model. Only relevant if the merchant’s handover point requires a pass (`shipment_method.arrival_pass_required`); not a buyer checkout feature. | Adds access-pass scheduling that August did not describe. This is conditional warehouse administration, not a blanket requirement.
| `return-point/{search,info}` — `#/paths/~1v1~1return-point~1search/post` | Discover/inspect locations for the merchant to receive returns (address, coordinates, schedule and point type). Relevant to reverse logistics/return handling, which August explicitly deferred; not first-release checkout. | Adds a separate return-receipt point catalogue; it is not the buyer’s pickup-point catalogue (`01-API-TO-WOOCOMMERCE-MAP.md:169–186`).
| `posting/get-insurance-certificate` — `#/paths/~1v1~1posting~1get-insurance-certificate/post` | Fetch an insurance policy/certificate for one posting. Useful for claims/accounting after dispatch; not rating or checkout. The 200 response has no declared media type/schema in this snapshot, so the actual file format remains unknown. | August documented insurance as separately quoted but had no certificate retrieval method (`wiki:205–216`, `337–352`).

`return/download_barcode` and `return/reset_barcode` are not new paths. The current spec still leaves the download 200 media/schema unspecified; reset returns JSON `barcode_content {barcode, expires_at}` (`#/paths/~1v1~1return~1download_barcode/post`, `#/paths/~1v1~1return~1reset_barcode/post`, `#/components/schemas/Return.ResetBarcode.Response`). This matches August’s understanding that a downloadable PDF and an expiring reset barcode are separate methods (`wiki:369–384`); neither belongs to checkout’s first release.

## Existing paths the plugin is expected to use

I compared each listed operation’s request/200 response schema with the corresponding August wiki description and checked captured read-only response shapes where present. No field rename or primitive-type change was apparent for the August-described checkout, point-availability, posting, or return core fields. Additions/contradictions worth carrying forward:

- **Pickup point batch limits now conflict with the spec prose and August measurements.** Current `delivery-point/info.delivery_point_ids` allows 1–1000 (`#/components/schemas/Ozon.DeliveryPoint.Info.Request`), while August says 1–100 (`wiki:284–286`). Current `delivery-point/list.pagination.limit` declares maximum 1000 (`#/components/schemas/Ozon.DeliveryPoint.Pagination.List`), while the August live probe rejected 1000 and established max 100 (`03-RECON-REPORT.md:47–48`; `wiki:266–269`). Keep 100 for the plugin unless a live recheck proves otherwise; the newer schema’s declared upper bound is not operational evidence. `check-availability` remains 1–100 point IDs and 1–100 postings (`#/components/schemas/Ozon.DeliveryPoint.CheckAvailability.Request`).
- **Posting info/search adds nullable `storage_expires_at`** (date-time) to each posting (`#/components/schemas/Ozon.Delivery.Posting.Types.Posting`); the August enumerated `posting/info` fields omit it (`wiki:341–352`). It can inform a merchant about pickup-point storage expiry, but does not change quoting or order creation.
- **Return search now documents optional filters** `statuses`, `shipment_method_id`, `created_at_from`, `created_at_to` (`#/components/schemas/Return.Search.Request`, `#/components/schemas/Ozon.Delivery.Return.Search.Filters`). August’s method table says only `pagination` (`wiki:369–373`). This enables incremental/targeted polling on paper; confirm server behavior before relying on it.
- **Return info now requires `created_at` and `status_changed_at`** in its return records (`#/components/schemas/Return.Types.ReturnShortInfo`). August says these are additionally present in search (`wiki:377–382`), implying they were search-only. The current schema says both search and info include them. No August live `return/info` capture is listed, so this is a spec-vs-wiki change, not a measured response change.
- **No added status enum values:** posting’s 13 values and return’s 8 values are unchanged from the August enum tables (`wiki:390–426`; `#/components/schemas/Ozon.Delivery.Posting.Types.PostingStatus`, `#/components/schemas/Return.Types.ReturnStatus`). `return_type`, `return_delivery_type`, and cancellation-responsible values also match the August descriptions.
- **Errors are not a closed enum in the new spec.** Per-item `error.code` remains nullable string; `NotEnoughBalance` is still an August-documented posting-approval outcome, not a newly typed value (`#/components/schemas/Ozon.Delivery.Common.Error`; `wiki:453–459`). I found no new machine-readable error-code enum to report. Posting/return batch inputs remain capped at 100; checkout/create postings remain 1–100; posting search and return search pagination remain capped at 100.

Captured August responses are consistent with the described core shapes for `check-client`, `delivery/location`, pickup list, checkout, posting search and return search (`tools/recon/out/02-check-client.json`, `03-delivery-location.json`, `04-delivery-point-list.json`, `07-order-checkout-pickup.json`, `08-order-checkout-courier.json`, `09-posting-search.json`, `12-return-search.json`). The captured empty posting-search response omitted `next_cursor`, as already recorded; the current schema makes it nullable/optional, so callers must continue to tolerate omission (`03-RECON-REPORT.md:39`). The sample `posting/info` capture is an error response, not usable success evidence. August did not execute write methods, so no live comparison exists for order creation, approval, labels, cancellation, or barcode writes (`03-RECON-REPORT.md:18–20`).

## Auth, hosts, throttling, idempotency, notifications

- OpenAPI declares one server, `https://api-delivery.ozon.ru`, `x-disableAuth: true`, and no security schemes (`#/servers/0`, `#/security`, `#/components/securitySchemes`). Thus this snapshot does not specify bearer auth or OAuth. August’s separately measured/documented token flow remains: `POST https://xapi.ozon.ru/oauth/token`, then bearer calls to the delivery host (`wiki:36–80`; `03-RECON-REPORT.md:29–33`).
- Operations list HTTP 429 errors, but no numeric rate limit or rate-limit headers/contract (`#/paths/~1v1~1order~1create/post/responses`). August’s 452 calls at 200 ms without 429 remain the only measured limit evidence, not a ceiling (`03-RECON-REPORT.md:47–49`).
- `order/create` declares optional header `Idempotency-Key`, string UUID (`#/paths/~1v1~1order~1create/post/parameters/0`). The spec’s presence/type does not establish whether it is honored or for how long. The August wiki says identical-key retries return the original response (`wiki:224–228`), but the live report still leaves Q-9 open (`03-RECON-REPORT.md:82`): operational idempotency/duration was not tested.
- There are no webhook/notification paths or callback schemas among the 40 operations. This is consistent with August’s polling design, but a REST OpenAPI file’s silence alone cannot prove that Ozon has no out-of-band notifications (`wiki:327–335`, `01-API-TO-WOOCOMMERCE-MAP.md:151–162`).

## August wiki statements now wrong or incomplete

- `docs/wiki/ozon-delivery-api.md:33–34`, `docs/00-PROJECT-OVERVIEW.md:46–49`, `docs/01-API-TO-WOOCOMMERCE-MAP.md:48–50`: “no API to enumerate shipment methods/manual ID copy” is stale; use `shipment-method/search`/`info` on paper.
- `docs/wiki/ozon-delivery-api.md:284–286`: `delivery-point/info` batch maximum is stated as 100; current spec allows 1000. The live 1000 rejection for list cautions against accepting the new ceiling without retest, and there is no equivalent info-limit measurement cited.
- `docs/wiki/ozon-delivery-api.md:341–352`: `posting/info` field inventory omits `storage_expires_at` from current Posting schema.
- `docs/wiki/ozon-delivery-api.md:369–373`: `return/search` request is summarized as pagination-only; current schema also has status/method/date filters.
- `docs/wiki/ozon-delivery-api.md:377–382`: says `created_at` and `status_changed_at` are additionally in search, while current ReturnInfo and ReturnShortInfo both include them; revise this if the snapshot is accepted as current contract.
- `docs/wiki/ozon-delivery-api.md:461–478`: statements that delivery API has no shipment-method discovery, dropoff points, arrival passes, containers, return points, or insurance-certificate method are incomplete as of this snapshot. Preserve the 2026-08-21 404 evidence at `03-RECON-REPORT.md:51–68`: `cancel-reason/list`, `delivery/map`, `posting/marks`, `order/cancel/check`, and `delivery/check` were already 404 on the delivery host. Other “gone” legacy forms (`delivery/point/{info,list}`, `order/cancel`, `posting/cancel/status`) are listed only as older/Seller-API route forms at `wiki:476–478`; they were not among those five August probes and should not be presented as formerly working delivery-host paths. Current cancellation remains `/v1/posting/cancel` with no documented cancel-reason lookup/status endpoint.
