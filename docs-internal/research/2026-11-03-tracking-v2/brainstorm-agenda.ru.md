# Отслеживание доставки v2 — повестка решений

> s214, 03.11.2026. Основа: [a-v1-inventory.md](a-v1-inventory.md) (что умеет v1 1.3.0), [c2-source-check.md](c2-source-check.md)
> (что дают фреймворк и наши службы доставки — проверено по коду), [c-framework-map.md](c-framework-map.md) (по документации,
> поправки в C2). Страница товара: https://woodev.ru/downloads/shipment-tracking (2 800 ₽, 60+ установок).
> Проходим с оператором по одному пункту; решение записывается сюда же.

## Факты, на которых стоит повестка

- v1 маленький: 1 219 строк PHP + 5 шаблонов; номер вводится вручную, 9 служб со ссылками, «своя служба»; номер в колонке
  заказов, во ВСЕХ письмах заказа и в личном кабинете; отдельное письмо — только вручную. Статусов не знает.
- Страница товара обещает: автоматическое добавление номера при экспорте в СДЭК и Почту, «автоматические уведомления»
  (и рядом — «не отправляется автоматически»), дропшиппинг, 8 служб со ссылками.
- Автодобавление от СДЭК уже не работает: СДЭК v2 этот хук убрал. Почта v2 хук ещё вызывает. Яндекс и Ozon никогда не передавали.
- **В личном кабинете трек сейчас не показывает никто** — ни фреймворк, ни четыре службы доставки. Только письма.
- Фреймворк умеет ответить «какая наша служба везёт этот заказ» (`Orders_Registry::resolve_provider_for_order()`), дать номер,
  ссылку и журнал статусов (`Delivery_Status_Log::read()`).
- Дубли сегодня возможны только в письмах: таблица v1 вставляется и в письма фреймворка о доставке, где номер уже есть.
- Попутно: письма фреймворка для заказов Ozon уходят без номера — карточка ozon#88.

## Пункты

1. **Чем плагин становится.** (а) Как v1: ручной номер для любой службы. (б) Плюс единое место для трека от НАШИХ служб: личный
   кабинет показывает номер, ссылку и статус для заказов СДЭК / Яндекса / Почты / Ozon, без ручного ввода.
   Рекомендация: (б) — это закрывает пустое место в личном кабинете и возвращает обещание «автоматически при экспорте» для всех четырёх.
2. **Дубли в письмах.** Не вставлять свою таблицу в письма фреймворка о доставке и в письмо Почты; в остальные письма заказа —
   только для ручных номеров. Рекомендация: так.
3. **Своё письмо: вручную или автоматически.** Рекомендация: настройка «отправлять при добавлении номера», по умолчанию включена
   для ручных номеров; для заказов наших служб письмо не шлём — его шлёт фреймворк.
4. **Статус рядом с номером** (из журнала статусов, только для наших служб). Рекомендация: да, в личном кабинете.
5. **Список служб.** 9 служб v1 (Почта, СДЭК, ПЭК, Shiptor, Сбер Логистика, Деловые линии, DPD, Boxberry, Энергия): обновить
   список и проверить ссылки; Shiptor, вероятно, убрать. Плюс «своя служба» с шаблоном ссылки в настройках, а не только в заказе.
6. **Лицензия.** v1 без лицензии «сохраняет» номер и молча теряет его. Рекомендация: без лицензии ввод виден, но с понятным
   сообщением; уже сохранённые номера покупатель видит всегда.
7. **Что сохраняем байт в байт.** Данные `_tracking_number_items` (читать и русское название службы, и код), id письма
   `order_tracking_number` и его настройки, шаблоны и их переопределение в теме, слаг, лицензия и EDD 2653, функции
   `wc_otn_*` и фильтр списка служб. Рекомендация: всё сохранить.
8. **Настройки** — на странице `woodev-settings` (список служб, письмо, вывод). Рекомендация: так.
9. **Номер версии и цена.** v2 выходит как 2.0.0. Цена — на его слово.

## Решения

1. **Пункт 1 — вариант (б)** (оператор, 03.11.2026): ручной номер для любой службы + единое место для трека наших служб.
   **Уточнение оператора:** показ трека покупателю (личный кабинет, страница после оплаты) для наших служб делается
   **на уровне фреймворка**, всегда, когда у доставки есть трек — как было в v1 СДЭК и Почты. Отдельная карточка фреймворка.
   Плагин отслеживания тогда НЕ дублирует этот вывод для заказов наших служб: его зона — ручные номера, свои письма, статус.
2. **Пункт 2 — по рекомендации** (оператор, 04.11.2026): своя таблица трека не вставляется в письма фреймворка о доставке
   (`customer_shipment_*`), в письмо Почты (`wc_russian_post_tracking_email`) и в письма администратору; в остальные письма
   заказа — только ручные номера.
3. **Пункт 3 — по рекомендации** (оператор, 04.11.2026): своё письмо уходит автоматически при добавлении нового ручного номера
   (настройка «Отправлять при добавлении номера», по умолчанию включена); каждый номер автоматически — один раз, только про
   новый номер; действие «Отправить номер отслеживания» остаётся для повторной отправки. Для заказов наших служб письмо шлёт фреймворк.
4. **Пункт 4 — статусов в плагине нет** (оператор, 04.11.2026). Его слова: «отдельно не нужно ни какие статусы запрашивать,
   этот плагин не про это. Его основная задача — добавили трек вручную или он подтянулся из наших плагинов, и письмо
   отправилось либо по нажатии на кнопку, либо автоматически, если это допустимо». Статус/история для наших служб — вопрос
   спецификации #1575. Для спецификации плагина: номер наших служб «подтягивается» (виден в плагине), но вывод покупателю
   делает фреймворк, а автоматическое письмо — только если оно не дублирует письмо фреймворка.
5. **Пункт 5 — по рекомендации** (оператор, 04.11.2026): проверить 9 ссылок v1 по сети; мёртвые убрать из выбора для новых
   заказов (старые заказы сохраняют название и прежний формат ссылки); добавить Яндекс Доставку и Ozon (и популярные службы
   с публичной страницей отслеживания по номеру); свои службы — в настройках (название + шаблон ссылки), ручное поле в заказе
   остаётся; фильтр `wc_order_track_number_providers_list` сохраняется. Проверка ссылок — `e-carrier-links.md`.
6. **Пункт 6 — по рекомендации** (оператор, 04.11.2026): без лицензии уже сохранённые номера покупатель видит всегда (ЛК, письма);
   добавить номер и отправить письмо нельзя — на странице заказа понятное сообщение и ссылка на продление вместо формы (не
   «тихое» сохранение, как в v1); номера наших служб от лицензии плагина отслеживания не зависят.
7. **Пункт 7 — по рекомендации** (оператор, 04.11.2026): сохраняются байт в байт данные `_tracking_number_items` (чтение и
   русского названия службы, и кода), id письма `order_tracking_number` и его настройки, шаблоны и их переопределение в теме,
   классы CSS, папка/файл плагина, plugin id `wc_order_track_number`, лицензия и EDD 2653, функции `wc_otn_*`, фильтр списка
   служб, текстовый домен `woocommerce-tracking-number` (не меняем).
8. **Пункт 8 — по рекомендации** (оператор, 04.11.2026): на `woodev-settings` — свои службы (название + шаблон ссылки),
   переключатель автоматической отправки, лицензия; тема/заголовок/текст письма остаются в WooCommerce → Email (ссылка
   «Настроить текст письма»); отдельных переключателей вывода нет — номер показывается всегда.
9. **Пункт 9** (оператор, 04.11.2026): версия **2.0.0**, цена **3 000 ₽**.
10. **Объём выпуска** (оператор, 04.11.2026): отдельной документации нет — всё на карточке товара; если наберётся на страницу —
    одна страница документации. Без экрана миграции, без мастера установки, без поста в блоге и в Telegram. Скорее всего,
    последнее обновление плагина: когда пользователей станет ноль — снять с продажи. Отдельную доску не заводить.
11. **Порядок выпуска** (оператор, 04.11.2026; вопрос Q1 спецификации): фреймворк с #1575 и плагин 2.0.0 — одной волной,
    плагин собран на новой версии фреймворка. Критик спецификации: раунд 1 — 1 Must fix, исправлено; раунд 2 — замечаний нет.
12. **«Дропшиппинг»** (оператор, 04.11.2026; Q2): отдельной функции нет — это ручной номер со «своей службой»; на карточке товара —
    как пример использования («добавьте номер, который дал поставщик, — покупатель получит письмо»).
13. **Автоотправка у обновляющихся магазинов** (оператор, 04.11.2026; Q3): включена у всех; после автоматической отправки на
    странице заказа пометка «Письмо с номером отправлено покупателю автоматически, <дата время>»; первая строка журнала
    изменений — «Письмо с номером теперь уходит автоматически».
