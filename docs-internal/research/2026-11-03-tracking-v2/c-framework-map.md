## 1. Tracking data and extension points in the framework

- **READ:** Framework architecture describes carrier-owned tracking number/link in the aggregate «Заказы доставки» page, with tracking number represented by the provider's order data and a provider tracking URL template. The orders-page provider contract has `marker_meta_key`, `tracking_url`, status map and columns; framework common columns include tracking (`docs-internal/specs/2026-09-07-sp10-orders-page-design.md`, §§M1–D3). This is an orders/export view for registered shipping providers, not a general-purpose tracking-number registry.
- **READ:** HPOS-safe order metadata is available through `Woodev_Order_Compatibility::update_order_meta()`, `get_order_meta()` and `order_meta_exists()`; the public guide demonstrates a plugin-owned key `_my_carrier_tracking_number` (`website/src/content/docs/core/hpos-and-blocks-compatibility.md:123-144`). A generic plugin can therefore persist a manually entered number without using post meta directly.
- **READ:** Framework canonical delivery tracking is a distinct feature: carrier owns API retrieval/polling and maps raw status codes to canonical statuses. The framework journal stores `_woodev_delivery_status_log_{provider id}` as JSON, oldest-first, capped at 20, with canonical state, UTC Unix timestamp and raw carrier status; it is forward-only, does not backfill a shipment first seen already underway, and only records changes (architecture wiki, “Delivery status log”, `Delivery_Status_Events`, `Delivery_Status_Log`, #1564; §13 in carrier plugin specs). `notify()` and `sync()` share reconciliation; locking/re-read/save behavior is documented there. This is not a log for arbitrary manual tracking numbers absent an `Orders_Provider`.
- **READ:** The framework has a one-page «Заказы доставки» registry aggregating registered carrier providers. It displays common tracking and canonical status data and supports carrier-specific refresh/actions, but SP-10 explicitly excluded shipment export, status sync and status history from the page itself; those belong to separate shipping seams (`docs-internal/specs/2026-09-07-sp10-orders-page-design.md:19, 133-179`, §§D1–D4; `docs-internal/wiki/architecture.md`, “Shipping orders page”).
- **READ:** Framework shipping plugin interfaces include `Orders_Provider`, `Abstract_Shipment_Handler`, status event journal, tracking URLs, and carrier API concepts. This is wired through a shipping plugin's method/handler registrations. A non-carrier plugin cannot simply register arbitrary order tracking in the shared carrier page based on the documented provider contract.
- **UNVERIFIED:** Exact public PHP calls/hooks for order metadata, status sync and URL construction beyond documented APIs; Serena was unavailable and no PHP source was read. The exact current method to render a neutral tracking URL outside a shipping provider is not established. The design contract indicates a URL template on `Orders_Provider`, not a framework-wide URL builder.
- **READ:** Framework shipping plugins get shared shipment-status buyer emails (`customer_shipment_created`, status-change IDs), with built-in tracking number/link/carrier placeholders and `woodev_shipping_delivery_email_placeholders` (`website/src/content/docs/shipping/orders-export-documents-and-tracking.mdx:356-358`; `website/src/content/docs/reference/hooks-and-filters.md:277`). This seam is provider/status based, not a generic email for an arbitrary manual number. **UNVERIFIED:** a shared generic My Account/order-view renderer for arbitrary tracking records was not established.

## 3. Framework plugin type and shared services

- **READ:** Framework's inheritance ladder is `Woodev_Plugin` → WooCommerce plugin base → shipping plugin / payment gateway specialization; documentation says choose the most specific class that fits (`website/src/content/docs/core/plugin-class.md:21`). A manual tracking-number plugin that is neither a shipping-method plugin nor gateway should extend the generic WooCommerce plugin base (the WooCommerce-aware non-shipping layer), not `Woodev_Shipping_Plugin`. The specific generic WooCommerce base is `\Woodev\Framework\Woocommerce_Plugin` (`website/src/content/docs/core/plugin-class.md:10-25), while `Woodev_Plugin` is for WordPress-only plugins.
- **READ:** Generic framework plugins get shared lifecycle, licensing/EDD updater, admin notices and plugin settings integration through framework plugin construction; `woodev-settings` is a shared React settings surface backed by `Settings_Page_Registry` (framework architecture and the v2 gateway reference report `docs-internal/research/2026-10-26-tbank-v2/c-framework-map.md`, “Settings”; architecture subsystem status). A generic tracking plugin can use the shared settings system without adopting shipping settings providers.
- **UNVERIFIED:** Exact settings-provider class registration for this specific plugin was not confirmed from PHP source because Serena was unavailable.

Framework's provider registry does not appear to cover a manually entered number without implementing carrier provider behavior.

## 5. Coexistence with carrier plugins

- **READ:** Shared admin tracking display belongs to framework orders page for registered carrier providers; each provider declares its marker key and tracking URL. This prevents four carrier-specific tables but does not itself define buyer-side ownership or suppress a separate generic tracking plugin (`SP-10 D1-D3`).
- **READ:** Framework sent markers `_woodev_delivery_email_<id>` exist. Russian Post avoids a second `customer_shipment_created` mail by writing `_woodev_delivery_email_customer_shipment_created` after its own email succeeds (`woodev-russian-post/docs/CURRENT-STATE.md:25`; framework contract in `docs-internal/specs/2026-10-21-russian-post-v2-plugin-design.md:461`).
- **UNVERIFIED:** No general cross-plugin filter was established for manual number output on email/account surfaces. The CDEK `woocommerce_edostavka_email_tracking_core_url` hook is carrier-specific, not a fleet-wide contract.
- **Recommended smallest coexistence behavior (inference):** render the manual number only when its own manual tracking meta exists and the order has no recognized carrier tracking number; allow explicit merchant override for orders that intentionally have both a carrier shipment and a separate parcel. Avoid deduplicating solely by number string because a combined order can legitimately have multiple parcels. A later shared filter could standardize ownership, but no existing public seam is verified.

## Gap list

**G1 — Generic manual tracking data/editor:** framework has HPOS-safe meta helpers, but no framework-owned arbitrary tracking-number CRUD contract or order editor is evidenced. Smallest fix: plugin-owned order edit field and namespaced meta key using `Woodev_Order_Compatibility`.

**G2 — Generic tracking URL:** provider tracking URLs exist on `Orders_Provider`, but no general URL builder for manual entries is evidenced. Smallest fix: store an explicit URL or a carrier template choice in the tracking plugin and validate/escape it at render time.

**G3 — Buyer surfaces for arbitrary numbers:** shared provider status emails exist, but they require provider/status events; generic manual-number email and My Account/order-view renderers are not evidenced. Smallest fix: plugin-owned WooCommerce render hooks/templates, with one shared renderer across email and account order view.

**G4 — Duplicate suppression / ownership contract:** framework sent markers prevent a known duplicate shipment-created email, but no cross-plugin arbitration for manual tracking output is evidenced. Smallest fix: local suppression when recognized carrier data exists, plus a plugin filter for merchant override; validate against all four renderers before shipping.

**G5 — Settings-provider registration details:** the base class is established, but exact registration code for `woodev-settings` was not inspected in PHP. Smallest fix: follow the generic plugin settings-provider pattern from a current non-shipping fixture before implementation.

**G6 — Status polling for arbitrary carriers:** framework status journal expects a carrier `Orders_Provider` and canonical mapper; arbitrary manual numbers have no generic status source. Smallest fix: keep v1 parity at number/link display; add status sync only through explicit carrier adapters using existing status seam.

**Not established:** Serena MCP could not be activated in this worker, so framework and carrier PHP hook implementations, exact class symbols, and duplicate buyer rendering behavior remain unverified. No tests or runtime rig checks were run; no network calls were made.
