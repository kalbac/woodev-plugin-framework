# Settings and v1 migration

## Settings ownership map

The default settings page is `woodev-settings`. Add plugin-global settings through `Shipping_Plugin::get_tab_settings_providers()`, returning `Settings_Provider` descriptors whose handler is a `Woodev_Abstract_Settings` instance and whose sections use `Settings_Section::create()` or `create_connection()`. Per-method tariffs and options belong in `Shipping_Method::get_method_form_fields()` and are stored on that WooCommerce shipping-method instance. For shared settings patterns, see [woodev-plugin-core settings](../../woodev-plugin-core/settings.md), especially “Contribute a tab” and “Connection blocks”.

| Settings | Owner and location | Notes / example |
|---|---|---|
| Carrier credentials and authentication | Plugin-global settings handler section | Use `create_connection()` for a connection test; implement `\Woodev_Settings_Connection_Test::test_connection( string $connection_id, array $values )`. Mark secrets `sensitive => true`; use `constant_name` when an environment constant may supply the secret. See core [settings](../../woodev-plugin-core/settings.md) and `tests/_fixtures/woodev-test-plugin/woodev-test-plugin.php` (`Woodev_Test_Settings`). Do not copy `class-test-cdek-integration.php` here — it is the Integrations-tab exception demo. |
| Sender, origin, account, shared defaults | Plugin-global settings handler section | These values affect multiple tariffs; include them in the rate-cache context when rates depend on them. |
| Enabled methods and tariff-specific fields | WooCommerce shipping-method instance fields | Use `get_method_form_fields()`; use plugin-global settings only when the value truly is shared across instances. See `tests/_fixtures/woodev-realistic-shipping-plugin/includes/abstract-class-realistic-shipping-method.php`. |
| Default dimensions | Framework-owned `Вес и габариты` section | Store-wide fallbacks used only when product dimensions are missing: `Default_Dimensions_Settings`. |
| Packing and shipping classes | Per-method `Shipping_Method` feature declarations and fields | Use `FEATURE_BOX_PACKING` / `FEATURE_SHIPPING_CLASSES`; parcel packing comes from `woodev/box-packer/`. |
| Location source and default locality | Framework-owned `Локация` section | Added when the plugin opts in via `needs_location_provider()` and supplies its adapter. The provider registry owns provider selection and locality fields. |
| Pickup map and shared checkout behavior | Framework-owned `Карта` and `Форма заказа` sections | Map settings appear when the returned `Pickup_Handler` needs them. Do not add a second picker. |
| Order export, delivered/cancelled status, print documents, status refresh | Framework-owned `Выгрузка заказов` section, laid out as cards | Added when the plugin registers its `Orders_Provider` and shipment handler on this request. Cards (ids `auto-export`, `labels`, `delivery-status`): «Автоэкспорт», «Документы для печати» (the carrier's own fields), «Статусы доставки» (`status_delivered`, `status_cancelled`, the refresh button), then the carrier's own cards. Merchant values are in `Export_Settings`; `Order_Automation`, `Delivered_Order_Status` and `Cancelled_Order_Status` read them. The plugin does not contribute export settings through `get_export_settings()`. Keys, the button and the seams: [Framework sections of the carrier tab](#framework-sections-of-the-carrier-tab). |
| Logging, hide on the cart page | Framework-owned `Дополнительно` section | On EVERY carrier's tab, last. `Advanced_Settings` via `Shipping_Plugin::get_advanced_settings()`. |
| Status mapping and tracking details | Provider/handler configuration and order metadata | Define the carrier raw-status map and tracking metadata when building `Orders_Provider`; render events in `Abstract_Tracking_Handler`. |
| Tools | Framework-owned `Инструменты` section | Register actions through `Shipping_Tools_Registry`; this section exists only when a tool is registered. |

`Shipping_Integration` (`woodev/shipping-method/settings/class-shipping-integration.php`) is a valid compatibility seam for an existing WooCommerce Integrations surface, returned by `get_integration_handler()`. The default is `woodev-settings`; Rule 8 in `docs-internal/AGENT-RULES.md` leaves exceptions to the operator's judgment. Bring a concrete case to the operator instead of treating the Integrations tab as forbidden or deprecated. Preserve `woocommerce_{plugin_id}_settings` and other stored values during migration.

The shared shipping page (`Shipping_Settings_Tab::register()`) includes `Форма заказа`, `Вес и габариты`, optional `Локация` and `Карта`, registered `Инструменты`, and — on each carrier's own tab — `Выгрузка заказов` when export is configured and `Дополнительно`. Do not add duplicate sections or a second tools page. Sources: `woodev/shipping-method/settings/class-shipping-settings-tab.php` and `woodev/shipping-method/class-shipping-plugin.php`.

## Framework sections of the carrier tab

`Shipping_Plugin::get_settings_providers()` builds ONE tab per carrier: the carrier's own sections, then `Выгрузка заказов` (only for an exporting carrier), then `Дополнительно` (always). The section ids `export` and `advanced`, and the setting ids below, are reserved: a clashing contribution is reported with `_doing_it_wrong()` and left out. Stored values live in the framework settings API's options, `woodev_{plugin id underscored}_{handler}_{key}`; each handler carries the v1 integration-option values over once (`woocommerce_{plugin id}_settings`, done-flag `…_migrated_from_integration`, never overwrites a value saved on the new page).

| Section | Setting id (= v1 key) | Stored option | Values / default | Read by |
|---|---|---|---|---|
| `Выгрузка заказов` | `auto_export_orders` | `woodev_{id}_export_auto_export_orders` | `yes`/`no`, off | `Order_Automation` |
| | `export_statuses` | `woodev_{id}_export_export_statuses` | `wc-…` list, `[wc-processing]` | `Order_Automation` |
| | `status_delivered` | `woodev_{id}_export_status_delivered` | `wc-completed` (default), another `wc-…` status, or `none` = «Не менять» — **v1's own spelling, carry v1 `status_delivered` verbatim** | `Delivered_Order_Status` via `Export_Settings::get_delivered_status()` |
| | `status_cancelled` | `woodev_{id}_export_status_cancelled` | `wc-cancelled` (default), another `wc-…` status or `none`; applied when the carrier reports the shipment cancelled (#1203) | `Cancelled_Order_Status` via `Export_Settings::get_cancelled_status()` |
| `Дополнительно` | `enable_debug` | `woodev_{id}_advanced_enable_debug` | `yes`/`no`, off — **the ONE logging key** (the old `debug_mode` of the integration option is gone) | `Shipping_Plugin::is_debug_enabled()` |
| | `disable_methods_on_cart` | `woodev_{id}_advanced_disable_methods_on_cart` | `yes`/`no`, off | `Shipping_Plugin::hide_rates_on_cart_page()` |

- **Delivered status.** `Delivered_Order_Status` listens to `woodev_shipping_delivery_status_changed`; when the canonical state becomes `delivered` it moves the order to the chosen status ONCE per order and carrier (marker meta `_woodev_delivered_status_applied_{provider id}` — data contract), leaves an order already in that status alone, and NEVER touches a cancelled, refunded, failed or trashed order. A carrier writes no code.
- **Logging.** Off = errors only. A failure goes through `$plugin->log_error( $message )` — it always writes, at the ERROR level (the inherited `$plugin->log()` writes at WooCommerce's default NOTICE severity, which a shop whose logging threshold is «Error» silently drops, so do not log failures with it). `$plugin->log_debug( $message )` and the carrier API request/response lines (`log_api_request()`) write at the DEBUG level and only with «Логирование» on; use `log_debug()` for anything that is not a failure. Redact foreign exception text (`Woodev_API_Base::redact_secret_log_text()`) before it reaches either. The framework's own informational lines (upgrade start/end, «response not cached») go through the base `log_debug()`, which a shipping plugin gates; other plugin types still write them unconditionally, as before.
- **Hide on cart.** WooCommerce runs `woocommerce_package_rates` only when it recalculates and caches the FILTERED rates in the session under the package's hash — a filter that hides the carrier on the cart page alone would leak both ways (cart rates served at checkout, checkout rates on the cart). So the plugin marks the cart page's packages on `woocommerce_cart_shipping_packages` (key `woodev_hidden_on_cart`, a list of plugin ids; classic cart via `is_cart()`, block cart via a Store API request whose referer is the cart), which gives each context its own cache entry, and `hide_rates_on_cart_page()` removes this carrier's rates from a package marked for it. Cost: the carrier API is called once more when the shopper moves between cart and checkout. A plugin whose option is off marks nothing, so its hashes are unchanged. Never skip the carrier in `calculate_shipping()`. v1 showed (and honoured) this option only while WooCommerce's cart shipping calculator was OFF; v2 honours it always, so a v1 migration should carry a stored `yes` only if that calculator was off.
- **«Обновить статусы сейчас».** Shown under the export fields when the provider declares `cron_hook` (`Orders_Provider::create()` args): the framework fires that action by hand (`Status_Sync_Tool`), so the carrier's refresh callback must be attached to it and run outside WP-Cron. No `cron_hook` (webhook-only) = no button; a hook nobody listens to = a disabled button. The carrier records `Delivery_Sync_Status::record_last_updated()` as usual and the result message quotes it.
- **Your own fields in `Выгрузка заказов`** (CDEK's «Формат этикеток», say): register the setting in a handler of `get_tab_settings_providers()`, keep it out of that contribution's own sections, and return its id from the protected `get_export_section_setting_ids()`; it is shown after the framework's fields. An unknown id is reported and skipped; a non-exporting carrier ignores the seam.
- **Groups: cards inside a section (#1201).** `Settings_Section::create(...)->with_groups( [ Settings_Group::create( $id, $title, $description )->with_fields( [...] )->with_actions( [...] )->with_notice( '…' ) ] )` draws related fields and the actions that act on them as ONE titled card. A group only NAMES members by id; fields stay in the section's field map (values, validation, `show_if`, Save are untouched). Use it for the carrier's own tab — CDEK's «Отправка» is three cards («Склад», «Продавец и отправитель», «Заказ и расчёты»); the sender toggle sits with the seller because a filled-in sender books a third-party shipment. A group id equal to a framework card id, an earlier group, or an action id already used on the tab is dropped with `_doing_it_wrong()`.
- **Carrier cards inside «Выгрузка заказов».** Override the protected `Shipping_Plugin::get_export_section_extension()` to return `[ 'actions' => Shipping_Tool[], 'groups' => Settings_Group[], 'description' => string ]`; the framework appends them after its own cards (CDEK puts its «Вебхуки» card, with «Подключить»/«Отключить», next to «Статусы доставки»). Skipped silently for a carrier that does not export. Compiled reference: "Settings page — sections, actions and groups" in `docs-internal/wiki/architecture.md`.
- **Section buttons / a toggle's ON-only line (any settings page).** `Settings_Section::create(...)->with_actions( [ Shipping_Tool ] )` puts buttons under an ordinary section's fields (run through the same REST route as «Инструменты», scoped to the tab). `register_control( $id, TYPE_TOGGLE, [ 'description_on' => __( '…' ) ] )` shows one line under the toggle only while it is on (developer-authored text, rendered as HTML like `description`). A field blocked by `disabled_if`/`disabled` is painted disabled (grey fill, muted text).

## Migrating a v1 plugin

Inventory installed-site contracts in the old plugin: option names and values, shipping method IDs, order/session metadata keys, hook names/signatures, cron and REST routes, admin slugs, and existing orders' stored data. Internal APIs may change on v2; persisted or externally consumed contracts must remain byte-for-byte stable (ADR-005: `docs-internal/adr/005-platform-v2-clean-break-policy.md`).

Use a plugin-specific checklist from `docs-internal/migration/*`; explicitly map old keys to new framework fields. Migrate in-flight orders as well as settings, make migrations idempotent, and check for external readers before removing legacy keys. See `docs-internal/specs/2026-06-25-shipping-module-decisions.md` §19.

Run `npm run probe:signature` against the v1 source and follow `docs-internal/migration/signature-probe.md` to discover extension hooks and signatures that are easy to miss. Preserve real public contracts; do not mechanically carry over internal architecture. The worked example is the CDEK plugin's `includes/lifecycle/` and `docs/migration-v1-table.md` (v1 vs v2 settings 62/26 and order data 22).

### Know what is installed before you decide what to migrate

- **Migrate from the RELEASED code, not the repo head.** The released CDEK v1 is commit `dd5c76f` (2.2.5.5); `origin/master` (2.3.2) was never released and has no test mode. Gotcha [the released CDEK v1 is dd5c76f](../../../../docs-internal/gotchas/the-released-cdek-v1-is-dd5c76f-not-origin-master.md).
- **Set the oldest supported previous version by measuring the release archives**, not by memory. All 92 released CDEK zips were fetched and compared (s168): 2.2.0.6–2.2.5.5 carry fully; 2.2.0–2.2.0.4 lose four service codes; 2.0/2.1 keep settings in a different option (`woocommerce_edostavka-integration_settings`) and use 34 per-tariff method ids; 1.x shares the method id and option name of 2.x and would half-migrate silently. The operator's boundary (edostavka#51): ≥ 2.2.0 migrates automatically; 2.0/2.1 keep keys and the licence only (journal `unsupported_origin`, a wizard notice, hyphenated `edostavka-…` rows untouched); 1.x is neither supported nor detected. Write the boundary down and make the migration refuse what it cannot carry faithfully.
- **Do not carry a v1 code whose meaning changed.** CDEK's old carrier box codes (`S`, `L`, `500GR`, …) were NOT migrated: the live catalogue gives other dimensions under other codes (s158). A code the carrier still uses but you cannot rename is reported by name (`PHOTO_OF_DOCUMENTS`).

### Splitting a v1 method id

One framework method id is one delivery type ([model, rates, location, pickup](model-rates-location-pickup.md)). When v1 had one id for courier and pickup, the migration (a) keeps the zone instance's number and settings but rewrites its `method_id` to the new courier or pickup id, (b) rewrites references to the id — CDEK also fixed COD gateways' `enable_for_methods` — and (c) leaves old ORDERS recognisable under the old id everywhere (the orders filter, tracking, export). Verify with real zone rows, not fixtures (CDEK s157, `Cdek_Wpdb_Zone_Method_Store`).

### Mechanics that held up

- **Idempotent, journalled, fill-only.** Never overwrite a value the merchant already saved on the new page; record every key carried, skipped and `no_counterpart` in a journal (it doubles as the rollback and cleanup list). Map only EXACT counterparts: CDEK carried v1 checkout-field switches into `woodev_checkout_fields_*` / `woodev_location_allow_custom_settlement` only where a counterpart existed and left the rest at framework defaults (#1149). A v1 value the framework retired still reads: `single` packing is read as `virtual` ([packaging](packaging.md)), and a stored `related-list` field mode is clamped on read (#1216).
- **A migration that cannot be confirmed must not mark itself done.** The framework stores the new version only after the upgrade routine returns, so throw a retryable exception (`Cdek_Migration_Exception`), let the lifecycle `init()` catch it, show an error notice and run again on the next admin page load (`Cdek_Lifecycle::init()`). The routine also runs from `install()` — a missing version option reads as a fresh install on a live shop, so make it safe over existing data.
- **A failed read is not an absent option.** `get_option()` turns a failed SELECT into the default AND caches the name as absent, so a one-time migration derives behaviour from an error (a pickup method becomes a courier) and the version then advances. Read prerequisites through a verified reader (`$wpdb` row, `last_error` checked at once, the bad `notoptions` entry dropped, a retryable exception before anything is written). Autoloaded options need no guard — a failure there means the site is down. Gotcha [get_option turns a failed SELECT into the default and caches it](../../../../docs-internal/gotchas/get-option-turns-a-failed-select-into-the-default-and-caches-it.md); worked example `includes/lifecycle/class-cdek-wpdb-option-reader.php`.
- **Move v1's scheduled work with the data.** The stand showed the migration must cancel v1's recurring Action Scheduler actions (`wc_edostavka_run_update_order_hook`), map v1 statuses the new map lacks (`IN_PROCESSING` → pending) and make the orders page's «next update» show the real poll (edostavka#41, PR #44).
- **Carry each v1 option under its v1 key where the framework has the same option**: `status_delivered`, `fee_payments`, `include_insurance`, `services`, `min_cost`/`max_cost` (v1 `static_price` → `min = max`, fill-only), `dropoff_address`, per-method `sender_city`, `clean_address_field` → `woodev_location_clear_address_on_change`, `hide on cart` only if v1's shipping calculator was off. Sources: s158–s160, `docs/migration-v1-table.md`.
- **Stand up a migration stand before you trust a green suite.** CDEK's stand is a separate wp-env on :8990/:8991 with the REAL previous release installed, a sandbox-redirect mu-plugin and snapshots (`tests/migration-stand/`, edostavka#41). It found three migration defects no unit test saw, and the wizard can only be judged on a migrated site.

### Migration wizard

A migration is also onboarding. Build it on the Setup Wizard v2 engine (`Woodev_Plugin::get_setup_wizard_handler()`, `woodev/setup/`; contract `docs-internal/specs/2026-10-08-setup-wizard-v2-contract.md`, D1–D4; worked example `includes/setup/class-cdek-migration-wizard.php`):

- **The shop keeps working before anyone opens it.** Completed means the merchant reached the end (monotonic: `completed` is never overwritten by `skipped`), not that the plugin is ready — readiness is reported by the plugin's own notices. «Настрою позже» = `skipped`; the wizard stays reachable.
- A step is `skippable`, validates BEFORE anything is persisted (structured per-field errors), and may carry typed ACTIONS (destructive ones declare it and are confirmed); callbacks are wrapped in `Throwable`. The step graph is recomputed on the server after every save; a save for a hidden step is refused (409). A plugin-supplied React component can fill a step slot. `Step::set_short_label()` (#1210) gives the stepper a one-word label while the full label stays the card heading.
- v1-only: the wizard is shown only where migrated data exists; empty steps are hidden; things that could not be carried are REPORT steps (zones, services, orders left as they were). Show merchant-readable names, never raw carrier codes (bounded resolve, «код СДЭК N» fallback). Offer «Начать с чистого листа» (undo of the migration), «Очистить старые данные» (destructive; deletes only keys the journal recorded) and finish with an honest «Готово» that acknowledges the limits notice.
